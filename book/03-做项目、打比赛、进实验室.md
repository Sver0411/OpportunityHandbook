# 做项目、打比赛、进实验室

## 项目与作品

### 什么才算真正的项目

```meta
id: project-what-is-real
status: complete
stages: [college, undergraduate, master, work_1_3]
topics: [project]
outputs: [portfolio, work_experience]
effort: medium
evidence: [official, experience_based]
summary: 什么才算真正的项目：解决真实问题、有别人可验证的产物、经历过一次真实反馈——不同项目类型的验证方式不同。
last_verified: 2026-09-28
```

一个「真正的项目」有三条共同特征：**解决一个具体的真实问题**（哪怕是自己的）、**有别人可验证的产物**（能运行、能看、能用）、**经历过至少一次真实反馈与修改**。三者缺二，它更接近一次练习——练习有价值，但别当经历写。

## 从每周都会遇到的小问题入手

从自己的真实需求出发，选一个**小而完整**的题目，而不是大而空的「平台」。写一句话问题陈述——为谁、解决什么、怎么算解决——然后缩到一个月内能出第一版可用的规模。「做完」的标准提前定好：可运行的入口、README、最基本的验证、至少一个真实使用者（见下）。上线后收集反馈，按反馈做第二轮修改，并记录改了什么、为什么。

## 「可验证」在不同类型的项目里含义不同

不要用一种标准衡量所有项目。常见的是这五类：

| 项目类型 | 更该拿什么证明它是真的 |
| --- | --- |
| 产品 / 工具型 | 真实用户、留存、使用反馈、使用场景 |
| 工程型 | benchmark、性能与稳定性数据、测试覆盖、能否长时间运行 |
| 开源型 | Issue 与 PR 记录、contributor、release、被下游使用的情况 |
| 研究型 | baseline 对比、实验与消融、可复现的数据与代码、同行反馈 |
| 硬件 / IoT | 真机测试、丢包率与功耗、现场部署、传感器误差范围 |

对产品型项目来说，「有别人在用」是很强的证据；但一个编译器优化项目、一篇复现实验、一块电路板，它们的证据形态完全不同——**能说清「我怎么知道它有效」就够**。

## 判断它到了可以写进简历的程度

三个问题：有没有人用到它（用户、下游、读者或使用者）？结论能不能被第三方验证（数据、链接、报告）？别人能不能在几分钟内看懂它是什么、怎么跑起来？README 至少要有五样：一句话说明是什么、用在什么场景、怎么安装运行、演示（截图 / GIF / 在线地址）、已知限制——不写限制反而降低可信度。

写简历用「问题 → 做法 → 结果」格式，结果尽量落到具体数字（用户数、处理量、耗时、误差、省下的时间），不要写「使用 X 框架实现了 Y」。项目多而浅是常见病：几个半成品不如一个能讲透的项目；把教程项目当原创、把 star 数当唯一指标、项目无法在你自己机器上重新跑起来，都是面试里一问就破的。

## 代价要说清楚

几十到几百小时的投入；上线之后的维护成本（Issue、兼容、更新）最常被低估——**发布不是结束**。被指出 bug 与被批评的心理成本也真实存在。换回的是经得起追问的一行简历、面试里能讲二十分钟的故事，有时还有工作与合作机会。注意边界：目标岗位以考试、资历、执业资格为主要筛选时，把时间投到对应门槛上，别硬做项目。

### 教程项目有没有价值

```meta
id: project-tutorial
status: complete
stages: [college, undergraduate]
topics: [project]
outputs: [portfolio]
effort: low
evidence: [experience_based]
summary: 教程项目有没有价值：为什么它常被认为「练习」、什么时候它能变成经历，以及改造的三个动作。
last_verified: 2026-09-27
```

跟着教程做出来的东西本身不是问题，问题在于**它没有回答任何人真正遇到的问题**。判断标准很简单：除了你，还有谁会在意它？

## 为什么教程项目常被当作练习
- 需求是别人设的（教程作者已经验证过它能跑通）；
- 路径是给定的（不需要你判断该做什么、不该做什么）；
- 结果是已知的（没有不确定性，也就没有决策可讲）。

面试里追问「为什么这样做」，如果答案是「教程里就这么写的」，这段经历的说服力就到此为止。

## 什么时候它能变成经历
当你在教程基础上做了**至少一件教程没写的事**：

1. **换输入**：用你自己的数据/场景跑一遍（例如把示例数据集换成你专业相关的一份）；
2. **加约束**：在真实条件下运行（断网、低配设备、数据脏、并发）；
3. **加判断**：改一个设计并说明为什么（换算法、换存储、换交互），用数据比较结果。

三个里做一个，性质就从「练习」变成「基于真实条件的改造」。三个都做，就是一个小作品。

## 改造后的写法
```
起点：跟着 X 教程实现了 Y（一句话，诚实说明起点）
改造：我换了 Z 数据 / 加了 W 约束
判断：比较了两种方案，选择 A 因为 <理由 + 数据>
结果：<指标或事实>，代码与说明在 <链接>
```

**诚实说明起点反而加分**：它表明你知道自己在哪一层，而不是把教程包装成原创。

## 什么时候不值得改造
- 教程内容与你目标方向无关（那就换一个）；
- 已经有一个更完整的项目（把时间投在更接近目标的事上）；
- 改造成本接近重做一个（那就直接做自己的）。

## 它的真实价值
认真跟完一个教程，换来的是技术栈的初始理解和一套可改造的代码基底。对初学者这是必要的阶段；问题出在止步于此——连续跟五六个教程获得「学了很多」的错觉，却从未脱离教程自主排错。

## 怎么把教程变成自己的东西
跟完立即做「改造练习」：换数据源、换核心功能、加一个教程没有的需求。遇到教程没覆盖的问题，查官方文档解决——这一步才是真实工作的常态。把改造后的版本作为第一个「自己的项目」，写清与原教程的差异。简历上不写教程项目原样，只写你在其之上做出来的东西。

## 把改造过的版本变成第一个自己的项目
有了第一个改造过的项目，就可以按 [什么才算真正的项目](03-做项目、打比赛、进实验室.md#project-what-is-real) 的标准升级成完整经历。

### 第一个个人项目怎么开始

```meta

outputs: [portfolio]
effort: medium
evidence: [experience_based]
summary: 第一个个人项目怎么开始：给自己解决一个真实痛点——需求真实、你懂用户、还能长期维护。
last_verified: 2026-09-21
```

个人项目的价值公式是**真实需求 × 完成度 × 展示质量**。最可靠的选题方向是「给自己解决一个真实痛点」：因为需求真实、你懂用户、还能长期维护。

## 先找出你每周重复做的麻烦事
列出你每周重复做、又麻烦的事，挑一个能用程序或流程解决的。第一版限制在两周内能用，功能只留最核心的三个；做完后自己真实使用两周，记录所有别扭的地方——这就是第二轮的清单。给它一个干净的 README（解决什么、怎么用、截图或演示），有真实用户后认真处理反馈，哪怕每月只有一两条。

## 一个能演示、能迭代的作品，代价是长期维护
做个人项目换来的是一件**能演示、能讲述、能继续迭代的作品**，以及完整走一遍「定义问题—实现—维护」的经验；如果做得好，还会有真实用户。

代价是数周到数月的业余时间，以及**长期维护**：只要还有人在用，它就会持续要求你修东西。这也是项目最容易被低估的部分——「做出来」不是终点，真正的成本在「做出来之后」。

## 三个常见死法
技术炫技但无人受益；功能膨胀导致烂尾；上线后再也不维护。反过来的极端——同时开五六个项目每个都半成品——同样要避免。选题追热点但自己不用的，做不出来也留不住。

### 团队项目

```meta
id: project-team
status: complete
stages: [college, undergraduate, master]

outputs: [work_experience, network]
effort: high
evidence: [experience_based]
summary: 团队项目练的是个人项目练不到的东西：分工、约定、依赖别人的进度，以及吵架之后还能把事做完。
last_verified: 2026-09-21
```

团队项目练的是个人项目练不到的东西：**分工、约定、依赖别人的进度、以及吵架之后还能把事做完**。雇主看团队项目，看的正是这些信号。

## 开工前的三条底线
三到五人、能力互补、时间表能对齐——缺一就先别开工。开工前书面约定：目标、分工、代码与文档归属、谁对外负责。用真实的协作工具与流程：任务看板、代码评审、每周同步。每个阶段都要有可交付物，而不是最后一个月赶工。

## 规模与协作经验，代价是沟通与依赖
和别人一起做，换到的是**真实的协作与版本管理经验**、一个人做不出的规模，以及日后可以互相背书的队友。

代价同样具体：沟通成本经常超出预期，进度可能被队友拖慢，利益与署名必须在开始前就写清楚。做完之后互相写一句**具体的**评价——「他负责数据管道，并扛住了三次需求变更」比「合作愉快」有用得多。

## 什么情况不如做个人项目
找不到靠谱队友、每次都自己扛所有事的人，先做个人项目；为组队而组队、目标不一致的草台班子，产出的信号是负的。一人干活全队署名、成果归属扯皮、烂尾后互相拉黑，是团队项目最常见的三种坏结局。

```meta

last_verified: 2026-09-27
```

这一页讲的是**自己这一侧的整理**：把做过的事按可展示的方式组织起来，长期维护，随时能抽出材料。投递时怎么裁剪给具体岗位看，见 [作品集怎么用于投递](05-从学校走向第一份工作.md#resume-portfolio)。

## 三类内容与取舍
| 类型 | 适合证明 | 保留几项 |
| --- | --- | --- |
| 个人项目 | 主动性、完整交付能力 | 1–2 项，选最完整的 |
| 团队/实习项目 | 协作、工程规范、真实约束 | 1–2 项，写清你的模块 |
| 公开产出 | 表达、影响力（文章、开源、数据集） | 1 项，选有反馈的 |

**总量控制在 3–5 项**。十项半成品会稀释重点。

## 每个条目写什么
```
背景：解决什么问题、给谁用（2 行）
我的角色与关键决策：做了什么、为什么这样选（3 行）
结果：数据或可核对的事实（1 行，带口径）
链接：代码 / 演示 / 报告
限制：已知问题与未完成部分（1 行）
```

**写清限制反而加分**：说明你知道边界在哪。

## 排序原则
- **按目标调整**：投研发把技术深度放前；投产品把问题定义与用户反馈放前；投数据把口径与方法放前；
- **可验证优先**：能点开链接的排前面；
- **时间近的优先**：除非旧项目更能说明能力。

## 常见失效原因
| 原因 | 表现 | 改法 |
| --- | --- | --- |
| 只有截图没有说明 | 看不出你做了什么 | 补上角色与决策 |
| 链接失效 | 点开是 404 | 每次投递前逐个检查 |
| 需要登录才能看 | 评审看不到 | 提供公开版本或截图说明 |
| 与岗位无关的凑数 | 重点被稀释 | 删掉 |
| 夸大规模 | 面试追问即露 | 写清团队规模与你的部分 |

## 与其他材料的关系
简历里放最相关的 2–3 项 + 链接；面试准备两个版本的口头讲法（3 分钟与 10 分钟）；申请材料里把作品与项目经历合并表述，避免重复（见 [简历怎么写](05-从学校走向第一份工作.md#job-hunting-resume)）。

## 怎么搭
选三个最能代表目标岗位能力的项目，宁缺毋滥。每个项目写统一结构：问题 → 你的方案 → 关键难点与解决 → 结果（数字或演示）→ 链接；再配一个三十秒内能看完的演示（截图或录屏）。排序按**与目标岗位的相关度**，不是时间倒序。每半年更新一次：删掉过时的，替换更强的。

## 提高的是简历通过率与面试主动权
整理作品集换到的是三样：简历通过率、面试里的主动权，以及对自己能力结构的清楚认识——写的时候你会发现，哪一块其实拿不出手。

代价不大，但需要持续：每个项目几小时的整理（写清问题、截图、录一段演示），加上定期维护链接与内容。

## 四个常见错误
十个仓库全是半成品；只有代码没有讲述；简历与作品集口径不一致；链接失效或打不开。只搬运 README、没有任何自己加工的，不算作品集。

### Demo

```meta
id: project-demo
status: complete
stages: [college, undergraduate, new_grad]
topics: [project]
outputs: [portfolio]
effort: low
evidence: [experience_based]
summary: Demo 要做到什么程度：三种演示形态的取舍、录屏与截图的规范，以及演示最容易出错的地方。
last_verified: 2026-09-27
```

Demo 的作用是**让人在很短时间里相信这件事真的做出来了**。它的标准不是好看，而是能被看懂、能被验证。

## 三种形态与取舍
| 形态 | 成本 | 适合 | 注意 |
| --- | --- | --- | --- |
| 线上可访问（部署后的地址） | 中 | Web/App 类项目 | 域名与稳定性，别在演示时挂掉 |
| 录屏（30–90 秒） | 低 | 交互流程、硬件演示 | 提前录制，避免现场网络问题 |
| 截图 + 说明 | 最低 | 数据类、分析类项目 | 一图一句结论，标清口径 |

**最优组合**：一段 60 秒录屏 + 一张截图 + 一个可点开的链接。

## 录屏与截图的规范
- **先给结论**：开头 5 秒说明「这是什么、解决什么问题」；
- **只演示核心流程**：不要展示所有功能；
- **画面干净**：关掉无关窗口、隐藏个人信息；
- **配字幕或旁白**：没有声音也能看懂；
- **控制时长**：控制在两三分钟内。再长，注意力就散了，核心信息也会被淹没。

## 最容易出错的地方
| 错误 | 后果 | 改法 |
| --- | --- | --- |
| 现场演示依赖网络/设备 | 崩了就没有替代 | 准备录屏与离线版本 |
| 展示功能但不展示结果 | 看不出价值 | 结尾放出数据或用户反馈 |
| 全屏操作无说明 | 评审看不懂在做什么 | 加步骤说明或旁白 |
| 截图没有标注 | 不知道重点在哪 | 用一句话说明结论 |
| 链接失效 | 等于没有 Demo | 每次投递前点开检查 |

## 什么时候需要 Demo
- 投递简历与作品集（链接）；
- 面试讲项目（现场演示比口头描述有说服力）；
- 创业或产品验证（Demo 是拿到反馈的最快方式）。

## 什么样的 Demo 有用
- **短**：两三分钟讲完——解决什么问题、怎么解决、效果如何；
- **真实**：用真实数据或真实场景，哪怕规模很小；
- **可访问**：一个链接（部署页面或录屏），打开就能看，不需要对方配置环境。

## 最短路径
录屏加旁白是最便宜的方案：屏幕录制软件加一份三分钟讲稿。演示只走核心流程，别的放在附录；Web 项目尽量部署一个公开地址。

```meta
summary: 数据、测试和指标怎么用：三种证据各证明什么、项目里最低限度的做法，以及没有它们会出现什么问题。
last_verified: 2026-09-27
```

项目里的「数据、测试、指标」是三种不同性质的证据，常被混着说，结果面试时说不清。

## 三者各证明什么
| 证据 | 回答什么问题 | 没有它会怎样 |
| --- | --- | --- |
| 测试 | 功能在预期输入下是否正常 | 改一处坏一处，别人不敢用 |
| 指标 | 效果如何、是否变好 | 只能说「感觉更好了」，无法比较 |
| 数据记录 | 运行过程中发生了什么 | 出问题只能靠猜，无法复盘 |

**三者不必都齐全**，但要清楚自己在用什么证明什么：练习类项目至少要有测试；面向用户的项目至少要有一个指标；长期运行的项目要有日志。

## 最低限度怎么做
**测试**：不必追求覆盖率，抓住核心路径——输入校验、关键流程、一个边界条件。能自动化就自动化，不能就写成手动检查清单。

**指标**：选一到两个能反映价值的数字，并写清口径：

```
指标名：任务完成耗时
口径：从提交到返回中位数，仅统计成功请求，样本 n=200
对比：优化前 1.2s → 优化后 0.4s（同机同数据）
```

**数据记录**：日志里至少包含时间、输入摘要、结果状态、异常信息。用于复现与排查。

## 常见问题
- **把「跑通了」当成测试**：跑通一次不等于稳定，边界与异常最容易出问题；
- **指标没有口径**：说「提升了 30%」但不说怎么算的，追问一句就崩；
- **只记录成功数据**：失败与异常不记录，导致无法分析；
- **数据不能公开就用描述代替**：涉密或敏感时，写清方法与范围，说明可提供的证据类型。

## 在面试与作品集里怎么用
用一句话把三者串起来最有说服力：

> 我给它加了核心路径的测试（覆盖下单与退款），记录了请求耗时中位数（从 1.2s 降到 0.4s，样本 200），并把异常写进日志便于排查。

**这比「做过性能优化」有力得多**，因为它可被追问且可被验证。

## 三件小事
- **定一个核心指标**：做好了的标志是什么？响应时间、准确率、转化率——写下来，别凭感觉说「效果不错」；
- **留基线对比**：改进前后的数字放在一起，「0.72 到 0.81」比「显著优化」可信得多；
- **加最基本的测试**：核心流程能自动跑通的一组检查，保证别人接手或三个月后的你，项目还能跑。

## 为什么值得做
面试里问「你怎么知道它有效」，答得出数字和对比的人很少。这也是把课程项目升级成可展示经历最便宜的方式，见 [什么才算真正的项目](03-做项目、打比赛、进实验室.md#project-what-is-real)。

## 别过度
课程项目不需要工程级的测试覆盖率。核心流程有检查、关键数字有记录，就已经超过多数同龄人；指标也不要贪多，一个核心指标足够。

### 真实用户与反馈

```meta
id: project-users-feedback
status: complete
stages: [college, undergraduate, new_grad]
topics: [project]
outputs: [portfolio, project]
effort: medium
evidence: [experience_based]
summary: 真实用户与反馈怎么获取：为什么熟人反馈无效、三类可获得反馈的方式，以及拿到反馈后怎么处理。
last_verified: 2026-09-27
```

项目从「练习」变成「作品」，关键是拿到**来自真实使用场景的反馈**——不是熟人出于情面给出的评价。

不同项目类型的「真实反馈」形态不同：产品与工具类看真实用户的使用与留存；工程类看压测、稳定性与线上故障；开源项目看 Issue、PR 与下游使用；研究类看复现、审稿意见与同行质疑；硬件类看现场部署与长期运行数据。共同点是：反馈来自场景，而不是来自关系。

## 三种能拿到真实反馈的方式
1. **垂直社群**：把你的工具发到目标用户聚集的社区，看有没有人实际使用（发帖要写清解决什么问题，而不是只发链接）；
2. **直接邀请**：找一批符合目标画像的人请他们试用一次，并观察过程（**看行为不看评价**）。人数不必多，够看出重复出现的问题就行；
3. **公开使用数据**：如果无法面谈，用访问量、留存、完成率等数据判断（哪怕数字很小）。

**优先级**：能观察到使用过程的 > 只看数据的。原因是你需要知道他们**卡在哪一步**。

## 怎么问才能拿到有用信息
不要问「你觉得怎么样」（会得到礼貌回答）。改问行为与事实：

- 「你上一次遇到这个问题是什么时候？当时怎么解决的？」
- 「刚才使用时，哪一步让你犹豫了？」
- 「如果明天这个工具不能用了，你会怎么办？」

**记录三类信息**：谁在用、用在什么场景、卡在哪一步。

## 反馈怎么处理
- **先分类**：是 bug（必须修）、理解问题（改文案或引导）、需求（判断是否在范围内）；
- **不要全做**：用户说什么就做什么会让项目失去重心；只做与核心价值相关且多次出现的；
- **记录决策**：为什么做、为什么不做的写一行，日后回看会发现判断依据。

## 常见误区
- **只找朋友**：得到「挺好的」，没有信息量；
- **只收集不行动**：反馈表填满，产品没变；
- **把抱怨当否定**：用户指出问题通常意味着他们在使用；
- **过早追求规模**：少数真实使用者的具体反馈，比泛泛的曝光数据更有信息量。

## 拿不到用户怎么办
这本身是信息：说明你选的问题可能不是别人真正关心的。此时有两个选择——**换问题**，或者**把这个项目定位成技术练习**（保留代码与文档，不宣称有用户）。

## 怎么找到第一批用户
从最近的圈层开始：同班同学、社团成员、目标场景里的人群。把项目放到他们真实使用的地方，而不是等「上线了自然有人来」。

## 收集什么反馈
- 他们**实际用在哪一步、在哪一步放弃**（行为比口头意见真实）；
- 最让人生气的三件事是什么；
- 有没有人把它用在**你没想到的场景**——这常常是真正价值的线索。

## 怎么回应
不承诺「马上改」，先记录、归类、挑影响最大的一个改掉，并告诉提反馈的人改了。这个闭环会让第二批反馈质量明显提高。

## 写进简历怎么写
「十个真实用户、留存 X 人、根据反馈重做了 Y」比「开发了某系统」有力得多。注意边界：只收集必要信息、说明用途，不要过度采集。

这一页只回答一个问题：**以我现在的处境，这场比赛值不值得占用我接下来的这段时间。** 至于某个具体赛事的分量如何评价，见 [怎么评价一个具体赛事](03-做项目、打比赛、进实验室.md#competition-what-worth-joining)；遇到收费可疑的赛事，见 [怎么识别低质量赛事](14-避坑.md#trap-paid-competitions)。

## 先看它和你的目标有没有关系

同一个比赛，对不同目标的价值完全不同：升学认定要求它在本校认定目录内；求职看的是它能产出什么作品；技能训练看训练密度与反馈质量。如果你的目标是「简历上多一行」，那它的优先级通常低于一段实习或一个完整项目。

## 再算成本与窗口

- **时间**：备赛周期是几天、几周还是几个月——从你的主线（课程、实习、申请）里扣；
- **金钱**：报名费、材料与设备、差旅；
- **机会成本**：这段时间如果不用来比赛，你实际会做什么（见 [什么叫机会成本](00-从这里开始.md#judge-opportunity-cost)）；
- **恢复成本**：连续作战之后需要多久才能回到正常节奏。

关键提醒是**窗口**：有些机会错过就没了（应届身份、限定年度的赛事），有些每年都有。前者值得为它调整节奏，后者不必挤。

## 什么情况下值得投入

- 与你目标方向一致，且产出可直接用于简历、作品集或申请材料；
- 你正缺一次**完整交付**的经验（从问题到成品走完一遍）；
- 团队与指导条件具备：有靠谱队友、有能问的人；
- 时间不与你当前的关键节点冲突。

## 什么情况下可以不投

- 参加它的唯一理由是「别人都在参加」；
- 备赛期间正好压着考试、实习或申请的关键节点；
- 你已经有同类产出，这次只是重复一次相似经历；
- 团队席位数不齐，而你实际要承担大部分工作。

## 决定参加之后

把产出当成任务清单的一部分：作品或报告、一页复盘（做对了什么、卡在哪、下次改什么）、能公开的验证材料。**赛后尽快整理**，趁过程、判断和失败细节还记得的时候完成——拖过一两周，细节就只剩下「参加了某个比赛」。

## 先确定用途，再谈值不值

| 你的用途 | 更该看的赛事 |
| --- | --- |
| 升学认定（保研加分等） | 本校认定目录内的赛事（以当年文件为准） |
| 求职（技术 / 设计 / 内容） | 有可展示产出的赛事 |

## 评价一个赛事时值得核对的几项

- **主办方与评审**：主办方能否查到实体机构与往届记录；评分标准、评委构成、获奖名额是否有公开说明；
- **外部认可**：本校认定目录（逐校逐年在变）、目标单位是否看它——认可度要问评价者，不要问主办方；
- **往届水平**：往届获奖作品长什么样、你够不够得着。够不着且备赛时间不足时，多数参与者拿不到有分量的结果；
- **能带走的产出**：作品、报告、数据集、评测结果、协作经历——只有证书而没有产出的赛事，作用有限；
- **团队与时间**：团队赛的成败常在协作，不在个人能力；时间是否与考试、实习、申请冲突。

如果大部分问题都答不上来，说明对这个赛事的信息还不够，先别急着投时间。

## 一个实用判断

把「这个奖能帮我过哪道门槛」和「这段过程能让我多会什么」分开问。两个都答不上来的赛事，无论名字多响，对你的价值都有限；两个都有答案的，即使名字不响，也值得投入。

## 奖项在什么场合起作用

奖项是筛选信号，主要作用是过初筛，而且**只在有明确认定规则的场合**生效：

- 保研与校内评奖：按本校认定目录与分值计算，规则以学校文件为准；
- 部分体制内岗位招录：会看奖项，但通常同时看其他条件；
- 升学申请：授课型项目看综合材料，研究型项目更看研究能力证据。

同一个奖在不同学校的认定差异很大，写简历时写清级别、名次与年份，避免含糊。

## 过程怎么变成证据

参赛之后真正耐久的东西是过程，把它变成可核对的形式只需要三步：

1. **整理作品**：代码、设计稿、报告或演示，写清问题、你的角色、结果；
2. **写一页复盘**：做对了什么、卡在哪、下次改什么；
3. **留可核对材料**：数据、评测结果、评审意见、用户反馈——能公开的公开。

为什么它更耐久：奖项只能证明「拿过奖」，过程能证明「你怎么解决问题」，而后者才是面试与申请里被反复追问的部分。

## 一张表看清两者权重

| 用途 | 奖项权重 | 过程权重 |
| --- | --- | --- |
| 保研 / 校内评奖 | 高（按本校认定目录与分值） | 低 |
| 留学（授课型） | 中 | 中（文书里要讲清） |
| 留学（研究型） | 低 | 高（研究能力证据） |
| 求职（技术 / 设计 / 内容） | 低到中 | 高（可展示的作品与判断） |
| 求职（体制内、部分国企） | 中 | 中 |

## 两个常见误判

- **「没拿奖就白参加了」**：只要留下作品与复盘，经历仍然有效，尤其是它同时是你作品集的一件；
- **「拿了大奖就够了」**：只写奖项、讲不出细节，在被深入追问时反而失分。

数学建模类竞赛的核心价值是**在 72–96 小时内完整走一遍「把现实问题翻译成数学问题、求解、写成论文」的流程**——这个训练对理工、经管、生物、环境等几乎所有需要数据分析的专业都通用。本科组与专科组分开评奖，高职高专学生同样有专属赛道。

## 主赛怎么参加
主赛是全国大学生数学建模竞赛（创办于 1992 年，每年 9 月举行，中国工业与应用数学学会主办，官网 mcm.edu.cn），报名与论文提交经竞赛管理系统进行，参赛费用由学校按标准承担，学生一般不直接向全国组委会交费。美赛（COMAP 主办的 MCM/ICM）是平行选择，时间、赛制与国赛不同，报名费自理。留意竞赛的 AI 工具使用规定（近年试行），违规使用会被取消评奖资格。

## 怎么备赛
组队按「建模 + 编程 + 写作」三角色互补——三个人都会编程却没人会写作，是最常见的失败配置。赛前用往年真题完整模拟至少三轮；比赛第一天别把半天耗在选题犹豫上。

## 三天的完整建模训练，代价是赛前数月的准备
数模换到的是一篇**完整走完「建模—求解—写作」的论文**、三个人的协作经验，以及在保研与评奖中被广泛认可的奖项（国家级奖项的认可度更高）。

代价主要在赛前：三天的比赛只是最后一步，前面是数月训练与组队磨合。判断标准很直接——**如果数学或编程基础接近零，又没时间补，指望赛前突击一个月拿奖，就不必参加**。

工程类竞赛（电子设计、机器人、智能车、结构设计等）与算法竞赛的最大区别是：**你的产出是实物，而实物会被现实条件打败**。

## 时间分配的现实（以 3–6 个月备赛为例）
| 阶段 | 占比 | 主要工作 |
| --- | --- | --- |
| 方案设计 | 15% | 需求分析、器件选型、可行性验证 |
| 实现 | 40% | 电路/结构/代码，反复调试 |
| 联调与稳定性 | 25% | 现场条件的各种意外（电源、干扰、温度） |
| 文档与答辩 | 20% | 报告、图纸、演示脚本 |

**最常见的失分点是把文档与答辩压到最后三天**——而评审里它们的权重往往不低于功能实现。

## 选题与器件选型
- **选能做完的题**：宁可功能少、做扎实，也不要贪多导致现场跑不起来；
- **器件要留余量**：关键器件买备份；采购周期常比预期长（提前 3–4 周下单）；
- **避免冷门器件**：资料少、出问题没人帮你；
- **先做最小闭环**：电源 → 主控 → 传感器 → 输出，逐段验证，不要一次性全接。

## 硬件调试的真实难点
- **偶发问题最难查**：十分钟出现一次的故障，通常来自电源波动、接触不良或代码里的竞态；
- **记录一切**：每次改动前后现象、参数、结果。**不做记录的调试会重复走同一条死路**；
- **先分离软硬件**：用最简单的测试程序验证硬件，再叠加复杂逻辑；
- **现场条件不同于实验室**：电压、电磁环境、光照、温度都会变，**按现场条件测试一次是必须的**。

## 团队分工
三人左右的队伍常见有效分工：硬件（电路/结构）、软件（控制/算法）、测试与文档（含答辩）。**必须有人专职负责文档与演示**，否则最后一定来不及。

## 答辩怎么准备
- 三段式：要解决什么问题 → 我们的方案与关键取舍 → 实测结果（带数据）；
- 准备「如果条件变成 X」的问题（评委常问）；
- 演示脚本写成步骤清单，**准备备用方案**（录屏、照片、备用样机）。

## 投入产出判断
- 与目标岗位对口（硬件、机械、自动化）→ 优先级高，产出可直接写进简历；
- 已有实习与项目 → 边际收益下降；
- 时间与课程冲突严重 → 宁可选周期短的赛题，或换赛道。

## 怎么参加
学校社团、科技企业、开发者社区都会办，优先选有明确评审与真实赞助方的；正规 hackathon 一般免费，收费的要警惕。赛前定好分工与选题方向，现场再微调——纯现场组队的成功率低。目标设为「能跑的 demo + 能讲的故事」，而不是功能完整；追求完美架构导致 demo 都跑不起来是头号错误。结束时把代码放公开仓库、写一篇复盘，让这个周末留下长期证据。

## 一个能演示的原型，代价是一个周末
参加这类比赛，换到的是一个**可演示的原型**、一次产品—设计—技术完整配合的体验，以及一圈同伴。企业命题的比赛还可能直接通向面试。

代价是一个周末，熬夜的强度要有心理准备。如果想体验更大规模的工程协作，机器人、智能车这类长周期赛事的投入和周期都更大，需要组队与经费。

编程竞赛（算法类）与数据竞赛（Kaggle 类）训练方式差别很大，但有一条共同原则：**训练要能被复盘，否则只是消耗时间**。

## 算法竞赛怎么练
- **按主题补短板**：把自己常错的类型（图论、动态规划、字符串）列出来逐类攻；
- **赛后补题**：比赛结束后把没做出来的题补完，**这一步的收益高于再打一场**；
- **限时模拟**：按真实时长与规则模拟，训练读题速度与取舍（哪些题该放弃）；
- **组队配合**：明确分工（读题、实现、验证），练习交流方式（如何快速说明思路）。

## 提分之外更要紧的事
比赛结束后尽快整理（趁过程与失败细节还记得）：

1. **代码与说明**：问题、数据、方法、验证方式、结果；
2. **关键决策记录**：试过什么、为什么放弃、最终为什么这么选；
3. **可复现说明**：环境、随机种子、运行步骤。

**面试里真正加分的是「你做过哪些判断」**，而不是名次本身。

## 算法竞赛与数据竞赛，哪个更适合你
- 想进入算法/数据方向且缺少项目 → 值得（能快速产出完整流程的证据）；
- 已有真实业务项目 → 边际收益下降；
- 时间紧（考试、毕业）→ 选赛程短的赛事，避免长期战线；
- 想练工程能力 → 竞赛的提分乐趣可能掩盖工程能力缺口，需额外补。

## 算法竞赛：信号极强，但高度头部化
程序设计竞赛（ICPC 及国内区域赛、蓝桥杯等）的奖牌信号极强，**铜奖以下的信号有限**。它的真实受众是愿意以年为周期训练算法的人——数百道题起步，天赋与训练量双重门槛。先用二十道基础题测自己是否愿意长期投入，再决定报赛；训练体系比刷题数量重要：分类刷、限时刷、赛后复盘题解。中学阶段的信息学奥赛路径以中国科协青少年科技中心的官方说明为准。注意别为竞赛牺牲 GPA 到影响保研底线。

## AI 与数据竞赛：确定性更高
以 Kaggle 为代表的数据竞赛，价值在于**在真实数据集上解决一个有评测标准的问题**，产出可以直接写进简历：「方案排名前 x%」比「学习过机器学习」有力得多。门槛比算法竞赛低：从入门赛（Getting Started 系列）走完全流程，别直接冲奖金赛（头部化严重，别用奖金做决策预期）；每场赛后读前三名方案，对比差距——这一步比参赛本身涨得快；把成果整理成报告或代码仓库，投岗位时直接给链接。

商业与创业类竞赛分两种，评价逻辑完全不同：**案例分析赛考结构化分析**，**创业计划赛考构想是否可信**。

## 案例分析赛：把问题拆开并收口
```
1. 读材料：20 分钟内找出「要做的决策是什么」
2. 定标准：利润 / 份额 / 风险 / 可行性，选 2–3 个作为判断依据
3. 拆模块：市场、竞争、成本、能力，逐块分析
4. 量化：能算就算（单位经济、盈亏平衡），比形容词有力
5. 收口：一个明确建议 + 三条落地动作 + 主要风险
```

**评分点在逻辑，不在结论对错**：假设是否标明、数据是否有来源、建议是否可执行。

## 创业计划赛：评委看什么
- **需求真实性**：有没有人已经在为这个问题花钱？你访谈过几个用户？
- **验证证据**：手工交付、预售、原型测试——**没有验证证据的项目通常排在后面**；
- **单位经济**：单价、成本、获客方式，能否算清；
- **竞争与替代**：用户现在用什么，你凭什么被选择；
- **团队匹配**：谁负责什么，为什么是你们做这件事；
- **里程碑**：未来 6 个月做什么、验证什么（不要只写三年后的收入）。

## 路演与答辩
- 10 分钟讲清：问题 → 方案 → 证据 → 商业模式 → 团队 → 需要什么；
- 预判追问：数据来源、市场规模算法、竞争对手、成本结构、失败预案；
- **答不出时如实说明**，比临时编造安全（评委通常问细节就能识破）。

## 投入判断
- 目标咨询/金融/产品方向且缺少结构化训练 → 案例赛价值较高；
- 目标自己创业 → 竞赛提供外部检验与同侪反馈，但**真实用户验证更重要**；
- 只为「简历多一行」→ 优先级通常低于实习与项目；
- 时间冲突明显 → 选赛程短的赛事，或放弃。

## 怎么做出彩
- 把市场估算拆成可核实的数字来源，别拍脑袋给「千亿市场」；
- 财务模型自己动手算一遍——评委追问第二层时能否接住，差距就在这里；
- 分工要真分工，别让一个人写完全部材料，那样你只练了排版。

## 一个重要提醒
比赛的好成绩证明你**讲商业故事的能力**，不证明市场需求存在。真想创业的话，用最小成本去验证需求，见 [创业前应该验证什么](08-自由职业、副业与创业.md#startup-validate-before-quit)。

## 想练商业推演或体验团队作战的人
想练商业分析、计划读商科、或想体验一次完整团队作战的人。只为「简历上多一行」参加，性价比不高。

设计、写作、影像、游戏等创作类竞赛的评审标准与工程类不同：**评委看到的是成品，看不到你的过程**。因此「可读性、完成度、风格一致性」往往比创意本身更决定名次。

## 评审通常在看什么
| 维度 | 具体表现 |
| --- | --- |
| 切题 | 是否回应当届命题，而不是自我表达 |
| 完成度 | 细节是否处理到位（排版、错别字、试玩体验） |
| 一致性 | 风格、色调、语气、机制是否统一 |
| 可读性 | 评委能否在几分钟内理解你的意图 |
| 说明质量 | 附的作品说明能否让评委看懂设计决策 |

**最常见的失分是「作品不错但看不懂」**——没有作品说明、没有过程图、没有玩法指引。

## 从命题到交付的流程
```
1. 拆命题：它要的是什么态度、什么场景、什么限制
2. 找参考：三到五个同类优秀作品，明确自己不想重复什么
3. 定范围：按剩余时间倒推能完成的体量（宁可小、做完整）
4. 先做核心：先完成「最能让评委看懂」的部分
5. 留时间做打磨：字体、配色、节奏、导出格式
6. 交付材料：作品 + 说明（含设计决策与过程）
```

## 时间不够时的取舍
- 保留：核心概念完成度、说明文档、可直接查看的成品；
- 砍掉：附加功能、复杂的动态效果、不影响理解的细节；
- 不要砍：错别字与格式检查——这类问题在评选中格外显眼。

## 团队创作的分工
设计与创作类常见问题不是分工不清，而是**风格不统一**。有效做法：开工前定一份简短的「视觉/语气规范」（配色、字体、语气、参考图），所有人据此产出。

## 作品如何复用
- 整理成作品集条目：问题 → 你的角色 → 关键决策 → 结果（含评审意见或数据）；
- 保留过程材料（草图、废弃方案）：**面试里「为什么改」往往比最终稿更能说明能力**；
- 若要公开，注意赛事版权与主办方要求（部分比赛要求独家或限制公开）。

## 值不值得参加
- 需要作品集（设计、内容、游戏方向）→ 值得，且产出可复用；
- 已有足够作品 → 选择性参加高认可度的赛事；
- 只是想练手 → 先做个人项目，成本更低（见 [项目与作品手册](../docs/manuals/项目与作品手册.md)）。

## 怎么参加
从线上 jam 入门（如 Ludum Dare），线下活动（Global Game Jam）按官方渠道报名。第一次参加的目标设为「完成」——不做完比做得丑更可惜。控制范围：一个核心玩法循环打磨到能玩，远胜五个半成品系统。赛后把游戏发布到 itch.io 等平台并收集反馈，这就是作品集的一页。

## 一款可玩的小作品，代价是一个周末
游戏创作活动换到的是一款**能玩、能分享的小游戏**、快速做原型的经验，以及社区里的同伴。工具基本免费，引擎与美术素材库都有开源可用的选择。

代价是一个周末。它不适合两类人：指望作品直接商业化的，和无法接受粗糙成品的人。参前功课很简单——先看往届作品；结束后把成果整理成可展示的页面，这一点对设计与写作类比赛同样适用。

职业技能竞赛（技能大赛、行业赛事）的特点是与**行业认可直接对接**：部分赛项的获奖者可获得职业技能等级晋升，或被企业直接关注。

## 与其他竞赛的区别
| | 职业技能竞赛 | 学科/工程竞赛 |
| --- | --- | --- |
| 内容 | 按职业标准考核实操 | 解决开放性问题或完成作品 |
| 依据 | 技术文件与评分标准（接近考纲） | 命题要求与评审偏好 |
| 产出 | 等级晋升、企业关注、就业推荐 | 作品、论文、名次 |
| 训练方式 | 按标准逐项练到熟练 | 方法与创意训练 |

## 备赛怎么做
1. **拿到技术文件**：评分标准就是考纲，逐项对照训练，而不是泛泛练基本功；
2. **按分值分配时间**：高权重项优先练到稳定，低权重项保证不失分；
3. **练稳定性**：赛场上失分最多的是「平时会、现场做不出来」——按现场条件（时间、设备、工具）模拟；
4. **练流程规范**：安全操作、工位整理、工具使用规范常被计入评分。

## 获奖的实际用途
- **等级晋升**：部分赛项的获奖可按政策晋升职业技能等级（**以当地人社部门规定为准**）；
- **就业推荐**：合作企业直接关注，部分赛项有推荐就业通道；
- **升学**：部分院校在专升本、评优中有认定（**以本校规定为准**）。

## 最适合谁
- 走技能路线与职业本科方向的学生（优先级最高）；
- 已有明确工种方向且愿意按标准练到熟练；
- 所在学校有相应实训条件与指导老师。

## 什么情况优先级较低
- 走学术升学路线，且赛项与方向无关；
- 实训条件不足（训练效率低，容易白投入）；
- 时间与关键节点（升学、实习）冲突。

## 参赛前查两件事
- **认可度**：目标行业与目标地区对这个赛事怎么看？人社部门体系内的赛事认可度较高；商业机构办的「国际大赛」要按 [付费拿奖的识别方法](03-做项目、打比赛、进实验室.md#competition-what-worth-joining) 核查；
- **通道**：获奖后能兑换什么——证书、等级晋升、企业 offer，查官方文件，别信口头承诺。

## 备赛的正确姿势
按竞赛的技术文件（评分标准）逐项训练，而不是泛泛练基本功。评分标准就是考纲，训练对齐标准才有效率。

## 技能路线与职业本科方向优先级最高
技能路线与职业本科方向的学生优先级最高；走学术升学路线的，除非方向相关，否则优先级不高。技能路线的整体走法见 [学徒制与技能路线](01-先决定下一步往哪里走.md#apprenticeship)。

## 科研初体验

### 科研到底是什么

```meta
id: research-what-is-research
status: complete
stages: [college, undergraduate]

effort: medium
evidence: [research_backed, experience_based]
summary: 科研的本质是产出新的、可检验的知识：先问出一个没被回答的问题，再用别人能重复的方法回答它，并用四要素自检一段经历算不算科研。
last_verified: 2026-10-06
```

科研的本质是**产出新的、可检验的知识**：先问出一个还没被回答的问题，再用别人能重复的方法回答它。它与「看论文」「在实验室待着」「帮老师干活」都不是一回事——没有问题、方法与可检验结论的，不构成研究经历。

## 从一个具体问题开始，而不是一个领域
选一个你有真实好奇的**具体问题**，而不是「一个领域」；读该问题下最常被引用的五到十篇论文，弄清已知什么、缺口在哪；进一个真实在做研究的组（见 [怎么找到第一次科研机会](03-做项目、打比赛、进实验室.md#research-undergrad-start)），从小任务做起；把自己的工作对着「问题—方法—证据—结论」四要素检查，缺哪个补哪个。

## 方法与推荐信，代价是漫长的失败期
研究训练带来的是**一段真实的研究经历**、可能的论文、导师与同行的推荐信，以及一套「提出问题—设计方案—验证—表达」的方法。这套方法在离开学术之后同样有用。

代价是以月计的持续投入。大部分时间花在重复、失败与改错上，而且**成果带有随机性**：同样的投入，可能没有产出。能不能接受这一点，是判断自己适不适合长期做研究的第一个关口。

## 一段经历算不算研究经历
用四个要素自检，缺一个就不是完整的科研经历：

| 要素 | 不合格的样子 | 合格的样子 |
| --- | --- | --- |
| 问题 | 「研究了人工智能」 | 「在 X 数据集上，Y 方法在 Z 条件下是否仍然有效」 |
| 方法 | 跟着师兄做，说不清为什么这么做 | 能说明为什么选这个方法、有哪些备选、怎么验证 |
| 证据 | 跑了一次，结果不错 | 有对照与重复，能说明波动有多大 |
| 结论 | 「效果很好」 | 「在什么条件下有效、在多大规模下开始失效」 |

**把打杂、读文献当产出**是最常见的问题：读了一百篇文献不等于有了问题，帮老师跑数据不等于做了研究。判断自己适不适合，见 [哪些人值得接触科研](03-做项目、打比赛、进实验室.md#research-who-suits)。

## 什么时候这段经历不该写成科研经历
如果你做的工作里没有「问题—方法—证据—结论」中的任何一环，它就是一段工作或实习经历，不是科研经历。如实写成实习或项目不会减分；硬包装成科研，面试追问两层就会露底。

适合做科研的人通常有三个特征：**对具体问题的耐心大于对短期回报的需要**、**能承受高比例的失败**、**愿意把一件事讲到任何人都能懂**。成绩好不是充分条件——成绩衡量的是掌握已知，科研面对的是未知。

## 用真实经历测试，而不是想象
用一段完整的研究经历（一学期到一年）做测试，不用想象或测评。测试中观察自己：卡住三天还能接受吗？重跑第十次实验还有耐心吗？写第一稿痛苦吗？记录「喜欢做什么」和「擅长做什么」的重合部分。无论结论如何，把经历整理成材料——它对任何路径都有用。

## 两个方向的误判
把不适感误判为不适合——多数不适应在两三个月后消失；也把长期痛苦硬扛成坚持。主要动机是「学历好看」或「家里希望」、对重复劳动与延迟满足明显不适、只想做应用落地（工程与产品岗位可能更合适）的人，慎选这条路。

## 它换回的最值钱的东西
一次低成本验证「我适不适合走研究这条路」的判断——这个判断本身就是最值钱的产出，直接决定读研读博的真实意愿。

科研不是只有“发论文”一种形态。对本科生来说，第一段科研经历更重要的产出是：**知道研究是怎么做的**、**知道自己在其中能不能待得住**，以及**得到一封了解你的推荐信**。论文是可能的副产品，不是入门条件。

## 不同学科的入口不一样
- 理工科：进课题组，从复现一篇论文或搭一套实验装置开始。
- 生命科学与医学：协助实验、整理样本与数据、学习规范操作。
- 人文社科：整理文献地图、编码访谈材料、核对档案与数据。
- 设计与艺术：做调研、跟项目、把过程整理成可展示的作品。

共同点是：都在做一件可以被检验的小事。

## 第一次任务应该足够小
不需要先达到“能独立完成研究”的程度。合适的起点是：在导师或高年级成员指导下完成一个可验证的小任务——复现代码、整理文献、协助实验、清理数据、访谈编码、档案整理、田野记录。小任务做完，才有资格谈更大的问题。

## 合适的时点
通常出现在三件事之后：基础课不再拖后腿、你能在指导下完成上面那样的小任务、每周能拿出固定的连续时间。顺序反了，容易变成在实验室里刷存在感。

## 怎么找老师
先读 5 篇该方向的论文（含 1 篇综述），能用自己的话讲出这个方向在解决什么问题；再带着一个具体的产出（复现结果、文献整理、数据梳理）去联系老师。邮件写法见 [联系导师邮件模板](../docs/tools/联系导师邮件模板.md)。

进组前问清五件事：每周投入要求、谁带你、是否参与具体课题、产出预期、署名规则。

## 进组以后先做什么
第一个月把小事做完并交付，让人知道你可靠，再谈更大的任务。同时把每次讨论、每个实验记录留档——这既是科研习惯，也是将来写材料时的依据。

## 怎么判断自己真的积累到了科研经验
三个自检问题：能不能讲清这个课题在解决什么问题？能不能复述自己做过的具体工作与结论？有没有人（导师或合作者）愿意为你写具体的推荐信？

## 如果发现不喜欢科研
尽早知道也是收获。科研训练里可迁移的部分——提问题、查文献、验证结论、把过程写清楚——在任何行业都用得上。

### 怎么找导师

```meta
id: research-find-supervisor
status: complete
stages: [undergraduate, master, phd]

outputs: [research_experience, recommendation]
effort: medium
evidence: [official, experience_based]
summary: 怎么找导师：先判断这个方向的实验室还在不在做、组里谁真正决定你能否进组，再决定联系谁、问什么。
last_verified: 2026-09-27
```

找导师不是「挑一位厉害的老师」，而是**判断一个课题组现在在做什么、你能不能在里面做事**。判断依据分布在三个层次上，越往下越可靠。

## 第一层：公开信息（能看出方向与产出，但常常过时）
- **导师主页**：多数主页更新频率很低，写的是五年前的方向。**别把主页当结论**；
- **近三年论文**：看三件事——还在不在做这个方向、一作是谁（学生一作多说明新人有机会）、产出节奏是否稳定（连续两年空白要留意）；
- **实验室 / 课题组页面**：成员名单、设备条件、项目介绍。注意与导师本人方向的差异：有的组主业是 A 方向，导师个人近年转做 B，新人进去做的可能是 A；
- **经费线索**：论文致谢里的基金号、项目页面上的在研项目，能判断有没有钱支持新人。

## 第二层：组里的人（决定你实际体验的信息）
只有问组里的人才知道的部分：

- 导师多久和学生单独讨论一次、给不给具体反馈；
- 组会是汇报还是讨论，新人有没有发言机会；
- 一个学生通常同时做几个课题、谁定题；
- 实验室的设备与数据是否够用，有没有排队；
- 毕业要求是什么、近三届学生几年毕业；
- 学生之间是否合作、有没有明显的竞争氛围。

**问法很重要**：不要问「这个老师怎么样」（对方不会说坏话），而是问具体事实——「你们组会多久一次？」「上次和老师单独讨论是什么时候？」「师兄毕业用了几年？」具体问题能得到具体答案。

## 第三层：制度（最常被忽略，却常常是决定性的）
**真正决定你能不能进组的，往往不是导师一个人**：

- **招生名额在谁手上**：有些院系名额由学院统一分配，导师只是「有意向」；
- **是否有资格限制**：推免、考研笔试、院系考核，任一环节不过，导师同意也没用；
- **经费与岗位**：RA/TA 岗位由经费决定，导师没有经费时可能无法提供资助；
- **委员会制 vs 导师制**：委员会制项目里导师的意见权重有限，申请材料与推荐信才是关键（见 [联系导师与套磁](../docs/research/联系导师与套磁.md)）。

**判断方法**：打开院系招生页面，看录取流程写的是「导师接收后报院系」还是「统一材料评审」。这一步花十分钟，能避免几周的无效沟通。

## 怎么判断实验室是否还在做这个方向
三条交叉验证：

1. 近三年的论文里，这个方向的工作是否还在出现；
2. 组里在读学生的课题是否与之相关（看学生主页、组会记录）；
3. 组里是否有对应的项目、设备或数据（没有条件的方向做不下去）。

三条只有一条成立，就要直接问：「老师，您组里现在还在做 X 方向吗？如果我想做这方面，大概会跟谁合作？」

## 联系之前要准备好的东西
- **一页简历**：教育背景、研究经历（写清你做了什么）、技能、联系方式；
- **能看的产出**：代码仓库、复现报告、论文、技术报告；
- **一段具体的研究兴趣**：不是「我对机器学习感兴趣」，而是「我在做 X 时发现 Y 现象，想搞清楚它为什么不成立」。

## 什么信号说明该换一个目标
- 发信三轮无人回复（且对方主页明确在招）；
- 组里学生普遍回避评价导师的指导方式（这是负面信号）；
- 谈过之后发现「方向」和你想做的不是一回事，且对方不打算调整；
- 资助与名额都没法落实，只给「欢迎报考」这类模糊答复。

## 两周的调查流程
1. 列出候选导师，逐一查近三年论文（第一作者与通讯作者是谁、方向与你是否匹配）与主页招生说明；
2. **至少联系两位在读或刚毕业的组员**，问四件事：日常怎么指导、组会怎么开、多久见一次、师兄师姐去了哪；
3. 邮件联系参考 [联系导师邮件模板](../docs/tools/联系导师邮件模板.md)，同一院系一次只联系一位；
4. 面谈问清：入学第一年做什么、课题是给定的还是自选、经费能否支撑实验；
5. 汇总信息再决策，警惕只有官网信息、没有学生视角的选择。

## 得到的是几年里的工作方式与心情
选对方向换到的是一段**能真正学到东西的关系**、稳定的指导，以及可能的推荐信。这件事决定你未来几年每天的状态。

代价是两到四周的调查、联系与面谈时间。这一步最常被跳过，代价却在后面兑现——具体怎么判断，见 [选导师](04-升学、就业还是出国.md#study-choose-supervisor)。

判断一个实验室看四件事：有没有明确的研究问题、有没有人带你、有没有近年的产出先例、以及你能不能拿到可验证的署名或成果。四项里缺两项以上，慎入。

## 怎么核实
查课题组近三年的公开产出：论文、会议、项目、学生去向——没有可查产出的组，要问清原因；找两三位在读或已毕业成员私下了解：每周投入、组会频率、导师是否给方向、毕业与署名情况（学生对课题组的评价是二手信息，要交叉验证）。明确你的目标——推荐信、学方法、发论文还是试水——并当面说清，目标不同投入方式应该不同。

## 进组后的两件事
确认署名规则与数据归属，建议留下邮件记录；设三个月检查点——没有指导、没有产出、也没有方法学习时，**换组不是失败，是止损**。别把课题组氛围问题当成自己能力不足，也别一次换组失败就认定「我不适合科研」。

## 训练、署名与推荐信，代价是六个月到两年
投入一段长期研究，换到的是方法训练、署名或成果、推荐信（取决于你实际做了什么），以及学术圈里才有的信息与人脉。

代价是六到二十四个月、可能的大量重复劳动，以及与导师期望不匹配时需要付出的沟通与换组成本。**如果你只想拿一封推荐信、不打算投入时间**，更合适的做法是先把预期讲清，找一个短期、边界明确的任务，而不是占住一个长期研究席位。

### 怎么判断自己是否喜欢科研

```meta
id: research-do-i-like-it
status: complete
stages: [undergraduate, master, phd]

summary: 怎么判断自己是否喜欢科研：用四个可观察信号而不是感觉，以及半年后仍然不确定时该怎么做。
last_verified: 2026-09-27
```

「我喜不喜欢科研」很难靠想象回答，因为科研的日常与你看到的成果差别很大。可靠的做法是**用一段真实经历里的可观察信号来判断**。

## 四个可观察信号
| 信号 | 说明 | 反过来是什么样 |
| --- | --- | --- |
| 能忍受「没有结论」 | 一周过去只有失败与排除 | 每天需要即时反馈才安心 |
| 对现象本身好奇 | 想知道「为什么会这样」而不只是「能不能过」 | 只关心指标和 deadline |
| 愿意反复验证 | 会主动补对照、换数据确认 | 结果不好就想换题目 |
| 有稳定节奏 | 能按计划读、做、写 | 靠灵感与情绪推进 |

四个里前两个最重要：它们决定你能否在长时间不确定中坚持。

## 用经历验证，而不是用感觉
具体做法（一到两个学期）：

1. 完成一件**完整的小研究**（复现、小实验、小分析都算），从问题到结论走完一遍；
2. 记录每周实际花在「读/做/写」上的比例与你当时的感受（两周一次写三行）；
3. 三个月后回看：你更想深入哪一个问题？还是只想让它结束？
4. 找三位博士在读或刚毕业的人各聊一次，问他们「哪一部分最耗人、哪一部分最值得」。

## 半年之后仍然不确定，怎么办
三种可能，处理方式不同：

- **不喜欢具体课题**：换方向或换组，先别否定科研本身（见 [怎么找导师](03-做项目、打比赛、进实验室.md#research-find-supervisor)）；
- **不喜欢这个组的氛围**：换组，观察是否变化；
- **确实不喜欢研究本身**：把科研训练当能力训练（问题定义、验证、写作），转到研究相关的岗位（研究型产品的工程、数据、策略岗），这很常见。

## 几个常见误判
- **把「学得好」当成「适合做研究」**：课程考得好与能做研究是两种能力；
- **把「导师很厉害」当成「我喜欢这个方向」**：跟的是名头还是问题，差别很大；
- **把「做不出来」当成「不喜欢」**：技能不足会伪装成兴趣不足，先补方法与指导；
- **把「不喜欢写论文」当成「不喜欢研究」**：写作是科研的一部分，但可以通过训练改善。

## 什么时候应该停止
- 完整走过一次研究流程后，仍然对问题本身没有好奇；
- 长期情绪与健康受损（睡眠、焦虑）且无法通过换组或调整节奏改善；
- 你更享受「把事情做成」而不是「把问题弄清」——那就去做产品与工程，不必勉强。

## 三个诚实的自测
- 进组半年后，没人安排任务的那一周，你会主动琢磨课题里的问题吗？
- 一个实验连续失败两周，你的第一反应是兴奋还是想逃？
- 读文献碰到看不懂的方法，你是绕过去，还是停下来弄懂？

## 日常的真实样子
科研的大部分时间在重复、失败和改稿里，高光（结果出来的那一刻）占比很小。能忍受这个比例的人，才适合长期做。

## 怎么低成本试
进实验室做一段真实的工作，见 [怎么找到第一次科研机会](03-做项目、打比赛、进实验室.md#research-undergrad-start)。一个暑期的真实体验，胜过一年的想象。不喜欢也不算失败——早点排除同样是这段经历的重要产出。

### 什么是开源贡献

```meta

effort: medium

summary: 什么是开源贡献：贡献的四种形式、为什么它比简历上的描述更可信，以及参与前的必要准备。
last_verified: 2026-09-27
```

开源贡献不只是「写代码」：任何让项目更好的公开工作都算贡献，而且**它的记录是公开可查的**——这正是它在求职与申请中可信度高的原因。

## 四种贡献形式
| 形式 | 例子 | 门槛 |
| --- | --- | --- |
| 文档 | 修正错误、补示例、写使用指南 | 最低，适合入门 |
| 问题与复现 | 提交清晰的 issue 与最小复现 | 低，但需要表达能力 |
| 代码 | 修 bug、补测试、实现小功能 | 中，需要读代码与遵循规范 |
| 维护与治理 | 评审 PR、参与讨论、发布版本 | 高，靠长期参与 |

**多数人的路径是「文档/issue → 小代码改动 → 持续参与」**，而不是一开始就做架构级改动。

## 为什么它比自我描述更可信
- 提交记录有链接、有评审意见、有时间线，无法伪造；
- 评审意见能反映你的沟通与接受反馈的方式；
- 面试官可以直接点开看，**追问三层的成本很低**。

## 参与前的准备
1. **先成为用户**：用这个项目解决过你自己的问题，才知道哪里不好用；
2. **读贡献指南**：`CONTRIBUTING.md`、issue 模板、代码规范——不按格式提交的 PR 常被直接关闭；
3. **确认许可证**：不同许可证对再分发与商用有不同要求（见 [开源手册](../docs/manuals/开源手册.md)）；
4. **注意劳动关系**：用公司设备与工作时间提交前，先确认合同与公司政策。

## 常见误区
- 「开源就是免费帮我干活」——它是公开协作，维护者有权拒绝不符合范围的改动；
- 「必须先很厉害才能参与」——文档与复现问题的价值常常更高；
- 「提交越多越好」——十个错别字 PR 不如一个有测试、说清动机的改动。

## 为什么它有信号价值
开源贡献可以被第三方直接核实：合并记录公开、代码质量可见、协作过程可查。这使它成为比自我描述可信得多的能力证明，见 [什么叫可验证成果](00-从这里开始.md#judge-verifiable-outcomes)。

## 从你在用的项目里找一个小问题
选一个你**自己真的在用**的项目，先读它的 CONTRIBUTING，从最小的改动做起。完整步骤见 [第一次贡献怎么开始](03-做项目、打比赛、进实验室.md#opensource-first-contribution)。

不要随便找一个标着「新手友好」的大项目乱改。正确顺序是：**先用起来，遇到一个具体问题，再按它的贡献指南修掉。** 先成为用户，再成为贡献者。

## 七步走

1. 选一个你**已经在用**的项目（工具、库、框架），能本地跑起来；
2. 读它的 CONTRIBUTING.md 与 Issue 标签说明——不少项目要求先开 Issue 讨论再提 PR，跳过会被直接关闭；
3. 从最小的事开始：文档错字、示例跑不通、错误信息不清、补测试。文档类贡献同样计入贡献记录；
4. 遇到 bug 先复现，写出最小复现步骤——这份描述本身就是有价值的工作；
5. 做最小改动：一个 PR 解决一件事，不夹带重构，写清改了什么、为什么、怎么验证；
6. 响应评审：CI 失败先修，评审意见照做或说明理由——被要求改动是正常流程，不代表你能力不行；
7. 第一次被合并后再认领更复杂的问题。在一个项目里持续贡献，价值远大于到处撒网。

## 第一次适合做什么

| 类型 | 难度 | 为什么适合入门 |
| --- | --- | --- |
| 文档修正与补充 | 低 | 影响清晰、评审快 |
| 示例代码修复 | 低 | 能验证、价值直观 |
| 补测试（边界 / 异常） | 中 | 维护者通常欢迎 |
| 小 bug 修复 | 中 | 需要读懂代码结构 |

不建议第一次就做大功能：涉及设计讨论，周期长，也容易被判定为超出项目范围。

## PR 被打回或关闭怎么办

常见原因：超出项目范围、与既有设计冲突、缺少测试、已有重复 PR。正确的反应是问一句「如果我要做这件事，应该怎么改」，把反馈用在下一个改动上；不要反复提交同一改动、在评论里争论，或换账号重提。

## 常见误区

修改前先大范围格式化（造成大量无关改动）；一次提交多个不相关的改动；不看 CI 结果就请求评审；忽略许可证与 CLA（贡献者许可协议）要求。

## 公开可见的贡献与工程流程经验，代价是前期投入

参与开源换到的是**一份公开可见的贡献记录**、与维护者的实际联系，以及对工程流程（Issue、分支、CI、Review、发布）的真实理解；少数情况下还会直接带来工作机会。

代价是前期读代码的时间通常多于写代码，以及英文沟通、被拒绝或被要求重改的心理成本。**PR 挂几周是常态，不是异常**——把这一点想清楚，才不会被沉默劝退。

Issue 与 PR 是开源协作的两个基本动作：**Issue 提出问题，PR 提出改动**。两者的写法都有公认标准，写得清楚比写得多重要。

## Issue 怎么写
一个可用的 issue 包含四部分：

```
环境：版本、系统、依赖（能复现的前提）
操作步骤：我做了什么（最小步骤）
预期与实际：我以为会 A，结果是 B
补充：日志、截图、最小复现仓库（可选但很有用）
```

**「最小复现」是关键**：能让人在三分钟内复现问题，你的 issue 就会得到响应；只说「用不了」通常无人理会。

## 为什么它们是可信证据
- 公开可查、有时间线、有他人评审意见；
- 能体现沟通与接受反馈的方式（这在团队协作里很重要）；
- 可以被面试官直接点开追问。

**注意**：不要为了数量提交低质量问题（例如只改错别字的批量 PR），这反而会留下负面印象。

## 评审为什么常常先说「不在范围内」
- 把 issue 当聊天（「有人吗」）——用模板把信息写全；
- 在 PR 里夹带无关改动；
- 忽视 CI 失败就请求评审；
- 提交前不读贡献指南。

## PR 怎么写
提之前先搜已有 Issue（重复提问最招人烦）；标题概括问题；正文给版本、环境、复现步骤。「我发现了 bug」但没有复现步骤，等于没提。

## PR 怎么提
先读项目的 CONTRIBUTING.md 与最近合并的 PR，对齐风格与范围；保持小——一次只改一件事，改动理由写在描述里并关联对应 Issue；收到 review 意见逐条回应，修改后在原 PR 上触发评审，不要另开新 PR。

PR（Pull Request）是你向一个代码仓库**提出修改请求**的方式：你改动一份副本，请维护者把它合并进主分支。

## 它什么时候有价值
对开源项目来说，PR 是最容易被第三方验证的贡献——合并记录公开、改动内容可见、评审过程可查。这使它比「我参与过某项目」这种自述可信得多，也是简历上少数能附上链接证据的经历，见 [什么叫可验证成果](00-从这里开始.md#judge-verifiable-outcomes)。

## 第一次 PR 怎么做
1. 先读项目的 CONTRIBUTING：不少项目要求先开 Issue 讨论再提 PR，跳过会被直接关闭；
2. 从小改动开始：文档错字、示例跑不通、错误信息不清楚、测试覆盖；
3. 一个 PR 只做一件事，描述里写清改了什么、为什么改、怎么验证；
4. 收到评审意见逐条回应，在原 PR 上补充提交，不要另开新 PR；
5. 被要求修改是正常流程，不代表你能力不行；PR 挂几周也是常态。

## 最容易踩的坑
一上来改核心代码然后被关掉；一个 PR 混入多个不相关改动；把机器翻译的文档或纯格式调整当主要贡献；提交后失联；用「提了多少 PR」当资本而不看合并率。更深入的写法见 [Issue 与 PR 的写法](03-做项目、打比赛、进实验室.md#project-issue-pr)。

文档不是给别人看的负担，而是**判断你自己是否想清楚的标准**：写不出「它解决什么问题」，通常意味着还没想清楚。

## 四类文档与用途
| 类型 | 给谁看 | 最少要写什么 |
| --- | --- | --- |
| README | 所有访客 | 解决什么问题、怎么运行、已知限制 |
| 使用文档 | 用户 | 安装、配置、常见操作、错误处理 |
| 设计/决策记录 | 未来的你与合作者 | 为什么这样做、放弃了什么 |
| 变更记录 | 使用者 | 每个版本改了什么、是否破坏兼容 |

**个人项目的最低要求是 README**；有真实用户后补使用文档；有协作后补决策记录。

## README 的最小结构
```
一句话说明它解决什么问题、给谁用
如何运行（能照做的步骤，含依赖版本）
一个使用示例（输入 → 输出）
已知限制（哪些情况不支持）
目录结构（可选）
许可证（开源时）
```

**检验方法**：找个没参与项目的人按 README 跑一遍，看他能否成功。这是最便宜的验收方式。

## 常见问题
| 问题 | 表现 | 改法 |
| --- | --- | --- |
| 只有功能清单 | 看不出价值 | 先写问题与场景 |
| 假设读者有环境 | 别人跑不起来 | 写清依赖与版本 |
| 截图没有说明 | 不知道在看什么 | 图配一句话 |
| 从不更新 | 与代码不一致 | 改功能时同步改文档 |
| 写给自己看 | 术语与缩写过多 | 换位成新人视角 |

## 「写不出来」意味着什么
- 不知道解决什么问题 → 项目定位不清；
- 说不清怎么运行 → 环境依赖混乱，别人无法复现；
- 列不出限制 → 还没测试过边界。

**所以写文档是检验项目质量的动作，不只是交付物**，见 [数据、测试和指标](03-做项目、打比赛、进实验室.md#project-data-test-metrics)。

## 什么改动都有价值
修正错字、失效链接与过时的版本号；补一个能跑通的安装示例（「照着文档装不起来」是新手流失的第一大原因）；把一段含糊的说明改写清楚；补上你当初缺失的那条信息。

## 为什么值得做
- 流程完整：提 Issue、改、提 PR、过评审——一次走通就学会了开源协作的全套动作；
- 维护者对文档 PR 的合并意愿通常很高，适合建立信心；
- 文档改动的评审记录同样是公开可见的贡献记录（见 [PR](03-做项目、打比赛、进实验室.md#opensource-pr)）。

## 文档改动最容易做错的地方
把文档改动做得太大（大段重写很难评审）；只改格式不改实质内容；机器翻译导致语义偏差；不看项目的文档风格与术语约定就动手。

Review（代码评审）是协作开发的质检环节：别人提交改动，你读并提出意见；反过来你的代码也会被评审。

## 作为评审者
从你**看得懂的**部分开始：文档是否有歧义、测试覆盖了改动吗、有没有更简单的写法。评审意见要对事不对人——「这里在并发时可能重复扣款」比「写得不严谨」有用得多。附带一句「这块改得很好」也是正常的，评审不只有挑错。

## 被评审时
把每条意见当成免费教学：维护者指出的问题，往往是你半年后才会自己踩到的坑。回复要具体——「已按建议改为 X」比「好的」有用。不认同可以讨论，用代码和场景说话。

## 为什么值得参与
评审是最快的成长途径之一：你能看到成熟项目怎么权衡、怎么防御性地写代码，这些在教程里学不到。持续的评审参与也是进入 Reviewer、Maintainer 角色的台阶，见 [Maintainer](03-做项目、打比赛、进实验室.md#project-maintainer)。

## 评审与回应里最容易出问题的地方
把评审当比赛（挑得越多越厉害）；只挑风格不谈设计；意见含糊让对方猜；被评审时把意见当成人身评价。


Maintainer（维护者）是**对项目方向与质量负责的人**：决定接受什么改动、什么时候发布版本、如何处理冲突。它与「贡献者」的差别不是写多少代码，而是承担责任。

## 维护者的实际工作
- 评审 PR、回答 issue、判断需求是否在范围内；
- 发布版本、维护变更记录、处理破坏性改动；
- 维护者之间协调（路线、权限、行为准则）；
- 处理安全与依赖更新。

**现实中的工作量主要不在写代码**，而在沟通与取舍。

## 成为维护者的常见路径
1. 长期参与同一项目（几个月以上），代码与文档都有贡献；
2. 主动承担评审与答疑（维护者最缺这类人）；
3. 与现有维护者建立信任，被邀请成为协作者；
4. 或者：自己发起一个项目，长期维护（这是另一条路，更容易开始也更难坚持）。

## 常见困境
| 困境 | 表现 | 应对 |
| --- | --- | --- |
| 需求堆积 | issue 永远处理不完 | 明确「不打算做」清单并写进 README |
| 精力不足 | 变成负担、不想看通知 | 降低承诺（只做安全修复）、招募共同维护者 |
| 冲突 | 与贡献者就设计争执 | 写清决策原则，必要时用路线图说明取舍 |
| 被当免费劳动力 | 使用者提要求甚至指责 | 写清支持范围与响应预期 |

## 什么时候该归档
- 你不再有时间或兴趣维护；
- 项目已被更好的替代品覆盖；
- 维护成本远超收益（法律、安全、社区冲突）。

**归档是负责的做法**：在 README 顶部写清「已停止维护」，标记仓库为 archived，并推荐替代方案。放着不管比归档更糟。

## 它对履历的作用
公开、长期、可查的维护记录能证明：技术判断、协作方式、长期投入与沟通能力。**这比一次性提交更有说服力**，也是面试中容易展开的话题。

## 怎么走到这一步
先在自己的项目上练习全套治理：发布版本、写变更日志、处理外部 PR；在参与的项目里主动承担可见的维护工作（审 PR、修文档、管 Issue 列表）；被邀请或主动申请时，先明确能投入的时间与权限范围。建立可持续机制：贡献指南、行为准则、明确的技术决策流程——一个人扛所有事不可持续。

## 治理经验与声誉，代价是长期义务
做维护者换到的是**真实的治理经验**——评审、发布、社区管理，这些在正式工作里很稀缺；此外还有社区声誉，以及用人单位看得见的领导力证明。

代价是每周固定的维护时间、处理分歧的情绪成本，以及一项长期义务。**学会归档也是一种能力**：项目不再维护时明确标注、留好交接说明，比放着不管体面得多。

### 社团有没有价值

```meta
id: community-club-value

effort: low
evidence: [experience_based]
summary: 社团有没有价值：三种可积累的产出、怎么选社团与承担角色，以及什么情况下应该退出。
last_verified: 2026-09-27
```

社团的价值取决于**你在里面做了什么**，而不是参加了几个。用「有没有留下可说的东西」来判断，比问「社团有没有用」更有效。

## 三种可积累的产出
| 产出 | 例子 | 能证明什么 |
| --- | --- | --- |
| 组织经验 | 策划活动、带小组、拉赞助、做流程 | 协调与交付能力 |
| 作品与内容 | 海报、视频、公众号、活动手册 | 创作与表达能力 |
| 关系网络 | 同届骨干、往届学长、外部合作方 | 长期可用的关系 |

**参加一年但没有上述任何一项**，说明你只是在消耗时间。

## 怎么选社团
- 看**每年实际产出什么**（活动规模、作品、对外影响），而不是看招新宣传；
- 看**骨干的在职时长**（全是新人说明流失严重）；
- 看**你能否在里面获得想要的技能**（组织、内容、技术、外联）；
- 看**时间成本**（会议频率、活动强度）。

## 承担角色的顺序
```
社员（参与活动）→ 负责一个环节（做具体事）→ 带小组（管人做事）→ 骨干/负责人（定方向、担责任）
```

**建议至少做到第三步**：负责过一个完整环节，才有可讲的经验。只做社员一年，很难写出具体内容。

## 常见误区
- **为了「简历好看」挂名**：面试一问具体做了什么就露；
- **把社交当产出**：认识了一大群人却不产出（见 [Networking](06-从新人到能独立负责.md#community-networking)）；
- **陷入事务性忙碌**：每周开会但没有一件事真正落地；
- **只在一个社团待到底**：同类经验重复，边际收益递减。

## 什么时候应该退出
- 你负责的事已经不再产生新经验（重复劳动）；
- 组织内耗严重（人际冲突、流程混乱），消耗大于收益；
- 与课程、实习、健康明显冲突；
- 你已经拿到了想要的三类产出。

**退出方式可以体面**：提前交接、推荐接替者、留下一份文档。这样留下的是正面印象。

## 怎么判断值不值得继续
一学期后问自己三个问题：我在里面负责过一件完整的事吗？产出能展示吗（活动、作品、制度）？我认识的人在我需要信息时会认真帮我吗？如果多数答案是否定的，就该考虑换一个。

## 哪类投入产出比高
与目标方向相关的技术类、行业类社团——产出直接对齐简历；需要真做事的岗位（组织、技术、内容），而不是只挂名的会员。

## 退出的成本被高估了
「都加入了就坚持吧」不是理由。时间是大一、大二最充裕也最容易被浪费的资产，把它移到更有产出的地方更划算，见 [学业、实践和生活怎么平衡](02-在学校里先把基础打好.md#study-life-balance)。

### 专业协会

专业协会（学会、行业协会）的价值集中在一件事上：**你参与的程度**。它不是「加了就有效」的组织——会员身份本身不带资源，资源来自你参与会议、分会与志愿工作的程度。

## 三样实际价值

- **信息**：行业标准、年会与期刊、政策解读，比二手转述更接近源头；
- **身份**：会员身份在某些场景是资格前提（部分会议投稿、部分认证、部分评审）；
- **网络**：会议与分会活动是认识同行的正式场合。

## 学生身份的特殊之处

学生会员通常有折扣甚至免费（以各协会官方规定为准），这让早期加入的成本很低。学生身份还能用到的通道包括：学生分会（Student Chapter，见 [Student Chapter](03-做项目、打比赛、进实验室.md#community-student-chapter)）、会议学生票与差旅资助（见 [Travel Grant](04-升学、就业还是出国.md#funding-travel-and-conference-grant)），以及行业报告、职位板与政策动向——后几项是重要的信息差来源。

## 怎么参与才有用

- 先看年会与分会：选与你方向最接近的分会，而不是泛泛加入；
- 投稿或做志愿者：志愿者通常能减免注册费，也能接触组织方；
- 听会并提问：一次会议听三场最相关的报告，问一个具体问题；
- 持续出现：连续参加两三次，才可能被记住。

## 常见误会

- 「加入就有资源」：不会，资源来自参与；
- 「学生身份没用」：部分会议与活动对学生有明显优惠与专门通道；
- 「会员证能当资格证」：多数协会会员身份不等于执业资格，准入类资格以国家目录为准；
- 「协会能练能力」：协会提供的是接触面与信息，能力仍然要靠项目与实习积累。

## 什么时候不必加入

你的方向与协会范围不匹配；会费与活动成本超出可承受范围，而信息与人脉已经能通过免费渠道获得；你只是想要一个头衔——这在简历上也无法被追问出内容。

### Student Chapter

```meta

summary: Student Chapter 是什么：它能提供什么、怎么做才不变成挂名、可获得的产出，以及什么时候该退出。
last_verified: 2026-09-27
```

Student Chapter（学生分会）是专业协会或组织在高校里的分支。它的价值不在头衔，而在三样可积累的东西：**组织经验、行业联系、公开产出**。

## 三样实际产出
1. **组织经验**：策划活动、拉讲者、带团队、做预算与复盘；
2. **行业联系**：分会通常与协会总部、企业有联系，能接触到校外的从业者；
3. **公开产出**：活动记录、技术分享、年刊或资料库——这些能在简历与面试中给出具体内容。

**只挂名不做事，一年后什么都写不出来**，这是最常见的失败方式。

## 怎么做才有效
```
第一年：参与活动（了解流程与人员）
第二年：负责一个环节（活动策划或外联）
第三年：带一个小组或负责一整届活动
```

**至少做到「负责过一个完整环节」**，才有可讲的经验。做法上：把每次活动的目标、分工、时间线写成一页，结束后留一页复盘。

## 与普通社团的区别
- 有明确的领域方向与协会背景（活动更容易与行业对接）；
- 常有校外资源（讲者、企业赞助、竞赛与实习信息）；
- 对组织规范要求更高（预算、审批、品牌使用）。

## 什么时候该退出
- 你负责的事已经重复，不再产生新经验；
- 内部管理混乱（无人决策、经费不清），消耗大于收益；
- 与课程、实习、健康明显冲突。

退出时提前交接、推荐接替者、留下一份文档，**别让下一届从零开始**。

## 怎么做出名堂
选一个你真正在用的领域（专业协会、技术社区、行业社群）——为了头衔去陌生圈子是最常见的错误。从一件具体小事开始：帮一次活动、整理一份资料、写一篇活动记录。做完立刻记录成果：参与人数、反馈、产出链接，这些是后来写材料时最硬的依据。争取一个**有名字的角色**（某分会成员、内容负责人），而不是「帮忙的人」——有名字的角色才能写进材料。半年后评估：有没有获得联系、产出和机会，没有就换方向。

## 组织经验与行业联系，代价是每月固定投入
组织活动换到的是**可以写下来的组织与协调经验**（办了几场、服务多少人、拉到什么资源）、与讲者、导师、同行的长期联系、公开产出的机会，有时还有会议差旅减免或实习内推。

代价是每月固定的时间投入、与学业或工作的取舍，以及活动遇冷的挫败感。部分角色需要缴费或垫付，务必提前问清。另外两条底线：**挂名不做事的声誉损失比收益大**；不要以社群名义做商业宣传或泄露他人信息。

志愿服务的价值分两层：一层是**政策层面明确写出来的**（服务期、待遇、部分招录倾斜），另一层是行业层面是否认可这段经历——后者差异很大，教育、公共服务领域认可度高，部分商业岗位几乎不看。

## 决定前核对三件事
1. 查项目官方网站确认**当年**的招募公告、服务期限、待遇构成与报名条件。西部计划、三支一扶、支教团、普通志愿活动在待遇、时长与政策上完全不同，别混为一谈；
2. 把「能拿到什么政策倾斜」抄成清单，逐条核对资格与时限——很多政策要求「服务期满且考核合格」、并须在特定期限内使用；
3. 评估目标行业是否认可这段经历，以及家庭经济能否支撑服务期待遇（通常低于同等学历的市场薪资，地点往往偏远）。

## 服务期内怎么做
选岗位优先看有没有明确的工作内容与产出（带一个班、完成一个项目），而不是「协助处理日常事务」；主动整理成果——教学记录、项目文档、活动总结，这些是面试时最有说服力的材料。被动等待安排、最后简历上写不出任何具体东西，是最大的浪费。

## 服务期证明与政策通道，仅在被认可的方向上值钱
服务期证明与考核材料、独立开展项目的经验、基层处理真实问题的能力、符合条件时的定向招录或加分通道，以及一段能支撑「我为什么选了这个方向」的具体经历。

Meetup（线下技术/行业活动）的价值在于**面对面的十分钟**：信息密度高于线上，且更容易建立后续联系。

## 参加流程（从报名到跟进）
```
报名前：看主题与讲者是否与你的方向相关（不然只是凑热闹）
到场后：坐在中间偏前，准备好自我介绍（三句话：做什么、在哪、在关注什么）
听讲时：记两个问题（讲者通常留提问时间）
结束后：上前问一个具体问题，交换联系方式
尽快发一条简短消息（提到你们聊的内容）
```

**只做前两步是常见做法**，所以收获有限。

## 现场该做什么、不该做什么
**做**：问具体问题（「你们用什么指标判断效果」）；介绍自己的方向（让别人知道能找你聊什么）；给一点价值（转一条有用的信息、介绍两个人认识）。

**不做**：只发名片或加微信而不说话；在问答环节做自我推销；全程沉默等结束。

## 适合你的活动类型
- **主题与你方向一致**：收获最大；
- **小而精的活动**（十几到几十人）：交流机会多；
- **有实操环节的工作坊**：能产出具体东西。

**避开**：纯营销宣讲会（内容全在卖课）、规模过大且无交流时间的活动。

## 什么时候不值得继续
- 连续三次活动内容重复、没有新信息；
- 现场以推销为主，参与者目的不匹配；
- 交通与时间成本远超收获。

**退出不需要理由**：活动是工具，不是身份。

## 怎么参加才有收获
- 选主题对口的场次，看讲者名单而不是活动标题；
- 到场前准备一个具体问题（「你们新人前半年主要做什么」比「这个行业前景如何」更容易得到认真回答）；
- 茶歇时直接找演讲者提问——刚讲完自己擅长的内容，是他们最愿意交流的时刻；
- 目标定为认识两三个人并交换联系方式，而不是「多认识人」；
- 会后 24 小时内发一条具体跟进消息（提到你们聊的内容）。这一步是把「见过」变成「认识」的关键。

## 成本与边界
成本主要是一个晚上的时间与交通；多数 Meetup 免费或低价（收费的要确认主办方与用途）。注意边界：不要在活动上只发广告或不参与讨论——那会留下负面印象。

## 从参与者走向自己讲一次
持续出现几次之后，可以考虑自己分享一次，这是从参与者走向 [Speaker](06-从新人到能独立负责.md#community-speaker) 的自然路径。

### 怎么从“参加”变成真正的贡献

社群里的「参加」和「贡献」差别很大：前者消耗活动，后者产生别人能用的东西。区别在于**你的输出是否被别人使用**。

## 贡献的三层
| 层级 | 表现 | 别人如何使用 |
| --- | --- | --- |
| 参与 | 出席、签到、在群里发言 | 不影响他人 |
| 交付 | 写纪要、整理资料、答疑、维护名单 | 被其他人用上 |
| 组织 | 策划活动、带小组、定规则 | 形成可重复的机制 |

**升级的关键动作**：把「我参加了」变成「我做了一件别人能用的事」。哪怕只是把每次活动的要点整理成一份可检索的文档。

## 从最小任务入手
```
第一次：参加三次同一类型的活动（先熟悉人和流程）
第二次：认领一件小事（签到、拍照、写纪要、整理资料）
第三次：做一次 10 分钟分享（讲清一个具体问题）
第四次：负责一个环节（拉一个讲者、组织一次小活动）
之后：带一个小组或做长期输出（专栏、年刊、资料库）
```

每一步都有可交付的东西，也就都有可写的记录。**跳过前两步直接要「核心角色」，通常拿不到。**

## 避免成为旁观者
- **带着问题去**：每次活动准备一个具体问题，散场前问到答案；
- **做记录并分享**：把笔记整理后发到群里，是最低成本的贡献；
- **持续出现**：只在需要时才出现的人，很难被记住；
- **给别人价值**：介绍两个人认识、转发有用信息、帮新人解答一次基础问题。

## 什么时候值得深入投入
- 这个社群与你的目标方向一致（求职、研究方向、行业）；
- 你能在里面拿到真实反馈（作品被点评、方法被纠正）；
- 你有可贡献的独特能力（不是重复劳动）。

## 什么时候应该退出
- 活动变成纯社交，你既不学也不交付；
- 组织工作占用时间超过你能承担的上限，且不再产生新经验；
- 关系建立在岗位而非共同兴趣上，你离开后就失效。

## 可写进履历的贡献记录
- 被使用的文档或资料（链接 + 使用情况）；
- 组织过的活动（规模、你的角色、结果）；
- 分享与内容产出（观看、引用、反馈）；
- 带过的新人（他们的成长）。

## 从小事切入
选定社区后，从整理会议纪要、修复文档、做一次调研这类小事开始——每个组织都需要这些劳动。做完立刻留下记录：产出链接、参与人数、被采纳的建议。争取一个有名字的角色而不是「帮忙的人」，有名字的角色才能写进材料。

## 进阶：SIG 与 Working Group
SIG（特别兴趣组）与 Working Group（工作组）是行业与开源社区里**真正决定技术方向和标准的地方**，这里的参与记录（会议纪要里你的名字、你主导的提案）比任何自我介绍都有说服力。找到目标领域的 SIG/WG（开源项目看治理文档，学术与行业协会看官网），先旁听三次会议、读纪要与邮件列表搞清楚谁在主导，再从小事切入，有能力后提交正式提案。门槛不高，难的是持续出席；加入后潜水直到退出、跳过背景阅读直接发言，是最常见的两种浪费。

## 参与记录与角色，前提是承担具体交付
领域内最前沿的信息与人脉、对标准与方向的实质影响、可核实的专业参与记录，以及通向更大角色（讲者、委员会、工作组核心）的路径。半年评估一次：没有产出与联系就换方向。

判断一段实习值不值得，看三件事：**能不能产出可写进简历的具体成果**、**能不能让你确认或排除一个方向**、**时间成本是否低于它替换掉的机会**。打杂三个月且说不出做过什么，不如用同样的时间做完一个自己的项目。

## 先问自己：这段实习在回答什么问题
是“这行的日常到底是什么样”，还是“我能不能胜任这类工作”，还是“这类公司适不适合我”。问题不同，应该找的岗位也不同：验证行业选大公司，验证能力选能给你真实任务的团队。

## 看岗位描述，而不是看公司名气
同一个公司里，有的实习能接触核心业务，有的只是整理表格。判断方法很朴素：看招聘描述里“你将负责什么”，如果通篇是“协助、支持、杂项”，进去之后大概率就是这样。

## 三个记录指标
进去之后每月问自己一次：

- 我在积累可写进简历的成果吗？
- 我学到了能带走的东西吗（方法、工具、行业理解）？
- 我确认或排除了什么？

三个都答不上来，就该主动争取任务，或者考虑结束。

## 关于报酬与协议
在校生利用业余时间勤工助学一般不视为就业，可以不签订劳动合同——这既意味着实习门槛低，也意味着你的社保与解雇保护与正式员工不同。签约前看清协议性质：是实习协议还是劳动合同，报酬、工时、保险怎么约定。职业院校学生还可以对照《职业学校学生实习管理规定》检查岗位、时长与报酬是否合规。

## 结束时留下三样东西
一段能具体描述的经历、一两个愿意为你背书的同事、以及对这个方向的判断。哪怕结论是“不适合我”，那也是有效收获——它让你少走两年弯路。

最常见的错误是等到「准备好了」再投——而实习的门槛通常比学生想象的低，准备本身也是靠投递反馈来校准的。

## 不要等「全都会了」
招聘方招实习生时的预期是：**能做具体的事、能问对问题、能按时交付**，不是「已经能独立带项目」。所以判断标准不是「我会多少」，而是「我能不能交付一件小事」。

**可以开始投的信号**：你能独立完成一个小任务（写一段脚本、整理一份数据、画出一版原型、写一篇分析），并能把它讲清楚。

## 各阶段该准备到什么程度
| 阶段 | 应该有的东西 | 能投什么 |
| --- | --- | --- |
| 大一大二 | 一门基础技能 + 一次完整的小项目 | 远程实习、校内助研、小公司实习 |
| 大三 | 一个可展示项目 + 一段相关经历 | 暑期实习、正规企业实习（提前半年关注） |
| 大四 | 项目 + 实习 + 明确的岗位方向 | 企业实习转正、秋招前置实习 |
| 研究生 | 研究方向相关的项目或论文 | 研究型实习、对口企业研发岗 |

## 第一批申请的作用不是拿 Offer
- 用真实 JD 校准「我缺什么」；
- 练面试表达（前几场必然讲不好）；
- 建立投递与跟进的习惯（用 [求职追踪表](../docs/tools/求职追踪表.md)）。

**心理上把第一批当成侦察**，成功率反而上升——因为你会更愿意投那些「看起来够不着」的岗位。

## 一份经历都没有时，先补什么
按性价比排序：

1. **一个能演示的小项目**（两周内能做完的最小闭环）；
2. **一次校内助研或助教**（门槛低、有真实工作内容）；
3. **一段社群/社团的组织或内容工作**（能证明协作与交付）；
4. **一个公开作品或分析报告**（能点开链接看到）。

四条里做完任意一条，就具备了投递的起点。

## 投了几十份没回复时的排查
- **岗位错配**：投了要求 3 年经验的岗位；
- **简历没有可验证内容**：全是「熟悉」「了解」；
- **时间不匹配**：岗位要求 6 个月全职，你只有寒暑假；
- **渠道问题**：平台岗位已截止、长期挂岗；
- **邮件/平台留言空白**：正文至少三句话说明来意与匹配点。

## 什么时候该继续投、什么时候先停下来补
```
连续 20 份无任何回复（含自动回复） → 先补一个可展示项目
有面试但总在初面被拒           → 改表达方式（问题—动作—结果）
面试能过但岗位不匹配            → 调整投递方向
```

## 三种形态
- **日常实习**：学期内每周数天，录取门槛最低、时间灵活，是多数人积累第一段经历的入口；
- **暑期实习**：录取最难、培养最系统、留用评估最正式，一般提前三到六个月招聘，各公司时间不同，以官方招聘渠道为准；
- **寒假实习**：春节前后的短窗口，部分行业（券商、审计）有专门招聘，名额少。

## 时间安排
大二、大三（或读研第一年）是开始的常见时间点，不必等「准备好了」。第一段优先选「能学到东西、能写进简历」的，薪资往后放。多段实习逐步升级：第一段求入行，第二段求方向确认，第三段冲留用或更好的平台。

## 两个常见错误
只投暑期实习、前面的时间全空着；为凑经历去做与方向无关的纯打杂岗位。学期中课业繁重的，用假期集中解决，别硬凑。找的渠道见 [没经验怎么找实习](03-做项目、打比赛、进实验室.md#internship-how-to-find)。

第一段实习的难点是**没有实习经历去换实习经历**。破解方式不是「投得更多」，而是换一种证明方式：用可展示的小交付替代工作经历。

## 没有经验时，你手里能用的四样东西
1. **课程项目或自主项目**：只要你能讲清问题、做法与结果，它就算经历；
2. **竞赛或开源贡献**：有公开记录，能被验证；
3. **技能的可验证证据**：代码仓库、作品集、数据报告、笔记教程；
4. **可迁移的软技能证明**：组织活动、带团队、做内容运营的记录。

**关键动作**：把其中至少一样做成「别人不问你也能看懂」的形式（README、演示、截图、数据）。

## 渠道按优先级排
| 渠道 | 为什么优先级高 | 怎么用 |
| --- | --- | --- |
| 老师 / 学长学姐推荐 | 有人背书，跳过初筛 | 具体说明你能做什么、能投入多久 |
| 学院就业群与校企合作 | 岗位真实、竞争相对小 | 第一时间响应，附材料 |
| 公司官网实习栏目 | 信息准确，有留用通道 | 提前 3 个月关注，按开头批次投 |
| 招聘平台 | 量大但竞争激烈 | 用关键词筛「实习」「在校生」 |
| 内推 | 提高被看到概率 | 找同岗位的人（见 [校友与内推](05-从学校走向第一份工作.md#job-channel-alumni)） |

## 投递时的三个具体动作
- **简历按岗位调整**：把与 JD 最相关的项目放到最上面，删掉无关内容。一页；不放照片、身高体重、家庭成员；
- **写清可投入时间**：实习最怕的是「每周能来几天」说不清。明确写出可实习时段与每周天数；
- **附上链接而不是描述**：把仓库、作品、报告链接放在简历顶部或邮件正文。

## 投了几十份没回复，通常是哪几种问题
- **岗位选错**：要求 3 年以上经验的社招岗，不要投；
- **简历没有可验证的东西**：全是课程名与「熟悉」「了解」；
- **时间不匹配**：JD 要求 6 个月全职，你只能寒暑假——这类信息要先核对；
- **投递渠道错**：平台已截止或岗位是长期挂岗（看发布时间）；
- **正文一句话都没有**：邮件投递时，正文至少三句（我是谁、为什么投、能做什么）。

对照上面五条排查，比继续盲投有效得多。

## 第一段实习该接受什么、不该接受什么
- **可以接受**：薪资低、活杂、公司不大——前提是能接触到真实业务，有人带你；
- **不该接受**：无薪且没有实质工作内容、要求先交培训费、承诺「转正」却无书面依据（涉及招聘诈骗的常见套路）。

## 什么时候该继续投、什么时候该先补项目
- **连续 20 份无任何回复**（含自动回复）：先补一个可展示的项目，再继续投；
- **有面试但总在初面被拒**：改表达方式，把项目讲成「问题—动作—结果」；
- **拿到面试但专业问题答不上来**：按岗位要求补基础，别的先放一放。

## 五步流程
1. 先定两三类目标岗位，据此改出**针对性简历**——一份简历海投所有岗位是最低效的做法；
2. 盘点内推资源：学长学姐、老师、实习过的同学、行业社群；内推时给对方一份现成的简历与岗位链接，降低对方的成本；
3. 学校就业信息网与院系群常有经过筛选的岗位，别忽略；
4. 公司官网与官方公众号的岗位最可靠；第三方平台上「收费内推」「保证录取」一律不碰；
5. 记录每轮投递的结果与反馈，两周复盘一次投递策略——投递无记录，被拒了也不知道原因。

## 心理与成本
被拒是常态，把它当成校准简历的数据来源。付出的是简历制作与投递时间、内推关系的维护、以及被拒的心理成本；换来的是面试机会和对目标行业招聘口径的了解。简历的写法见 [简历怎么写](05-从学校走向第一份工作.md#job-hunting-resume)。

实习和项目不是竞争关系，选择的关键是分辨**你缺的那种经验能不能自己造**。

## 先分辨缺口属于哪一类
能靠项目补的：技术能力、作品产出、独立解决问题的过程——一个认真做完的项目就能提供，而且时间自由、可随时开始。必须进组织才能获得的：真实业务的复杂度、多人协作的流程、被 deadline 和需求变更反复摩擦的经验、来自上级的具体反馈——这些项目模拟不了。

## 按缺口选
还没做过任何项目时，先做项目：它是找实习的敲门砖，也是你想清楚方向的素材。已经有拿得出手作品后，实习的优先级通常更高——因为下一个稀缺项变成了组织内的真实经验。学期内做项目、假期找实习，是多数人走得通的节奏。

## 两种选错的代价都不高
项目的成本是时间与自律，失败时损失可控，而且失败本身也留下代码和复盘。实习的成本是一段完整的时间窗口（通常两到三个月）与通勤；如果岗位没有实质工作，损失的是这段窗口期。两者的回退成本都不高：**做错了都还能回头补另一项**，所以不用把这个选择看成不可逆的决定。

## 一次低成本验证
不确定自己缺什么时，用一个两到四周的小项目试一次：如果做完整流程很吃力，先补项目能力；如果做完很容易但讲不出「给谁解决了什么」，那缺的是真实场景，去找实习。见 [没经验怎么找实习](03-做项目、打比赛、进实验室.md#internship-how-to-find)。

### 实习和科研怎么选

```meta

status: complete

effort: medium

last_verified: 2026-09-27
```

实习与科研不是对立的两种「好经历」，它们证明的是不同的东西。选择依据是**你的下一条路看什么**。

## 两者各证明什么
| | 实习 | 科研 |
| --- | --- | --- |
| 证明 | 能在真实组织里交付、协作、按规范做事 | 能定义问题、设计验证、写出结论 |
| 产出 | 模块、上线结果、主管评价 | 报告、论文、数据/代码、导师推荐 |
| 适合 | 就业导向（研发、产品、运营、数据） | 升学导向（研究型硕博）、研究岗 |
| 周期与门槛 | 有固定批次与招聘流程 | 需要提前联系导师，周期更长 |

**共同点**：两者都要留下可展示的产出，否则只是「待过一段时间」。

## 怎么按目标判断优先级
```
目标研究型升学 / 研究岗 → 科研优先（尽早进组，产出论文或报告）
目标企业研发 / 数据岗 → 两者都值，实习通常更直接（先有一段实习再加科研）
目标产品 / 运营 / 职能岗 → 实习优先
还不确定方向 → 先做成本低、周期短的那个（通常是一段实习或一次小科研）
```

## 可以同时做吗
可以，但要注意两条：

- **时间上不一定冲突**：科研通常更灵活（按周投入），实习是固定工时；
- **产出会变薄**：两边都只投入一半，可能都没有可展示的结果。**优先保证一条出成果**。

## 常见误区
- **「科研一定比实习高级」**：多数企业岗位不看科研，看能否交付；
- **「实习越多越好」**：三段浅实习不如一段深度实习 + 一段科研；
- **「科研必须有论文」**：没有论文也可以有复现报告、数据集、工具等产出。

## 先判断路线，再分配时间
用真实体验判断，别靠想象：进实验室做一段，找实习做一段。判断方法见 [怎么判断自己是否喜欢科研](03-做项目、打比赛、进实验室.md#research-do-i-like-it)。两条线的产出也不同——科研线的产出是论文、推荐信与研究能力；产业线的产出是工程能力、业务理解与实习证明。

## 什么时候偏向实习
目标岗位看作品与工程经验；已经确认不做学术；需要尽快有收入或确定方向；当前阶段缺的是真实协作经验。实习还能让你提前知道一份工作到底长什么样，这对校准方向很有效。

## 科研转产业比反向更容易
科研投入周期长（以月计），成果有随机性，中途退出会浪费一段窗口；实习周期短、反馈快，但深度有限。**科研转产业比产业转科研更容易**——工程能力加研究训练很受欢迎，反向则要补论文与推荐信。所以犹豫不决时，先做那条回头更难的选择（即先试科研）通常更划算。

## 低成本验证
先做一次两到四周的科研小任务（复现、整理文献、数据清理），再决定要不要投入一个长周期课题；同时保留一段短实习作为对照。见 [实习和项目怎么选](03-做项目、打比赛、进实验室.md#internship-vs-project)。

## 什么时候偏向科研
目标是博士或研究型硕士；目标岗位看重研究训练（研究院、部分算法岗）；所在专业的研究经历本身就是硬门槛；你想验证自己是否耐受长期不确定。

实习值不值得，不看公司名气，看**你能带走什么**。四个维度可以快速判断。

## 四个判断维度
1. **真实交付**：你会负责具体的模块或任务，还是只做杂活？入职前问清「前三个月我要交付什么」；
2. **指导质量**：有没有指定带教人、多久同步一次？没人带是实习体验差的主因；
3. **可展示产出**：结束时你能写进简历什么（做了什么、结果如何）？
4. **方向相关性**：这段经历是否指向你的下一份工作或目标方向？

**四个里前两个最重要**。前两个缺失时，即使公司很有名，收益也有限。

## 远程实习的额外风险
- **交付边界模糊**：容易被安排零散任务，缺少完整项目经验；
- **指导更难获得**：需要你主动约时间、主动同步，否则很容易被忽略；
- **暴露度低**：转正与推荐信更依赖你主动争取；
- **合规问题**：跨境远程的合同与报酬结算方式要问清（是否需要票据、如何纳税）。

**远程实习的应对**：每周主动同步进展（三行邮件：做了什么、卡在哪、需要什么），每两周约一次一对一。

## 什么时候应该提前结束
- 连续一个月没有明确任务或只有纯杂活；
- 承诺的报酬与待遇不兑现（**保留聊天与合同记录**）；
- 涉及违规操作（伪造数据、无薪超时、要求支付费用）；
- 严重挤占学业且没有可展示产出。

**结束方式**：提前说明原因、完成交接、要一封实习证明（有比没有好）。

## 通用判断标准
好的实习至少满足：有具体的人带你、每周有明确任务与反馈、结束时你能拿出具体的东西（代码、文档、报告、成果数据）。只有「参与过」的描述、面试追问时讲不出一件完整的事，这段经历的价值就很低。

## 远程实习的特别注意
远程的好处是地点自由、门槛相对低，坏处是**学习密度天然更低、成果更难被看见**。它适合自律且目标明确的人，以及开发、设计、内容、数据这类可远程交付的岗位；需要现场观察行业运作、或自驱力不足容易被挂起的人，线下更好。入职前确认周会、任务分配与交付方式；把成果沉淀为可验证的形式（仓库、文档、成品）；主动同步进度——远程环境里没人看见你的努力，要让成果可见；结束时请带教写一段具体的评价。

## 一票否决项
收费的实习、「先交钱培训再上岗」的内推，都是骗局，见 [求职与实习里的坑](14-避坑.md#trap-fake-internships-and-paid-research)。无带教、无任务的挂名远程实习，投入产出接近于零。
