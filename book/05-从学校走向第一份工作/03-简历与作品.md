# 简历与作品

### 简历怎么写

```meta
id: job-hunting-resume
status: complete
stages: [college, undergraduate, new_grad, work_1_3]
topics: [job]
outputs: [work_experience]
effort: medium
evidence: [official, industry_data, experience_based]
summary: 简历怎么写：不同阶段的写法差异、各段经历写几条、没数字怎么办、技术岗与非技术岗的侧重、ATS 与链接、失败示例与修改顺序。
last_verified: 2026-09-27
```

简历的目标不是「介绍你」，而是**让筛选者在一分钟内找到留下你的理由**。因此它是一份按岗位定制的材料，不是一份自传。

## 先看清不同阶段的差异
| 阶段 | 简历重点 | 常见误区 |
| --- | --- | --- |
| 大一/大二（找第一段实习） | 课程项目、技能、可到岗时间 | 因为经历少而堆无关内容 |
| 大三/研一（找暑期实习） | 相关项目、成绩（如岗位看）、实习经历 | 只罗列技术栈 |
| 应届秋招 | 实习 + 项目 + 与岗位直接相关的产出 | 把经历写成职责描述 |
| 社招 | 交付成果与可迁移能力，按结果组织 | 仍按时间顺序堆经历 |

**同一份简历不能投所有岗位**：至少准备一个基础版，再按 JD 调整顺序与关键词。

## 一段经历写几条
通常每段经历写 2–4 条，核心项目可以 4–5 条。每条按三段写：

```
做了什么（动作，不是职责）
怎么做的（方法/约束/你的取舍）
结果如何（数字或可核对的事实）
```

**只写一条的经历**通常说明你没有展开它——要么补，要么删。

## 没有数字怎么办
数字最有说服力，但不是必须。替代品按可信度排序：

1. 可核对的事实（上线状态、使用范围、覆盖范围、通过率）；
2. 明确的对比（优化前 1.2s → 优化后 0.4s，同机同数据）；
3. 规模描述（团队人数、你的模块、用户量级）；
4. 方法与限制（说清你在什么约束下解决了什么问题）。

**不要编数字**：面试追问一层就会露底（见 [背调](05-Offer.md#job-hunting-background-check)）。

## 技术岗怎么写技术深度
- 写**取舍**而不是工具清单：为什么选这个方案、放弃了什么；
- 写**瓶颈与解决**：卡顿在哪、你怎么定位、结果如何；
- 给出**链接**（仓库、文档、演示），可点开比描述有力；
- 写清你的角色（几人团队、你负责哪部分）。

## ATS 与格式
部分公司用系统初筛（ATS），因此：

- 用常见的结构（教育/经历/项目/技能），不要把内容拆进复杂表格；
- 关键词用 JD 里的术语（同一件事用行业通用说法）；
- 不要放照片、身高体重、家庭信息（多数场景不需要，且可能引入偏见）；
- 一页（应届）到两页（社招），PDF 优先（除非要求其他格式）。

## 链接与作品集
- 放 2–3 个最相关的链接（代码仓库、演示、报告）；
- **提交前逐个点开检查**，失效链接等于没有；
- 需要登录才能看的内容，改提供截图与说明。

## 失败示例与改法
| 失败写法 | 问题 | 改法 |
| --- | --- | --- |
| 「负责后端开发，参与需求评审」 | 职责描述，没有动作与结果 | 写清你做了哪个模块、结果如何 |
| 「熟悉 Java、Python、Go、SQL…」 | 工具清单，无法验证 | 只保留与岗位相关且能深入解释的 |
| 「提升了系统性能」 | 没有口径 | 补上指标、样本与对比 |
| 「参与国家级项目」 | 归属不清 | 写清团队规模与你的部分 |
| 三页简历，课程占半页 | 重点被稀释 | 应届简历压缩到一页 |

## 修改顺序（比一次写好更重要）
1. 列出目标岗位的 3 个核心要求；
2. 检查简历是否在前三分之一就回应了它们（不够就把最相关的经历上移）；
3. 逐条删掉与岗位无关的内容；
4. 给每条补上结果或方法；
5. 让一个不了解你背景的人读一遍，看能否复述你做过什么。

## 先研究岗位，再动笔
选 2–3 类目标岗位，各看 5 份真实招聘启事，把任职要求里的关键词按重要性列出来。简历的作用是让筛选者在 30 秒内看到“这些关键词我都有”。

## 每段经历写成“动词＋做了什么＋结果”
- 有数字的写数字：负责某模块，上线后日活多少、错误率降了多少。
- 没有数字的写交付物：报告、代码仓库、作品链接、证书名称、公开发布的内容。
- 写清规模和角色：几人团队、你负责哪一部分，避免“我们”盖过“你”。

## 排版与长度
一页为限（经历特别多时最多两页）；倒序排列；用 PDF；文件名包含姓名与目标方向。排版只服务于可读性，不需要装饰。

## 一份简历投所有岗位是浪费
不同岗位要求不同，关键词也不同。按类改简历，通常每类花一两个小时，回报高于多投几十份。同类岗位可以共用一版，跨类要重写。

## 常见问题
- 写职责不写结果。
- 把跟岗位无关的经历堆满版面。
- 用“参与”“协助”开头，看不出你实际做了什么。

## 投递前自查
找一个做过招聘的人看一遍，只问一个问题：“30 秒内你能说出我是谁、适合什么岗位吗？”

## 三段式写法
```
项目名 + 你的角色（一句话）
做法：用了什么方法、解决了什么具体困难（2 行）
结果：数据或可核对的事实（1 行）
```

示例：

> 校园二手交易平台｜后端负责人（3 人团队）
> 我负责订单与支付模块；为解决并发下单的重复扣减问题，把库存校验放进事务并加幂等键。
> 上线后 3 周内完成 400+ 笔交易，无重复扣款；代码与接口文档在 <链接>。

## 按岗位调整侧重
| 目标岗位 | 侧重写什么 |
| --- | --- |
| 技术岗 | 技术难点、方案取舍、性能/稳定性数据 |
| 产品岗 | 问题来源、用户验证、指标变化 |
| 数据岗 | 数据来源与口径、方法、结论与影响 |
| 运营/内容岗 | 策略、执行规模、增长或转化数据 |
| 研究岗 | 问题、方法、结果、你的独立贡献 |

## 结果怎么量化
- 用**你确定的数字**：用户数、耗时、准确率、覆盖范围；
- 写清**口径**：「日活 200」不如「注册用户 1200、周活跃约 200」；
- 没有数字就写**可核对的事实**：上线状态、被谁使用、评审结论、测试通过率；
- **不要编**：面试追问一层就会露底。

## 没有项目时写什么
- 课程设计（写清问题与你的角色）；
- 竞赛作品（与 [竞赛经历怎么写](03-简历与作品.md#resume-competition) 配合）；
- 开源贡献（见 [开源手册](../../docs/manuals/开源手册.md)）；
- 自主复现或小工具（写清为什么做、怎么验证有效）；
- 实习中的具体模块（哪怕是支持性工作，也要写清你交付了什么）。

## 常见问题
| 问题 | 改法 |
| --- | --- |
| 只写功能清单 | 改成「解决了什么问题、结果如何」 |
| 用「参与」「协助」 | 写清你的具体动作 |
| 技术栈堆砌 | 保留与岗位相关、且你能深入解释的 |
| 团队成果写成个人成果 | 标注团队规模与你的部分 |
| 链接失效 | 提交前逐个点开检查 |

实习经历的价值取决于**你能否说出交付了什么**。只写公司名称与时间段，等于浪费一段真实经历。

## 三段式写法
```
做了什么（具体任务，不是职责描述）
怎么做的（方法、约束、你的判断）
结果如何（上线/交付/反馈/数据，带口径）
```

示例：

> 在某公司数据团队实习（3 个月）｜负责埋点校验工具
> 发现手工核对埋点耗时且易漏，写了一个校验脚本对比上报字段与数据表结构。
> 结果：核对时间从半天降到 10 分钟，覆盖了 30+ 事件；代码与说明在 <链接>。

## 不同岗位的侧重
| 目标岗位 | 侧重写 |
| --- | --- |
| 技术岗 | 技术实现、性能/稳定性数据、你的模块 |
| 数据岗 | 数据来源与口径、方法、结论影响 |
| 产品/运营岗 | 问题来源、方案、指标变化 |
| 研究岗 | 问题、方法、结果、你的独立贡献 |

## 短实习、杂活、远程实习怎么写
- **短实习（1–2 个月）**：写你完成的一件具体的事，不写时长；如果确实只是熟悉环境，就如实简写一行并说明学习到的流程；
- **杂活为主**：写清你交付的部分（数据整理、文档、测试），并说明你如何把它做得可靠（例如把重复流程做成模板）；
- **远程实习**：写清协作方式（同步频率、工具）与交付物，消除「是否真实参与」的疑虑。

## 常见误区
- 只写「协助完成……」——听不出你的动作；
- 把团队成果写得像个人成果（面试追问即露）；
- 时间线与实习证明不符（**以合同与证明为准**）；
- 写的技能与岗位无关，稀释重点；
- 没有留下任何可核对的事实。

## 与项目经历怎么取舍
- 实习有真实交付 → 实习优先，项目作为补充；
- 实习以辅助为主、项目更完整 → 项目放前面，实习写一行交付说明；
- 两者都弱 → 先补一个项目（见 [项目经历怎么写](03-简历与作品.md#resume-projects)），再回来改写实习。

## 怎么写才有信息
- 挑一件你**完整负责**的事来写：从接到需求到交付，你做了哪些决定；
- 写结果：产出了什么、带来了什么变化（数字最好，哪怕是「覆盖多少条数据」「节省多少时间」）；
- 写清你的角色边界：独立负责、主导某部分、还是参与执行——诚实比夸大安全，背调与追问都会核实，见 [背调](05-Offer.md#job-hunting-background-check)。

## 示例结构
「在 XX 团队负责 YY 模块的 Z 项改造：重新设计了 A 流程（说明你的判断），上线后 B 指标从 X 降到 Y；过程中处理了 C 问题（说明难点）。」

## 只有打杂经历怎么办
从日常里挑一件你做得比别人深的事（整理的数据、写过的文档、维护的流程），按上面的结构写；同时用项目经历补上不足，见 [项目经历怎么写](03-简历与作品.md#resume-projects)。

### 科研经历怎么写

```meta
id: resume-research
status: complete
stages: [undergraduate, master, phd]
topics: [job, research]
outputs: [work_experience]
effort: low
evidence: [experience_based]
summary: 科研经历怎么写：写清问题与你的具体贡献、用证据代替形容词，以及没有论文时怎么呈现研究经历。
last_verified: 2026-09-21
```

科研经历在简历里的价值不被「发表」决定，而由**你在研究里做了什么、做到什么程度**决定。招聘方与招生委员会看的是这个。

## 三段式写法
每一段科研经历按三段写，每段一到两行：

```
背景：研究什么问题、什么规模的团队/课题（一句话）
我的工作：负责哪一部分、用了什么方法、解决了什么具体困难
结果：可验证的产出（论文/报告/代码/数据/被采纳的方案）+ 你的位次或角色
```

示例（不必有多高的成就，但必须具体）：

> 参与 XX 方向课题组（3 人），负责数据清洗与基线复现。
> 复现两篇论文的关键结果，定位到原实现中未说明的数据预处理差异并整理成复现报告。
> 产出：复现报告与脚本（链接），组内用于后续实验的环境搭建。

## 用证据代替形容词
| 不写 | 改写成 |
| --- | --- |
| 熟悉机器学习 | 复现 X 方法并在 Y 数据集上达到与原论文一致的指标 |
| 参与国家级项目 | 负责其中 Z 模块的实现与测试，代码在组内使用 |
| 有一定的科研能力 | 独立完成文献综述 20 篇、提出并验证一个假设（结果：不成立） |

**「结果不成立」也可以写**：它证明你能设计验证、能接受负结果，这在研究岗里是加分项。

## 没有论文怎么写
- 写**正在进行**的工作，标注状态（在投/在写/数据收集完成）；
- 写**复现报告**与**文献综述**——它们本身就是研究训练的证据；
- 写你在组里承担的**具体模块**（数据、实验、分析、写作），而不是「参与课题」；
- 有代码或数据就放链接；没有就写清可提供的材料清单（面试时展示）。

## 常见问题
- 只写课题名称与导师名字，看不到你做了什么；
- 把团队成果写成个人成果（面试一问就露）；
- 罗列用了多少工具，却不写解决了什么问题；
- 全部写成「参与了……协助了……」——没有动作与结果。

简历的整体写法见 [简历怎么写](03-简历与作品.md#job-hunting-resume)；研究经历的深挖见 [科研手册](../../docs/manuals/科研手册.md)。

## 投学术/研究岗怎么写
突出四要素：研究问题是什么、你用什么方法、你**具体**贡献了哪部分、结果如何（论文、报告、数据集）。署名位次要如实写，见 [作者位次与署名](../04-升学、就业还是出国/04-深入科研.md#research-writing-and-submission)。

## 投产业岗怎么翻译
把科研动作翻译成岗位语言：

- 复现与改进实验 → 工程实现与调优能力；
- 设计对照与指标 → 实验设计与数据分析；
- 写论文与做报告 → 结构化表达；
- 跨组协作取数 → 跨团队沟通。

用「问题—做法—结果」的结构写，避免一整段术语。招生与求职的不同侧重见 [科研到底是什么](../03-做项目、打比赛、进实验室/03-科研初体验.md#research-what-is-research)。

```meta
summary: 竞赛经历怎么写：奖项之外要写清解决的问题、你的角色与产出，以及名次不高时怎么写。
last_verified: 2026-09-21
```

竞赛在简历上的作用取决于你**能不能讲清做过的具体问题**。只写奖项名称，等于把一个可验证的素材浪费掉了。

## 一行奖项 + 三行内容
```
赛事名称 · 奖项/名次（若有）
问题：什么类型的题目/目标
我的角色与动作：负责哪部分、用什么方法、遇到什么问题怎么解决
产出：代码/论文/原型/评测结果（链接）
```

**示例**：

> 全国大学生数学建模竞赛 · 省级二等奖
> 题目为城市交通信号优化；负责建模与编程（3 人队）。
> 用排队论建立路口延误模型，发现原模型未考虑转向比例后加入该因素，使预测误差从 X 降到 Y。
> 产出：论文与代码（链接）。

## 名次不高时怎么写
- 写**过程中的具体判断**（试过什么、为什么放弃、最终选了什么），这比名次更能说明能力；
- 把可展示产出放上去（代码、原型、报告）——**评委与招聘方更信能点开的东西**；
- 如果同方向有更强的证据（实习、项目），竞赛可以只留一行。

## 写法上的三个提示
- **不要写赛事介绍**：招聘方不会因为你解释比赛规模而加分；
- **不要堆参赛数量**：三次参赛各写两行，不如一次写透；
- **数字要有口径**：名次（省赛第几/前百分之几）、队伍规模、你的模块占比，写清才有可比性。

## 不同用途的侧重点
| 用途 | 侧重 |
| --- | --- |
| 技术岗 | 你解决的技术问题、方法选择、代码产出 |
| 产品/咨询岗 | 问题拆解、分析框架、团队协作与表达 |
| 升学（研究型） | 与研究方向的相关性、能否转化为研究能力 |
| 升学（授课型） | 体现动机与基础的证据，权重低于成绩与语言 |

## 什么时候可以省略
奖项完全与目标岗位无关、且你只是挂名参与时，可以省略或压缩成一行。把省下的空间给 [项目经历](03-简历与作品.md#resume-projects) 通常更划算。

这一页讲的是**投递时怎么用**：面对具体岗位，从已有的作品素材里挑哪几项、按什么顺序、用什么格式递出去。素材本身怎么整理与长期维护，见 [作品集怎么组织](../03-做项目、打比赛、进实验室/01-项目与作品.md#project-portfolio)。

## 三类项目怎么讲
| 类型 | 讲什么 | 适合证明 |
| --- | --- | --- |
| 个人项目 | 问题来源、你的独立贡献、结果与限制 | 主动性、完整交付能力 |
| 团队项目 | 你负责的模块、接口与协作方式 | 协作与工程规范 |
| 真实使用/上线 | 用户量、留存、反馈、迭代记录 | 结果导向、真实场景能力 |

**每一条都要有「你的动作」**，而不是「项目做了什么」。

## 每个条目的结构（一页之内）
```
背景：解决什么问题、给谁用（2 行）
我的角色与关键决策：做了什么、为什么这样选（3 行）
结果：数据、用户反馈、测试结果（带口径）
链接：代码 / 演示 / 报告
限制：已知问题与未完成部分
```

**写清限制反而加分**：它说明你知道边界在哪。

## 排序与数量
- **按目标岗位排序**：投研发把技术深度放前，投产品把问题定义与用户反馈放前；
- **数量**：两到三个打磨完整的项目胜过十个半成品；
- **每个项目都要能点开**：链接失效等于没有。

## 常见误区
- **只有截图没有说明**：看不出你做了什么；
- **罗列技术栈**：不解释为什么用、解决了什么问题；
- **把教程项目当作品**：复刻一遍教程（见 [Demo](../03-做项目、打比赛、进实验室/01-项目与作品.md#project-demo)）；
- **夸大归属**：团队成果写成人成果，面试一追问就露；
- **长期没更新**：一年前的项目链接已失效。

## 检查清单（提交前逐项确认）
1. 每个条目都有：问题、我的动作、结果、链接；
2. 结果有数字或可核对的事实；
3. 链接可访问（代码、演示、报告）；
4. 没有需要登录才能看的材料（除非说明申请方式）；
5. 没有与岗位无关的凑数内容；
6. 用目标岗位的语言描述（对齐 JD 术语）。

## 作品集在哪里放
- 简历中放**最相关的两三个**（附链接）；
- 单独做一个可访问的页面或仓库（README 汇总）；
- 面试时准备 3 分钟与 10 分钟两个版本的口头讲法。

## 放什么
选三个最能代表目标岗位能力的项目，宁缺毋滥；每个项目写统一结构：问题 → 方案 → 关键难点 → 结果（数字或演示）→ 链接；再配一个三十秒能看完的演示（截图或录屏），见 [作品集](../03-做项目、打比赛、进实验室/01-项目与作品.md#project-portfolio)。

## 没有作品怎么办
用一个两到四周的小项目补一个（见 [第一个个人项目怎么开始](../03-做项目、打比赛、进实验室/01-项目与作品.md#project-personal)），或者把课程项目按可展示标准整理出来。
