# 项目作品与开源

项目的价值不在代码写了多少行，而在**有没有人用它、你能不能证明它成功过、别人能不能在五分钟内看懂**。

这三个问题可以立刻筛掉大多数“项目经历”：教程复刻、跟着视频敲的练习、没有 README 的仓库、没人用过的工具。它们不是没价值，但它们是**练习**，不是**经历**。

开源是项目的延伸而不是另一件事：它把“我自己做的东西”变成“被别人评审、被别人使用的东西”，因此能换回真实反馈、公开记录和行业可见度。代价是它需要承担别人的期望。

### 什么叫真正的项目

```meta
effort: low
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  一个“真正的项目”要满足三个要素：**解决一个具体的真实问题**（哪怕是自己的）、**有别人可验证的产物**（能运行、能看、能用）、**经历了至少一次真实的反馈与修改**。三者缺二，它更接近一次练习。

- 适合谁：
  需要用作品证明能力的学生与转行者；不确定自己的东西算不算“项目”的人。

- 不太适合谁：
  ——（标准本身对所有人都适用；不必用它否定做过的练习，练习有练习的价值。）

- 能换回什么：
  简历上经得起追问的一行；面试时能讲 20 分钟的故事；对“完成”的真实理解。

- 要付出什么：
  数周到数月；真实的迭代（这一步最容易被跳过）。

- 怎么开始：
  1. 写一句话问题陈述：为谁、解决什么、怎么算解决。
  2. 缩到一个月内能出第一版可用的规模——完成一个小而真的项目，胜过规划一个大而空的。
  3. 上线或交付给至少一个真实用户（用户可以是自己持续使用、可以是同学同事），收集反馈。
  4. 按反馈做第二轮修改，记录改了什么、为什么。
  5. 把过程沉淀为 README 与演示（见 [作品集](10-项目作品与开源.md#project-portfolio)）。

- 常见误区：
  把跟教程做的东西当项目；只有代码没有使用者；规划宏伟、从未完成；没有版本二，反馈环节完全缺失。

- 下一步可能打开什么：
  作品集的核心件；面试叙事；真实用户的意外反馈（常常指向下一个项目）。

- 证据与来源：
  - 项目能力评估的普遍经验。 （Experience-based）

### 教程项目

```meta
id: project-tutorial
status: complete
stages: [highschool, college, undergraduate, secondary_vocational]
topics: [project, skill]
outputs: [work_experience]
effort: low
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  教程项目是学习工具，不是能力证明——**面试官看一眼就知道它是教程，因为教程项目长得都一样**。它的问题不在“做了”，而在“没有做任何教程之外的决定”。

- 适合谁：
  初学者（认真跟完、改出变化的教程项目是有价值的阶段）；想补齐技术栈的人。

- 不太适合谁：
  把三四个教程项目放进简历核心位置的人；跟完教程连改一个需求都不会的人。

- 能换回什么：
  技术栈的初始理解；一套可改造的代码基底。

- 要付出什么：
  教程本身的数小时到数周；如果止步于此，沉没的是本可以做真实项目的时间。

- 怎么开始：
  1. 跟完教程后立即做“改造练习”：换数据源、换核心功能、加一个教程没有的需求。
  2. 遇到教程没覆盖的问题，查官方文档解决——这一步才是真实工作的常态。
  3. 把改造后的版本作为第一个“自己的项目”，写清与原教程的差异。
  4. 简历上不写教程项目原样，只写你在其之上做出来的东西。

- 常见误区：
  跟完教程就放进简历；连续跟五六个教程获得“学了很多”的错觉；从不脱离教程自主排错。

- 下一步可能打开什么：
  第一个真实项目（见 [什么叫真正的项目](10-项目作品与开源.md#project-what-is-real)）。

- 证据与来源：
  - 招聘方对教程项目的普遍判断。 （Experience-based）

### 个人项目

```meta
id: project-personal
status: complete
stages: [college, undergraduate, master, secondary_vocational, new_grad, work_1_3]
topics: [project]
outputs: [project, work_experience]
effort: medium
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  个人项目的价值公式是**真实需求 × 完成度 × 展示质量**。一个可靠的选题方向是“给自己解决一个真实痛点”——因为需求真实、你懂用户、还能长期维护。

- 适合谁：
  需要作品的学生与转行者；有真实小痛点愿意自己动手解决的人。

- 不太适合谁：
  选题追热点但自己不用的人（做不出来也留不住）；同时开五六个项目、每个都半成品的人。

- 能换回什么：
  一个能演示、能讲述、能迭代的作品；完整的问题定义—实现—维护经验；可能的真实用户。

- 要付出什么：
  数周到数月的业余时间；维护的长期成本（一个有人用的项目会持续要你修东西）。

- 怎么开始：
  1. 列出你每周重复做、又麻烦的事，挑一个能用程序或流程解决的。
  2. 第一版限制在两周内能用，功能只留最核心的三个。
  3. 自己真实使用两周，记录所有别扭的地方——这是第二轮的清单。
  4. 给它一个干净的 README：解决什么、怎么用、截图或演示。
  5. 有真实用户后，认真处理反馈，哪怕每月只有一两条。

- 常见误区：
  技术炫技但无人受益；功能膨胀导致烂尾；上线后再也不维护；README 空到没人知道怎么跑起来。

- 下一步可能打开什么：
  作品集的核心件；面试叙事；甚至一款小生意的起点（见 [创业、自由职业与副业](14-创业自由职业与副业.md#startup-side-project)）。

- 证据与来源：
  - 个人项目经验的普遍规律。 （Experience-based）

- 最后核实：
  2026-09-21

### 团队项目

```meta
id: project-team
status: complete
stages: [college, undergraduate, master, secondary_vocational, work_1_3]
topics: [project, community]
outputs: [project, work_experience, network]
effort: medium
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  团队项目练的是个人项目练不到的东西：**分工、约定、依赖别人的进度、以及吵架之后还能把事做完**。雇主看团队项目，看的正是这些信号。

- 适合谁：
  缺协作证据的学生；想做比个人能力更大的事的人。

- 不太适合谁：
  找不到靠谱队友、每次都自己扛所有事的人（不如先做个人项目）；为组队而组队、目标不一致的草台班子。

- 能换回什么：
  真实的协作与版本管理经验；规模更大的产出；可以互相背书的队友。

- 要付出什么：
  沟通成本（经常超过预期）；进度被队友拖累的风险；利益与署名的提前约定。

- 怎么开始：
  1. 三到五人、能力互补、时间表能对齐——这三条缺一就先别开工。
  2. 开工前书面约定：目标、分工、代码与文档归属、谁对外负责。
  3. 用真实的协作工具与流程：任务看板、代码评审、每周同步。
  4. 每个阶段都有可交付物，而不是最后一个月赶工。
  5. 结束后互相写具体的评价（比“合作愉快”有用得多）。

- 常见误区：
  一人干活全队署名；没有约定，成果归属扯皮；把“开会多”当协作好；烂尾后互相拉黑。

- 下一步可能打开什么：
  面试中的协作证据；一段可验证的伙伴关系；更大的项目。

- 证据与来源：
  - 团队协作项目的普遍经验。 （Experience-based）

- 最后核实：
  2026-09-21

### GitHub 项目做到什么程度才算项目经历

```meta
id: project-what-counts-as-experience
status: complete
stages: [undergraduate, master, new_grad, work_1_3, career_change]
topics: [project]
outputs: [portfolio, project, public_contribution, work_experience]
effort: medium
evidence: [official, experience_based]
last_verified: 2026-09-21
```

- 一句话：
  三个问题就够了：有没有人用它、能不能被验证、别人能不能在五分钟内看懂并跑起来。过不了这三关的，可以叫练习，但不要写进简历当经历。

- 适合谁：
  想用项目补简历的人；在校生与转行者；面试被问到“讲一个你做的项目”却答不上来的人；有技术能力但缺少可展示产出的人。

- 不太适合谁：
  目标岗位不通过项目评估的情况（以考试、资历、执业资格为主要筛选的岗位）。这时应把时间投到对应门槛上，而不是硬做项目。

- 能换回什么：
  可验证的作品；面试中的具体话题（能深聊半小时的项目远胜十个 demo）；技能证明；真实用户反馈；公开贡献记录；有时还有工作或合作机会。

- 要付出什么：
  几十到几百小时；维护成本（Issue、文档、兼容、更新）；被指出 bug 与被批评的心理成本；发布之后持续的投入——这一点最常被低估。上线不是结束。

- 怎么开始：
  1. 从自己的真实需求出发，选一个**小而完整**的题目：解决一个你每周都会遇到的问题，而不是做一个大而空的“平台”。
  2. 定义“做完”的标准：可运行的入口 + README + 最小测试 + 至少一个真实用户。缺一项都还没到可以展示的程度。
  3. README 五要素：一句话说明是什么；用在什么场景；怎么安装运行；演示（截图、GIF 或在线地址）；已知限制。
  4. 先做能在两周内跑通的版本，再迭代。不要憋大招。
  5. 找 1–3 个真实用户（同学、社群、同事），收集反馈，把反馈与处理写进 README 或 Issue。
  6. 写进简历时用“问题 → 做法 → 结果”的格式，结果要能量化：用户数、处理量、耗时、误差、节省的时间。不要写“使用 X 框架实现了 Y”。

- 常见误区：
  项目多而浅——十个半成品不如一个有真实用户的项目；没有 README，或 README 只列技术栈；把教程项目当原创（面试官看得出来）；只有 commit 记录没有交付；不写限制与不足，反而降低可信度；把 star 数当唯一指标（star 受推广影响大于质量）；项目无法在你自己的机器上重新跑起来。

- 下一步可能打开什么：
  开源贡献与维护者角色；面试中的深挖环节；实习与工作机会；技术社群与同行关系。

- 证据与来源：
  - GitHub 官方文档：README、许可证、Issue 与 Pull Request 的规范与实践。https://docs.github.com/ （Official）
  - 开源项目的贡献指南（CONTRIBUTING）、行为准则与治理文件，是其所在仓库的权威依据。 （Official）
  - “项目经历在招聘中的权重”因岗位而异，缺少统一统计，本条只给出可验证性的判断方法。 （Experience-based）

- 最后核实：
  2026-09-21

### 作品集

```meta
id: project-portfolio
status: complete
stages: [college, undergraduate, master, secondary_vocational, new_grad, career_change]
topics: [project]
outputs: [project, work_experience, optionality]
effort: low
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  作品集不是项目列表，是**按目标岗位组织的能力证据**：三个打磨过的项目加清晰的讲述，胜过十个仓库链接。评审平均只给每个项目一两分钟，所以第一屏就要回答“这是什么、解决了什么、做得怎么样”。

- 适合谁：
  找实习与工作的人；转行需要证据的人；接单与自由职业者（给客户看的能力陈列）。

- 不太适合谁：
  只搬运 README、没有任何自己加工的人。

- 能换回什么：
  简历通过率；面试中的主动权；对自身能力结构的清晰认识。

- 要付出什么：
  每个项目的整理时间（写清、截图、录演示各需数小时）；定期维护。

- 怎么开始：
  1. 选三个最能代表目标岗位能力的项目，宁缺毋滥。
  2. 每个项目写统一结构：问题 → 你的方案 → 关键难点与解决 → 结果（数字或演示）→ 链接。
  3. 给每个项目配 30 秒内能看完的演示（截图或录屏），评审点开就能看懂。
  4. 排序按“与目标岗位的相关度”，不是时间倒序。
  5. 每半年更新一次：删掉过时的，替换更强的。

- 常见误区：
  十个仓库全是半成品；只有代码没有讲述；简历与作品集口径不一致；链接失效或打不开。

- 下一步可能打开什么：
  更高的面试转化；清晰的自我定位。

- 证据与来源：
  - 作品集评审的普遍经验。 （Experience-based）

- 最后核实：
  2026-09-21

## 开源

### 第一次开源贡献怎么开始

```meta
id: opensource-first-contribution
status: complete
stages: [undergraduate, master, new_grad, work_1_3, career_change]
topics: [project, community]
outputs: [public_contribution, network, portfolio, reputation]
effort: medium
evidence: [official, experience_based]
last_verified: 2026-09-21
```

- 一句话：
  不要随便找一个标着“新手友好”的大项目乱改。正确顺序是：先用起来一个项目，遇到一个具体的小问题，然后按它的贡献指南把它修掉。先成为用户，再成为贡献者。

- 适合谁：
  想进开源但不知从哪开始的人；想接触真实代码评审流程的人；想用开源补充项目经历的人。

- 不太适合谁：
  把开源当求职捷径、只想刷 commit 数的人（维护者能识别，这类贡献通常也不被计入）；不使用目标项目的人；无法承担“提交后几周无人回应”的人。

- 能换回什么：
  真实的评审经验；与维护者的联系；公开可见的贡献记录；对工程流程（Issue、分支、CI、Review、发布）的实际理解；少数情况下直接带来工作机会。

- 要付出什么：
  前期阅读代码的时间通常比写代码多；英文沟通；被拒绝或被要求重改的心理成本；持续跟进——PR 挂几周是常态，不是异常。

- 怎么开始：
  1. 选一个你**已经在用**的项目（工具、库、框架都可以），能本地跑起来。
  2. 读它的 CONTRIBUTING.md 和 Issue 标签说明。不少项目要求先开 Issue 讨论再提 PR，跳过这一步会被直接关闭。
  3. 从最小的事开始：文档错字、示例代码跑不通、错误信息不清楚、测试覆盖。文档类贡献同样计入贡献记录。
  4. 遇到 bug 先复现，写出最小复现步骤。这份描述本身就是有价值的工作。
  5. 提 PR 保持小而聚焦：一个 PR 解决一件事，写清“改了什么、为什么、怎么验证”。
  6. 维护者要求改动是正常流程，不代表你能力不行。及时跟进回复。
  7. 第一次被合并后，再认领更复杂的问题。在一个项目里持续贡献，价值远大于到处撒网。

- 常见误区：
  一上来改核心代码然后被关掉；不看贡献指南直接提 PR；一个 PR 混入多个不相关修改；把机器翻译的文档或格式调整当成主要贡献；提交后失联；用“提了多少 PR”当资本，而不看合并率；被拒绝一次就认为开源不欢迎新人。

- 下一步可能打开什么：
  成为常用项目的稳定贡献者；参与 SIG 与工作组（见 [社群、导师与行业影响力](13-社群导师与行业影响力.md)）；申请开源项目的差旅或开发资助（见第 12 章）；维护者身份带来的机会。

- 证据与来源：
  - GitHub 官方文档：Issue、Pull Request 与开源项目治理文件的说明。https://docs.github.com/ （Official）
  - 各开源项目的 CONTRIBUTING.md 与行为准则，是判断贡献方式的权威依据。 （Official）
  - 开源导师与资助项目官方页面：Google Summer of Code https://summerofcode.withgoogle.com/ 、Outreachy https://www.outreachy.org/ ；时间与资格以当年度官方公告为准。 （Official）

```meta

status: complete
```

- 一句话：
  Issue 和 PR 的写法决定维护者愿不愿意理你：**先搜索再提问、一次一个主题、提供可复现的最小例子、改动的理由写清楚**。维护者时间有限，沟通成本低的人拿到的机会也多。

- 适合谁：
  开始参与开源的人；想让自己的贡献被更快合并的人。

- 不太适合谁：
  ——（写法本身对提需求给同事同样适用。）

- 能换回什么：
  更高的回复率与合并率；维护者的好感（下一次贡献的信任基础）。

- 要付出什么：
  提交前多花的半小时（自查、补信息）；被要求修改的耐心。

- 怎么开始：
  1. 提 Issue 前先搜已有 Issue（重复提问最招人烦）；用标题概括问题，正文给版本、环境、复现步骤。
  2. 提 PR 前读项目 CONTRIBUTING.md 与最近合并的 PR，对齐风格与范围。
  3. PR 保持小：一次只改一件事，改动理由写在描述里，关联对应 Issue。
  4. 收到 review 意见逐条回应；修改后 re-trigger 评审而不是另开新 PR。
  5. 被拒也是正常结果：礼貌收尾，社区声誉是长期账户。

- 常见误区：
  “我发现了 bug”但没有复现步骤；一个 PR 塞五个改动；不读贡献指南直接提交；被拒后口出恶言。

- 下一步可能打开什么：
  被合并的贡献记录；维护者的信任；更深入的参与（见 [Maintainer 与治理](10-项目作品与开源.md#project-maintainer)）。

### Maintainer 与治理

```meta
id: project-maintainer
status: complete
stages: [work_1_3, work_3_5, master, phd, undergraduate]
topics: [project, community]
outputs: [reputation, network, leadership]
effort: high
evidence: [experience_based]
last_verified: 2026-09-21
```

- 一句话：
  从贡献者到 Maintainer 的转变不是荣誉授予，是**接过一份长期责任**：审别人的代码、回别人的 Issue、处理社区分歧、在自己没空的时候项目也活着。想做之前先想清楚维护成本，很多流行项目死于作者失联。

- 适合谁：
  有一个真实被使用、自己也持续在用的项目的人；愿意把“让项目活下去”当长期事务的人。

- 不太适合谁：
  只想要 Maintainer 头衔的人；项目爆火但自己已无力维护的人（及时补充维护者或明确归档，比装死体面）。

- 能换回什么：
  真实的治理经验（评审、发布、社区管理——这些是工作里稀缺的证据）；社区声誉；用人单位看得见的领导力证明。

- 要付出什么：
  每周固定的维护时间（社区通常比想象中 demanding）；处理分歧的情绪成本；长期义务。

- 怎么开始：
  1. 先在自己的项目上练习全套治理：发布版本、写变更日志、处理外部 PR。
  2. 在参与的项目里主动承担可见的维护工作（审 PR、修文档、管 Issue 列表）。
  3. 现有 Maintainer 邀请或你主动申请时，先明确能投入的时间与权限范围。
  4. 建立可持续机制：贡献指南、行为准则、明确的技术决策流程；一个人扛所有事不可持续。
  5. 学会归档：项目不做了就明确标注，留好交接说明。

- 常见误区：
  不好意思拒绝低质量贡献导致精力耗尽；治理规则缺失导致社区争吵；失联式维护毁掉项目与自己的声誉。

- 下一步可能打开什么：
  开源社区的正式角色；行业声誉与工作机会；治理与领导力的实证经历。

- 证据与来源：
  - 开源治理的普遍实践（各基金会与社区公开的治理文档）。 （Official）
  - 维护者经验的普遍规律（维护者倦怠是开源社区的公开话题）。 （Experience-based）
