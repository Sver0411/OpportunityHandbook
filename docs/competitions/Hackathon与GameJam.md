# Hackathon 与 Game Jam

Hackathon（黑客松）与 Game Jam 属于**限时创作活动**：24–72 小时内从零做出可演示的东西。它们的价值不在奖，而在**强制你完整体验一次「定义问题 → 做出来 → 讲清楚」的全过程**。

## 现场真实节奏（以 48 小时为例）

```
第 0–2 小时：组队、确认主题与规则（有些活动命题固定）
第 2–4 小时：定范围 —— 写下「必须做的三件事」与「明确不做的清单」
第 4–20 小时：做核心闭环（哪怕很粗糙，先让主流程跑通）
第 20–24 小时：睡觉（熬夜到最后一刻往往导致演示失败）
第 24–36 小时：补完主流程 + 开始做演示材料
第 36–44 小时：冻结功能，准备演示脚本、录屏、README
第 44–48 小时：演示与答辩
```

**最关键的两条**：一是在前 4 小时把范围砍到能做出来，二是**留出至少 4 小时做演示准备**。

## 选题与切范围

- 选题标准：**你自己或你身边人真实遇到的问题** + 48 小时内能做出可演示版本；
- 范围控制：把功能列出来，只保留「不做演示就讲不清」的部分；其余明确写进「未来做」；
- 技术选择：优先用你熟悉的栈。**用没学过的技术是限时活动里最常见的失败原因**。

## 演示决定一半分数

评委看不到你的代码，只看到 5 分钟演示。所以：

- **准备一段可重复播放的脚本**（不要现场即兴，网络/硬件都不可靠）；
- **从用户视角讲**：谁遇到什么问题 → 现在怎么做 → 我们的方案改变了什么；
- **诚实说明没做的部分**：评委通常会问「你们没做什么」，答得清反而加分；
- **录屏备份**：现场演示崩了还能放录屏。

## Game Jam 的额外要点

- **玩法优先于美术**：一个有趣的机制 + 粗糙画面，胜过漂亮但没有可玩性；
- **一个核心机制做深**：新手团队常见问题是塞太多系统，结果每个都不完整；
- **测试别人的机器**：构建产物要在没装环境的电脑上能跑；
- **提交页面写清操作**：没有操作说明的提交常被忽略。

## 组队

- 3–5 人比较合适；确定一个**决策者**（否则定范围会耗掉整个上午）；
- 分工按「交付物」划分（前端/后端/美术/演示），而不是按技术名词；
- 提前约定：谁负责演示材料、谁负责提交、什么时候冻结功能。

## 赛后

- 把项目整理成作品（补 README、录演示、写下已知问题）；
- 如果机制有趣，可以继续做成完整作品——**很多个人项目就起源于一次 Jam**；
- 写一页复盘：范围判断是否准确、哪一步最耗时、下次改什么。
