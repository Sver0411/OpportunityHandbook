# Playbook：把一项新技术学到“能用”

这份 Playbook 不规定几周学会，也不规定必须看多少课程。进入下一步的条件只有一个：**你是否已经能完成上一层的真实任务。**

## 先定义“我为什么要学”

不要写“学 Docker”“学 Python”。改成一个任务：

> 我需要把一个服务在新机器上稳定部署。  
> 我需要用 Python 把一份真实 CSV 清洗、分析并输出报告。  
> 我需要让 ESP32 可靠读取传感器并处理断连。

如果说不出任务，先不要开始系统学习。你很容易陷入“学知识点但不知道何时够用”。

## 只补最小前置知识

先用官方 Quick Start、入门文档或一份可靠教程，把最小闭环跑通。此时允许照着做，但同时记两张清单：

- 我理解的部分；
- 我只是照抄、还解释不了的部分。

第二张清单就是下一步学习任务。

## 关掉教程，重新做一遍

换一个输入、目录、设备或业务场景，从空白开始。可以查文档，但不要重新逐步照教程。

卡住时先判断自己缺的是：
- 概念；
- API 用法；
- 环境配置；
- 调试能力；
- 前置知识。

不同卡点用不同方法补，不要统一回去“重看课程”。

## 主动制造一个错误

真正会用技术的人必须见过它怎么坏。

可以尝试：
- 输入为空/异常；
- 配置缺失；
- 网络断开；
- 权限不够；
- 依赖版本变化；
- 数据规模放大；
- 硬件掉线。

目标不是折腾，而是练习：现象 → 假设 → 证据 → 根因 → 修复 → 验证。

见 [如何 Debug：从现象到根因](../learning/调试方法.md)。

## 做一次迁移测试

把技能放到一个相邻但不同的任务：

学 SQL：从教程表换成真实业务数据。  
学前端：从静态页面换成有异步状态的页面。  
学嵌入式：从读一个传感器换成处理掉线和恢复。

如果一换场景就完全不会，说明你记住的是路径，不是能力。

## 怎么判断已经“够用”

至少能做到：
- 不看教程完成一个小任务；
- 遇到问题知道去哪里查；
- 能解释关键取舍；
- 能说出它不适用的场景；
- 过一段时间仍能重新做出来。

达到这里就可以先停，把时间投入真实项目或工作。更深的知识应由后续问题拉动，而不是为了“学完”。
