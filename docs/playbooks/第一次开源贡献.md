# Playbook：第一次开源贡献

目标：走完一次真实开源协作闭环。是否合并由维护者和项目节奏决定，不把固定时间或“必须合并”当成成功标准。

## Step 0 · 选项目：先找你真正能运行和理解的仓库

- 动作：从你**经常在用**的工具里挑少量候选（编辑器插件、命令行工具、库都可以）；
- 筛选：近期仍有维护迹象、issue/PR 有真实回应、贡献规则能找到；
- 检查点：你能在本地把它跑起来并复现一个正常流程吗？
- 产出：一个主选 + 一个备选。

## Step 1 · 找切入点：优先小而独立的问题

- 动作：读 CONTRIBUTING、看若干最近合并的 PR，理解维护者接受什么粒度和写法、翻 `good first issue` 与文档 issue；
- 更好的做法：记录自己使用中遇到的困惑（文档说不清、示例跑不通、报错信息不清楚）；
- 检查点：这个改动是否**小且独立**（能被一次说清）？
- 失败分支：找不到小改动 → 换项目；不要硬做大功能；
- 产出：一个具体待办（一句话能描述）。

## Step 2 · 先讨论：是否需要等待取决于项目活跃度

- 动作：搜是否已有相关 issue → 没有就开一个（最小复现 + 期望 + 实际）→ 说明打算修并问方向；
- 检查点：维护者或其他人有回应吗？没有回应也可以继续，但要按最小改动做；
- 失败分支：被告知方向不对或已有计划 → 换问题，别硬推；
- 产出：issue 链接。

## Step 3 · 写测试再修

- 动作：先加一个失败测试证明缺陷存在 → 改代码 → 让测试通过 → 跑全量测试；
- 检查点：本地全量测试通过吗？
- 产出：代码改动 + 测试。

## Step 4 · 提 PR

- 动作：标题写清问题；描述写「改了什么 / 为什么 / 怎么验证」；关联 issue；一个 PR 只做一件事；
- 检查点：diff 里有没有无关改动（格式、重命名）？有就拆出去；
- 产出：PR 链接。

## Step 5 · 过评审：按项目节奏等待和回应

- 动作：CI 失败先自己修；评审意见逐条回应；被要求改的照改或说明理由；
- 检查点：每条意见是否都有回应（改了什么 / 为什么没改）？
- 失败分支：被关闭 → 问一句「如果我要做这件事，应该怎么改」，把它用在下一个贡献上；
- 产出：合并记录。

## 停止条件

- 已被合并 → 可以开始第二个改动（同一个项目持续贡献价值更大）；
- PR 长时间无回应且仓库本身也缺少维护迹象 → 礼貌提醒一次；仍无回应就把它视为维护状态信息，转向其他贡献；
- 如果多次被关闭且理由相似 → 先停下来研究已合并 PR 和贡献规则，确认自己是不是反复犯同一种流程错误。

## 贡献之后

把合并记录写进简历（项目名 + PR 数 + 每个改动解决了什么）；把这次评审里学到的规范用在下一个项目。
