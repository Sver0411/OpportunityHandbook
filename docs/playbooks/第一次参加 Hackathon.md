# Playbook：第一次参加 Hackathon

## Before：会前把规则、队伍和环境准备好

- 动作：
  1. 组队：人数服从赛事规则，优先保证技能互补和可投入时间一致；
  2. 读规则：评分项、提交要求、是否允许预制代码（多数允许使用库，但禁止预制作品）；
  3. 准备少量能在赛事规定时间内做出闭环的题目，优先选择能演示核心价值的问题，不要一开始就做“大平台”；
  4. 准备环境：账号、依赖、网络、备用热点。
- 检查点：赛期最后一天全员可用吗？
- 产出：选题范围 + 分工表。

## Kickoff：尽快把赛题压缩成可演示闭环

- 动作：把题目翻译成一句话问题 + 一个能演示的闭环；明确「不做什么」；
- 检查点：全员对范围达成一致了吗（复述一遍）？
- 产出：范围卡（写在共享文档里）。

## 赛期节奏

不要按固定百分比分配所有比赛，而是守住四个阶段门：

| 阶段门 | 进入下一阶段前必须满足 |
| --- | --- |
| 闭环 | 核心输入到输出已经能跑通并演示 |
| 证据 | 有真实数据、用户反馈或评测结果，而不只是功能 |
| 打磨 | 核心路径稳定，开始收敛演示、文案和答辩 |
| 冻结 | 不再加高风险功能，只修影响提交与演示的问题 |

- 纪律：主分支随时可演示；提交前留出缓冲；
- 产出：可运行原型 + 演示材料。

## 演示脚本

以赛事官方时限为准。无论时限长短，都优先保证：问题足够短 → 尽早进入现场演示 → 用证据说明结果 → 最后交代差异化与限制。准备一个兜底录屏，避免现场环境把全部成果归零。

## After：趁决策与失败细节还记得时尽快整理

- 动作：归档代码与演示；写一页复盘；把原型整理成作品集条目；
- 检查点：我的产出能让别人复现吗？
- 产出：作品集条目 + 复盘。

## Stop condition

- 主流程在中期检查点仍跑不通 → 砍范围，保住最小闭环；
- 队友中途失联 → 立刻重排范围，不要等；
- 连续熬夜影响演示状态 → 强制休息，演示质量优先。
