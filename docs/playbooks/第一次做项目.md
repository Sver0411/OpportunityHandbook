# Playbook：第一次做项目

打开这份手册时你要做的事：在一个你能持续投入的可控周期内，做出一个能被展示、测试和解释的项目。每一步用**动作、检查点、失败分支、产出**判断是否继续，而不是按固定周数推进。

## Step 0 · 准备：先确认真实可投入时间

- 动作：确定每周可投入时间（如实写，别写理想值），准备一个笔记本记录决定；
- 检查点：这个投入强度能否持续，而不是只靠一两次突击？
- 产出：时间承诺 + 一个空白决策记录。

## Step 1 · 选题：直到问题足够具体

- 动作：写出三个「谁在什么场景下有什么麻烦」，选一个你**自己就是用户**的；写一句话问题陈述；
- 检查点：能否说清「谁、什么问题、现在怎么凑合」？有没有用真实使用者、真实数据或自己的持续使用验证这个问题确实存在？
- 失败分支：如果反复验证仍找不到真实问题、使用场景或可观察后果 → 换题，并记录为什么换；
- 产出：一句话问题陈述 + 一份「不做什么」清单。

## Step 2 · 范围与里程碑：先把最小闭环写清

- 动作：把「第一版完整走通」定义成「输入 → 处理 → 输出 → 有人看到」；设两到三个里程碑；
- 检查点：每个里程碑能否「运行 / 演示 / 评审」？
- 失败分支：里程碑反复推迟且没有新增关键信息 → 先砍功能，不要无限延后；
- 产出：里程碑清单（含日期）。

## Step 3 · 实现：持续保持可演示状态

- 动作：先做能闭环的最土版本；频繁保持「能给别人看的状态」，不要等所有功能做完才第一次集成；
- 检查点：现在能不能跑一次完整流程给别人看？
- 失败分支：卡在某个技术点很久、且继续投入已经不再产生新信息 → 换替代方案（手工、现成库、换数据源）；
- 产出：可运行的版本 + 每周进展记录。

## Step 4 · 测试与测量：从“能跑”变成“有证据”

- 动作：列输入表（正常/边界/异常）；写核心流程的自动检查；定一个指标并记录；
- 检查点：换台机器／换个人，能跑出同样结果吗？
- 失败分支：完全测不了 → 至少写清「已知在什么条件下会失败」；
- 产出：测试记录 + 指标数字 + 限制清单。见 [工程项目的测试、指标与证据](../projects/测试与指标体系.md)。

## Step 5 · 文档与 Demo：让陌生人能理解和复现

- 动作：写 README（问题、安装、用法、限制）；录一段两三分钟的演示；
- 检查点：陌生人照着 README 第一次能成功吗？
- 产出：README + Demo 链接或录屏。检查表见 [README 检查表](../tools/README检查表.md)。

## Step 6 · 发布与复用：把项目变成可带走的资产

- 动作：打版本、写变更；把过程整理成一页案例（问题—动作—结果）；
- 检查点：简历上那一行能被追问三层吗？
- 产出：一页作品案例 + 简历 bullet。

## 什么时候停下来

- 连续多个检查点都没有任何可展示的进展 → 复盘范围和技术路线，而不是单纯加时间；
- 项目已经能回答最初的问题 → 停下来测量，而不是继续加功能；
- 你发现自己在为了「看起来完整」而加功能 → 立即冻结范围。

## 最终产出清单

一句话问题陈述 · 不做什么清单 · 里程碑记录 · 可运行版本 · 测试与指标 · README · Demo · 一页案例。
