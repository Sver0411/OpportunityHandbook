# 项目与作品手册

项目与作品的区别只有一个：**作品是别人可以看、可以用、可以验证的东西**。这一页讲清楚一个项目从想法走到作品的全过程，以及每一段最常见的失败点。

## 什么才算作品

判断标准有四条，缺一条就会被打折：

1. **有真实问题**——解决的是你或某群人的实际麻烦，不是「练手」；
2. **能被使用**——有人（哪怕只有你自己）真的在用它，持续一段时间；
3. **能被验证**——有 README、演示、测试结果或数据记录，别人不用问你就知道它做了什么；
4. **能被维护**——出问题你知道怎么修，或者明确写了已知限制。

只有前两条是「项目」，四条齐了才是「作品」。相关判断见 [什么才算真正的项目](../../book/03-开始积累真正能留下来的经历.md#project-what-is-real)。

## 现实中一个项目的完整路径

以「一个物联网方向的学生把课程 Demo 变成作品」为例，每一层都对应一种能力：

```
传感器读数 Demo（读过数据，会用库）
→ 数据持久化（存起来，考虑断连与重复）
→ 异常检测（定义什么算异常，处理误报）
→ 长时间真实运行（连续跑 30 天，记录丢包/功耗/重启）
→ 让其他人复现（写清接线、依赖、运行步骤）
→ 产出 README + 演示 + 测试结果 + 真实使用记录
```

**关键转折点在第三层之后**：大多数人的项目停在「功能能跑」，而作品从这里开始才是「在真实条件下可用」。每往上一层，能讲的判断与取舍就多一层——这也是面试官真正想听的部分。

## 从选题到第一版

- **选题**：列出你每周重复做、又觉得麻烦的三件事，挑一件能用程序或流程解决的。第一版限制在两周内能用，功能只留最核心的三个；
- **不要从技术出发**：先想清「谁在什么场景下会遇到什么问题」，再决定用什么技术。反过来做出来的东西往往没人用；
- **先做「能跑通的最小闭环」**：输入 → 处理 → 输出 → 反馈，每一环都可以很粗糙，但必须都在。

## 让它变成作品：四件必做的小事

1. **README**：一段话说清它解决什么、给谁用、怎么跑起来、已知限制。写不出来通常意味着你自己也没完全想清楚；
2. **演示**：一张截图、一段 30 秒录屏或一个可访问的线上地址。评审与面试官不会替你安装环境；
3. **证据**：测试结果、性能数据、用户反馈、运行日志。**带口径的数字比形容词有力得多**；
4. **记录决策**：为什么选这个方案、放弃了什么。这部分内容在面试中的价值往往高于代码本身。

## 团队项目：分工与归属

多人项目要在开始就说清三件事：每人的负责模块、接口约定（数据格式/API/文件结构）、贡献怎么记录（提交记录、文档署名）。**归属清晰的项目才能在简历与面试里讲得理直气壮**，见 [项目经历怎么写](../../book/05-从学校走向第一份工作.md#resume-projects)。

## 作品集怎么组织

- **数量不追求多**：两到三个打磨完整的项目，比十个半成品更有说服力；
- **每个项目一页**：问题、你的角色、关键技术决策、结果（带数字）、链接；
- **顺序按目标调整**：投研发岗把技术深度放前面，投产品岗把问题定义与用户反馈放前面；
- **可访问性检查**：链接是否失效、仓库是否可克隆、演示是否还能跑。**每年至少检查一次**。

模板与写法见 [作品集](../../book/05-从学校走向第一份工作.md#resume-portfolio)。

## 常见失败方式

| 失败方式 | 表现 | 处理 |
| --- | --- | --- |
| 功能膨胀 | 想做的东西越来越多，一年没上线 | 砍到两周能用，先发布再迭代 |
| 技术炫技 | 用了很新的技术，但没人用 | 回到问题：谁需要它？ |
| 烂尾 | 卡在一个非核心问题上放弃 | 记录卡点，换最笨的办法先把它贯通 |
| 不维护 | 上线后再没更新，链接失效 | 明确写下「已停止维护」或每季度修一次 |
| 无证据 | 做得不错但说不清结果 | 补测试、补数据、补使用记录 |

## 与其他路径的关系

- **竞赛**：竞赛是限时项目，产出可以并入作品集（见 [竞赛手册](竞赛手册.md)）；
- **开源**：把项目开源是最直接的公开证据，也是找同行的方式（见 [开源手册](开源手册.md)）；
- **实习与求职**：作品是「能做什么」的证据，实习是「在真实组织里做过什么」的证据，两者互补。
