# 开源手册

开源不是「把代码传上 GitHub」就结束了——它是一套**公开协作的规则与社交系统**：有人维护、有人评审、有人提问题、有人做文档。理解这套规则，你才能既拿到它的好处，也不在里面踩坑。

## 开源世界的四种角色

| 角色 | 做什么 | 门槛 | 常见产出 |
| --- | --- | --- | --- |
| 使用者（User） | 用项目、提出问题 | 最低 | issue、使用反馈 |
| 贡献者（Contributor） | 修 bug、写文档、补测试 | 中等 | 被合并的 PR |
| 审查者（Reviewer） | 评审他人 PR、把关质量 | 较高 | 评审记录 |
| 维护者（Maintainer） | 决定路线、发布版本、处理冲突 | 高，靠长期投入换来 | 发布版本、治理文档 |

**大多数人的路径是从使用者到贡献者**，而不是直接承诺「我要维护一个项目」。

## 第一个贡献该怎么做

1. 从**你每天在用的库**里找问题——你懂它的使用场景，比随机挑一个仓库更容易坚持；
2. 先读 `CONTRIBUTING.md` 与 issue 模板：**不按格式提交的 PR 常被直接关闭**；
3. 从最小的改动开始：文档错别字、示例代码、边界条件测试，比新功能更容易被接受；
4. 提 PR 前自查：改动是否只做了一件事、有没有加测试、有没有破坏向后兼容、commit message 是否说清动机；
5. 被要求修改是正常的，评审意见不是针对人。

## 现实中一个 PR 会经历什么

```
fork 或新建分支
→ 写改动 + 测试
→ 提交 PR（描述里写清：解决什么问题、怎么验证）
→ 自动检查（CI、lint、覆盖率）可能失败，需要修
→ 维护者评审，可能要求拆分或改设计
→ 反复修改（几天到几周不等）
→ 合并，或被认为「不在范围内」而关闭
```

时间成本主要在**等待与返工**，而不是写代码。接受这一点，就会把「写好描述 + 一次只改一件事」当成主要技巧。

## 什么算好的贡献记录

- 提交本身能被追溯（PR 链接、合并记录）；
- 改动有说明与测试；
- 有持续参与（而不是一次性提交十个错别字就消失）；
- 能讲清一次「有分歧的技术讨论」——这是面试里最有说服力的部分。

## 许可证与法律边界

- 使用别人的代码前看清许可证（MIT、Apache-2.0、GPL 等的义务不同）；
- 公司内部项目引入开源组件要经过合规确认；**在工作时间与设备上给开源项目提交代码前，先确认劳动合同与公司政策**；
- 自己开源时选择一个明确的许可证，并写清贡献与行为准则；不确定时选被广泛使用的宽松许可证（如 MIT / Apache-2.0）通常风险更低；
- 涉及用户数据、模型权重、素材时，注意授权范围（很多「开放」数据集并不允许再分发）。

## 维护一个项目要面对什么

- **问题积压**：issue 永远多于你能处理的数量，需要明确「不打算做」的清单；
- **破坏性改动的沟通**：版本语义（semver）与弃用周期是基本礼貌；
- **安全与依赖**：依赖有漏洞时要评估影响并发布修复；
- **精力与退出**：明确写出维护状态（活跃 / 仅修安全漏洞 / 已归档），**允许自己把项目归档**，比放着不管更负责。

## 什么时候值得开源、什么时候不值得

- 值得：希望被复用、想建立公开记录、项目本身与社区生态相关、愿意长期回应问题；
- 不值得：包含公司或他人受限代码、含个人隐私数据、你完全没有时间回应 issue（可以先「开源但明确不接受支持请求」）。
