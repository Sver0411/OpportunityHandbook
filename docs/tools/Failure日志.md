# Failure Log

用途：把「踩过的坑」变成可复用的经验。它与提交记录不同——记录的是**判断过程**。

## 模板

| 字段 | 内容 |
| --- | --- |
| 日期与场景 | 何时、在做什么 |
| 现象 | 具体表现（报错原文、异常行为） |
| 影响 | 影响了谁、损失多少（时间/数据/用户） |
| 定位过程 | 试过什么、排除过什么、关键证据 |
| 根因 | 为什么发生（不是「哪里报错」） |
| 修复 | 改了什么 |
| 预防 | 加了什么检查/日志/测试，避免重复 |

## 示例

| 字段 | 内容 |
| --- | --- |
| 现象 | 定时任务偶发 `FileNotFoundError`，手动执行不报错 |
| 定位 | 打印工作目录 → 定时环境下为 `/`，与手动执行不同 |
| 根因 | 代码使用相对路径读取配置文件 |
| 修复 | 改为基于脚本位置的绝对路径 |
| 预防 | 启动日志输出当前工作目录；补一条「路径解析」单元测试 |

## 三条纪律

1. **当天记**：拖两天只剩「好像出过一个问题」；
2. **写根因不写现象**：「工作目录不同」才是根因；
3. **预防栏必须落成具体动作**（一条日志、一个测试、一行校验）。

## 什么时候回看

- 每季度扫一遍：哪些根因重复出现？重复的那类应该变成规范；
- 面试准备时回看：失败案例是项目面试的必备素材（见 [项目面试](../job-search/项目面试.md)）。
