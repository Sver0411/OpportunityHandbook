# PR 检查表

提交前逐项打勾。**目标是让对方一次就能判断能不能合并。**

## 五项自查

- [ ] **范围**：这个 PR 只做一件事？没有夹带格式化、重命名或无关重构？
- [ ] **测试**：新增/修改的行为有对应测试？先确认过测试在修复前会失败？
- [ ] **文档**：影响使用方式的改动，README / 文档 / 变更日志同步更新了吗？
- [ ] **描述**：写清了「改了什么、为什么、怎么验证」？关联了 issue 编号？
- [ ] **本地验证**：本地全量测试通过？CI 失败是否已自查？

## 描述模板

```
修复 #1234：<一句话问题>

改了什么：
为什么：
怎么验证：
影响范围：
```

## 提交后的三步

1. CI 失败 → 先自己看日志修复，不等维护者指出；
2. 收到评审意见 → 逐条回应（改了什么 / 为什么保持原状），并在原 PR 上更新；
3. 合并后 → 记录到自己的贡献清单。

## 常见被要求修改的原因

| 原因 | 预防 |
| --- | --- |
| 改动太大 | 拆成多个 PR |
| 没有测试 | 先写失败测试 |
| 描述不清 | 用上面的模板 |
| 风格不一致 | 读最近合并的 PR |
| 忘记更新文档 | 把文档列入检查项 |

## 「只做一件事」怎么判断

自问一句：**如果只保留其中一半改动，另一半还需要一起上吗？** 不需要的话，它们本来就是两件事。

常见的夹带：顺手格式化整个文件、重命名不相关的变量、升级依赖、修一个顺手看到的 bug。这些改动本身没错，但会让评审变成解谜——对方要在几百行里找出真正想改的那三行。

拆分方法：

- 先提「基础 PR」（重构、补测试、不改变行为），合并后再提「功能 PR」；
- 格式化单独一次提交，描述里写明「仅格式化，不含逻辑改动」；
- 依赖升级单独提，因为它失败时回滚范围最小。

例外：一次改动如果不放在一起就无法通过测试，那就一起提，并在描述里说明为什么不能拆。

## 评审意见分歧时

不是所有意见都必须接受。先分清三种：

- **事实问题**（这里是 bug、这个 API 会抛异常）：直接改；
- **风格问题**（命名、写法偏好）：项目有 lint 或风格文档就照它做；没有就按维护者的习惯来，不值得坚持；
- **设计分歧**（该不该这么做）：把你的理由写清楚——约束是什么、考虑过哪些方案、为什么选这个。对方坚持时，多半是他知道你不知道的历史原因，先问「当初为什么这么设计」比继续论证更有效。

如果讨论三轮仍不收敛，请另一位维护者判断，或者把方案缩小到只解决当前这个问题。**在别人的项目里，一致性比你的偏好重要。**
