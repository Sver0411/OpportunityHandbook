# JD 拆解表

用途：把「看 JD」变成可比较的数据。用法：每份 JD 填一张单表；攒够 8–15 份后填汇总表。

## 单份 JD 拆解

| 项目 | 内容 |
| --- | --- |
| 公司 / 岗位 / 城市 | |
| 来源与日期 | |
| 职责（每天做什么） | 1. 2. 3. |
| 硬性要求 | 学历 / 专业 / 年限 / 必会技术 |
| 优先与加分 | |
| 关键词（可对齐简历的名词） | |
| 隐藏信号 | 团队阶段、业务方向、技术栈迁移、值班与节奏 |
| 我的差距 | 每条要求 → 具备 / 部分 / 没有 |
| 准备优先级 | 差距最大且可短期补齐的前三项 |

## 多份 JD 汇总

| 要求 | 出现次数 | 占比 | 我的状态 | 补齐方式 | 期限 |
| --- | --- | --- | --- | --- | --- |
| 例：熟悉 MySQL | 12/15 | 80% | 部分 | 做一个含索引优化的项目 | 4 周 |
| 例：熟悉 Redis | 6/15 | 40% | 没有 | 小项目加缓存层 | 6 周 |
| 例：分布式基础 | 6/15 | 40% | 没有 | 读概念 + 复现一个场景 | 8 周 |

## 判读规则

- 出现率 ≥ 60%：行业共识，尽量补齐；
- 20%–60%：竞争维度，能补就补；
- < 20%：通常是公司特殊要求，先不管。

## 常见误用

- 只用一份 JD 就改简历；
- 把加分项当硬门槛，提前自我淘汰；
- 统计了很多份却不动手补差距。

## JD 本身不可靠的三种信号

JD 是招聘方写的广告，不是岗位说明书。拆之前先判断它值不值得拆：

- **要求离谱**：三年经验要求精通六项技术栈——通常说明没想清楚要什么人，投了大概率收到「不合适」；
- **职责与要求对不上**：写着「负责业务增长」，要求却是「精通 C++」——实际可能在做内部工具；
- **挂了很久**：同一个岗位挂了大半年，可能是在做人才储备，不是真实招聘。

判断方法：把它和其他公司的同岗位 JD 放一起比。**只在一份 JD 里出现的诡异要求，不要拿它来否定自己。**

## 拆完之后怎么落到简历

统计出高频要求后，按这个顺序改：

1. **对齐关键词**：出现率 ≥ 60% 的行业共识词，要在你简历里以同样说法出现——不少筛选是按关键词做的；
2. **给每条要求配一条证据**：要求「熟悉 MySQL 索引优化」，简历里就得有对应的项目与结果，不能只写「熟悉」；
3. **把最相关的经历前置**：同一段经历，按岗位调整描述重点，而不是用一份简历投所有岗位。

**不要为了对齐 JD 而编造经历。** 拆解的目的是让真实的经历被看见，不是虚构不存在的东西——面试追问两层就会暴露。
