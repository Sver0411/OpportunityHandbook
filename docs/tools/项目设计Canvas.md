# 项目设计 Canvas

用途：在写代码之前把项目想清楚，一页写完。写不满说明还没想好；写不下的说明范围太大。

## 一页模板

```
问题（一句话）
  谁，在什么场景下，遇到什么问题，现在怎么凑合：

不做（明确排除）
  · 不做多用户
  · 不做移动端
  · 不处理历史数据

第一版「完整走通」的定义
  输入 → 处理 → 输出 → 谁看到结果：

会留下的证据
  · 可访问地址 / 录屏
  · 指标与口径：
  · 真实使用（谁、多久）：

风险与替代
  最大风险：            替代方案：
  次大风险：            替代方案：

里程碑（含日期）
  M1（能跑通）：
  M2（能演示）：
  M3（能交付）：

停止条件
  · 连续两周无可展示进展 → 砍范围
  · 已能回答最初问题 → 停止加功能，转测量
```

## 填写要点

- 「问题」一栏必须能说出「现在怎么凑合」——说不出说明需求不真实；
- 「不做」至少写三条，否则范围没有边界；
- 「证据」一栏先写再做事，因为证据形态决定实现取舍（见 [项目类型专项](../projects/项目类型专项.md)）；
- 里程碑不要超过三个，每个都要能「演示」。

## 什么时候更新它

- 每次要加新功能前：先看它属于哪个里程碑，还是应该进入下一版；
- 每次里程碑到期：写三行进展（做完什么、没做完什么、砍什么）。

配套：[项目测试计划模板](项目测试计划.md)、[Playbook：第一次做项目](../playbooks/第一次做项目.md)。

## 示例：一页填好的 Canvas

```
问题（一句话）
  我们班每学期要在三个平台核对作业截止时间，我上个月漏交过一次实验报告。

不做（明确排除）
  · 不做多用户与登录
  · 不做移动端 App（先用网页 + 邮件提醒）
  · 不处理历史学期数据

第一版「完整走通」的定义
  手工录入 CSV → 脚本合并去重 → 输出一份 Markdown 清单 → 邮件发给自己
  （全程 5 分钟内完成，结果可核对）

会留下的证据
  · 三个数字：手工耗时（15 分钟/周 → 2 分钟）、漏交次数（1 → 0）、脚本 1.3 秒
  · 两位同学试用两周的反馈记录
  · README 与限制说明（只支持一个平台导出）

风险与替代
  最大风险：三个平台导出格式不同 → 替代：先只支持 iCal，其余手工录
  次大风险：提醒邮件被当垃圾邮件 → 替代：先只在本机生成清单

里程碑（含日期）
  M1（10-12）：能跑通 CSV → 清单
  M2（10-19）：接入 iCal + 去重
  M3（10-26）：邮件提醒 + README

停止条件
  · 连续两周没有可展示进展 → 砍范围到 M1
  · 已能回答最初问题 → 停止加功能，转测量
```
