# 一份 JD 到底怎么拆

JD 不是招聘广告，是一份**筛选标准的公开版本**。拆 JD 的目的不是「看懂它」，而是产出四样东西：岗位画像、技能矩阵、简历关键词、准备优先级。

## 以一份典型 JD 为例

> **岗位：后端开发工程师（校招）**
> 职责：参与业务系统的服务端设计与开发；参与性能优化与稳定性建设；与产品、前端、测试协作完成需求交付。
> 要求：本科及以上，计算机相关专业；熟悉 Java 或 Go；熟悉 MySQL、Redis；了解分布式系统基本概念；有良好的沟通与协作能力。
> 加分：有高并发项目经验；熟悉消息队列；有开源贡献；有大厂实习经历。

### 第一层：职责（你每天会做什么）

「参与服务端设计与开发 + 性能优化 + 稳定性建设 + 跨岗协作」——四个动作，说明这个岗位不是纯写业务逻辑，还有运维性工作。**职责描述决定你入职后的日常，比要求更重要**。

### 第二层：硬性要求（不满足大概率不进流程）

「本科及以上」「计算机相关」是门槛；「熟悉 Java 或 Go」是技术栈门槛（注意是「或」）；「熟悉 MySQL、Redis」是必备工具。

判断方法：把每条标注为 **必须 / 优先 / 加分**。写「熟悉」「掌握」而没写「精通」的，通常指「用过、能独立完成任务」。

### 第三层：偏好与 wishlist

「了解分布式系统基本概念」是软性门槛（知道 CAP、一致性、幂等就算过线）；加分项里出现「高并发」「消息队列」「开源」「实习」——这些是**竞争对手的配置**，不是你必须有，但决定你在排序里的位置。

### 第四层：隐藏信号

- 团队规模与成熟度：写「参与建设」说明团队还在搭建期；
- 业务方向：JD 里没写业务，说明业务可能不重要或不便写；
- 技术栈切换：写明「Java 或 Go」说明团队内部可能正在迁移；
- 加班与节奏：写「稳定性建设」「值班」暗示有 on-call。

### 第五层：关键词（用于简历）

把名词抄下来：Java/Go、MySQL、Redis、分布式、消息队列、性能优化、稳定性、跨部门协作。简历里**出现了相同词汇**，才更容易被筛简历的人（人或者系统）匹配上。注意：写进简历的前提是你真的做过。

## 从一份 JD 到四份产出

| 产出 | 内容 |
| --- | --- |
| 岗位画像 | 每天做什么、在什么团队、技术栈、节奏猜测 |
| 技能矩阵 | 每条要求 → 我的现状（具备/部分/没有）+ 证据 |
| 简历关键词 | 我真实具备、且 JD 出现过的词 |
| 准备优先级 | 差距最大且可短期补齐的前三件事 |

## 多份 JD 一起看才有信息量

单份 JD 只能看到一家公司的偏好。收 8–15 份同类岗位 JD，做两件事：统计高频要求（出现 5 次以上的就是行业共识）、标出只出现一次的（通常是这家公司的特殊要求）。统计表见 [JD 拆解表](../tools/JD拆解表.md)。

## 常见误读

- 把加分项当成硬门槛，自我否定；
- 把「熟悉」理解成「精通」，面试被追问三层就崩；
- 只看要求不看职责，入职后才发现工作内容与预期不符；
- 只投一份 JD 就开始改简历，结果是「什么岗位都能投但都不够匹配」。

## 自检

- 我能说出这个岗位每天做什么吗？
- 硬性要求里，我缺哪一条？是短期能补的吗？
- 我的简历里出现了几条 JD 关键词？每条都有证据吗？
