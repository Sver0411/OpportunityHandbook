# 一份 JD 到底怎么拆

JD 不是岗位真相，它是公司公开给候选人的一层描述。拆 JD 的目标不是猜公司内部发生了什么，而是产出五样东西：**岗位画像、硬门槛、技能差距、简历证据、需要在面试里核实的问题**。

## 先把一份 JD 分成三类信息

以一个典型后端校招岗位为例：

> 职责：参与业务系统的服务端设计与开发；参与性能优化与稳定性建设；与产品、前端、测试协作完成需求交付。  
> 要求：本科及以上，计算机相关专业；熟悉 Java 或 Go；熟悉 MySQL、Redis；了解分布式系统基本概念。  
> 加分：有高并发项目经验；熟悉消息队列；有开源贡献或相关实习。

第一类是**可以直接相信的明示信息**：学历要求、技术栈、职责范围、工作地点、经验年限。它们可以直接进入你的筛选表。

第二类是**招聘偏好**：例如高并发、消息队列、开源、实习。它们会影响竞争力，但通常不等于“没有就不能投”。

第三类是**只能形成假设、必须继续核实的信息**。例如“稳定性建设”可能意味着会处理线上故障，但不能直接推出一定有 on-call；“Java 或 Go”可能是多团队共用一份 JD，也可能是技术栈正在迁移。正确动作不是下结论，而是把它改写成面试问题。

## 从措辞生成问题，而不是生成事实

看到这些词时，可以这样处理：

| JD 表述 | 不要直接推断 | 更好的核实问题 |
| --- | --- | --- |
| 稳定性建设 | “一定要值班” | 这个岗位是否参与线上故障响应或值班？频率如何？ |
| Java 或 Go | “团队正在迁移 Go” | 团队当前主要使用哪种语言？新项目和存量项目分别是什么？ |
| 参与平台建设 | “团队还在从零搭建” | 目前平台已经到什么阶段？新人通常负责新建还是维护？ |
| 快速迭代 | “一定高强度加班” | 一个典型迭代周期多长？需求变化通常如何处理？ |
| 跨团队协作 | “会议很多” | 主要协作对象是谁？这个岗位拥有哪部分决策权？ |

**JD 能告诉你要问什么，但不能替你回答。**

## 硬门槛、核心能力和偏好要分开

不要只按“必须 / 加分”两个框分类。更实用的是四层：

1. **资格门槛**：学历、专业、资格证、地点、签证、经验年限；
2. **入职就要能用的能力**：主力语言、数据库、设计工具、行业知识；
3. **可以入职后补的能力**：某个框架、内部平台、具体业务知识；
4. **排序偏好**：实习、比赛、开源、特定行业经历。

当你不确定某条属于哪一层时，去看同类岗位，而不是凭一个词判断。

## 多份 JD 怎么一起看

单份 JD 只代表一家公司的一个招聘文本。收集多份同类、同级别岗位，直到新增 JD 已经很少带来新的核心要求，然后做两件事：

- 按出现比例排序，识别高频技能；
- 单独标出只在少数公司出现的特殊要求。

这里的频率只是**你的样本内信号**，不能直接叫“行业共识”。样本如果来自同一家公司、同一城市或同一平台，也会有偏差。

配套工具：[JD 拆解表](../tools/JD拆解表.md) 与 [技能 Gap 矩阵](../tools/技能Gap矩阵.md)。

## 把 JD 变成自己的准备清单

假设你整理出的高频要求是：Java、SQL、缓存、分布式基础、测试与线上问题排查。

不要得到“我要学 Java / Redis / 分布式”这种大目标。继续追问每项的**可验证证据**：

- Java：能独立完成一个服务并解释并发、异常和资源管理；
- SQL：能解释索引为什么生效或失效，并做一次真实慢查询优化；
- 缓存：不仅“用过 Redis”，还要能解释一致性、失效和为什么需要缓存；
- 分布式：能用真实场景解释幂等、重试、超时和一致性；
- 排查：能讲清一次问题如何从现象缩到根因。

最后你的准备计划应该长成“补什么证据”，而不是“看什么课”。

## 简历匹配不是关键词堆砌

JD 里的词可以帮助你使用招聘方熟悉的语言，但前提是你确实做过。更好的写法是把关键词嵌进证据：

差：
> 熟悉 Redis、MySQL、分布式系统。

好：
> 为接口增加 Redis 缓存并处理失效策略；通过索引与查询改写降低数据库慢查询；对重复请求加入幂等校验并记录失败重试。

后者既包含关键词，也能被追问。

## 面试前再做一次“事实 / 假设”复核

把你的岗位画像分成两栏：

**已经知道**：来自 JD、官网、书面 Offer、公开技术文章。  
**仍是假设**：团队规模、值班、代码质量、导师机制、晋升速度、业务稳定性。

把第二栏变成反问。这样可以避免最常见的错误：把自己从几句招聘文案里脑补出的公司，当成真实公司。

## 自检

- 哪些是 JD 明确写出的事实，哪些只是我的猜测？
- 我缺的是资格门槛，还是可以短期补齐的能力？
- 每个“我会”的技能有没有项目、代码、报告或经历能证明？
- 我已经准备好哪些问题去验证团队和工作方式？
- 多份 JD 的统计是不是来自足够相似的岗位，而不是混在一起？
