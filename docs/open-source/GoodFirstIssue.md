# 怎么找 Good First Issue（以及为什么常常找不到）

`good first issue` 是一个善意但不可靠的标签：很多被标注的问题实际上需要读大量代码，或者早就有人在处理。

## 标签为什么不可靠

- 标注后长期无人跟进，问题已经过时或已被他人修复；
- 维护者的「简单」与你的「简单」标准不同；
- 有些问题看似独立，实际牵涉架构改动。

所以**不要只靠标签**。

## 更可靠的三个入口

1. **文档与示例**：错字、过期命令、跑不通的示例。影响清晰、评审快，是最稳的入门；
2. **测试**：边界条件缺测试、失败用例缺失。维护者通常欢迎；
3. **你自己的使用问题**：你在用的时候遇到的困惑，往往没人报过——这类问题最容易得到回应。

## 怎么筛一个项目

| 判断项 | 看什么 |
| --- | --- |
| 是否活跃 | 最近三个月有提交、issue 有回复 |
| 是否规范 | 有 CONTRIBUTING、issue 模板、CI |
| 是否对新人友好 | 有已合并的外部贡献者 PR；有「help wanted」类标签 |
| 是否与你的领域相关 | 你至少能读懂一半代码，或有明确的学习意愿 |

## 找 issue 的具体做法

- 在 issue 列表里按更新时间排序，看**最近两周有维护者回复**的；
- 读三位已合并 PR 的 diff，感受这个项目的改动粒度；
- 关注「文档」「测试」「DX（开发者体验）」类标签；
- 直接搜你使用中的报错信息，看是否有人提过。

## 找不到合适的怎么办

换项目。**在错误的地方坚持，是最常见的沉没成本**。判断标准：连续两周找不到一个能在一周内完成的小改动，就换。

## 找到之后

先在 issue 下留言说明打算做（避免撞车），再按 [第一次 PR：从发现到合并](第一个PR.md) 的流程走。

## 自检

- 我选的项目最近三个月有人合并外部 PR 吗？
- 这个改动我能在一周内做完吗？
- 我在 issue 下说过我要做吗？
