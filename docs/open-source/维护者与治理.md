# Maintainer、Release 与项目治理

从贡献者到维护者不是荣誉，是**接下一份长期责任**。

## 维护者每天在做什么

- 处理 issue：分类、复现、判断优先级；
- 评审 PR：读 diff、要求补测试、决定合并；
- 发布：打版本、写变更日志、处理兼容问题；
- 沟通：拒绝不合理的需求、调解分歧；
- 维护基础设施：CI、依赖升级、安全更新。

时间成本通常远超预期——「维护者倦怠」是社区公开话题。

## 发布流程的关键概念

- **语义化版本（MAJOR.MINOR.PATCH）**：不兼容的改动升 MAJOR，向后兼容的新功能升 MINOR，修缺陷升 PATCH。它是一份**对使用者的承诺**；
- **变更日志（Changelog）**：面向使用者的说明，按「新增 / 修复 / 破坏性变更」分类，写清影响与迁移方式；
- **发布检查**：版本号、变更日志、文档更新、打标签、构建产物、公告渠道。

## CI 与质量门槛

常见的自动门槛：构建、单元与集成测试、格式检查、依赖安全扫描。CI 失败先自己修，不要等维护者指出——这是贡献者的基本功。

## 许可证与治理

- **许可证**：决定别人能怎么用你的代码。常见的有宽松型（MIT、Apache-2.0）与传染型（GPL 系列）；选择前看清义务（署名、专利条款、衍生作品要求）；
- **治理文件**：CONTRIBUTING（怎么贡献）、CODE_OF_CONDUCT（行为准则）、GOVERNANCE（决策方式）、SECURITY（漏洞上报）；
- **决策方式**：从「BDFL（作者决策）」到「委员会投票」都有，重要的是写下来，避免争吵。

## 从贡献者到维护者

1. 持续在一个项目贡献（10 个以上被合并的 PR，或长期处理某类 issue）；
2. 主动承担可见的维护工作：修文档、管 issue 列表、复现问题；
3. 被邀请或主动申请时，明确你能投入的时间与权限范围；
4. 建立可持续机制：贡献指南、自动检查、明确决策流程——一个人扛所有事不可持续；
5. 需要退出时明确交接或归档，不要失联。

## 自检

- 如果我是这个项目的维护者，我会愿意合并我自己的 PR 吗？
- 我发布的版本号与变更日志，能让使用者判断要不要升级吗？
- 我有没有把「我怎么做决定」写下来？

## 一次 release 的完整流程（时间线）

某小型开源库 2.4.0 的发布记录：

| 时间 | 动作 | 说明 |
| --- | --- | --- |
| T-14 天 | 冻结新功能，只合并修复 | 在 issue 里公告冻结日期 |
| T-7 天 | 检查待合并 PR：3 个合并、1 个延到下版 | 未合并的都在 PR 里说明原因 |
| T-5 天 | 更新 CHANGELOG：新增 2 项、修复 5 项、破坏性变更为无 | 按「新增/修复/破坏」分类 |
| T-3 天 | 本地跑全量测试 + 一个真实项目回归 | 发现一处兼容问题并修复 |
| T-1 天 | 打标签 `v2.4.0`，构建并上传产物 | 版本号：向后兼容的新功能 → MINOR |
| T 日 | 发布公告（含升级方式与迁移说明） | 明确「无需改动」 |
| T+3 天 | 处理两条回归 issue，补 2.4.1 | PATCH 版本只修缺陷 |

**三条纪律**：变更日志写「使用者要做什么」而不是「我改了什么」；破坏性变更必须升 MAJOR 并给迁移说明；发布后一周盯回归 issue。
