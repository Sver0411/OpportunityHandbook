# 第一次 PR：从发现到合并

PR 是「请求把你的改动合并进项目」。它能不能被合并，取决于三件事：**范围是否合理、描述是否清楚、测试是否齐全**。

## 完整链路（七步）

1. **发现**：自己用的时候遇到问题（比翻 issue 列表更可靠，因为你熟悉场景）；
2. **搜 issue**：确认没有重复，看维护者的偏好；
3. **复现**：写出最小复现，确认问题稳定出现；
4. **开 issue 或先在 issue 下留言**：说明打算修，问方向。项目若要求先讨论，跳过会被直接关闭；
5. **写测试**：先加一个会失败的测试，跑一遍确认它真的失败；
6. **修复**：只改与问题相关的部分，不夹带格式化与重命名；
7. **提 PR**：标题+描述（改了什么/为什么/怎么验证）+关联 issue；随后按评审意见修改，直到合并。

## 一份 PR 描述的骨架

```
修复 #1234：重复键静默覆盖

改了什么：配置加载阶段检测重复键，遇到时抛出与现有校验一致的错误信息。
为什么：当前行为会静默丢失用户的配置，且难以排查。
怎么验证：新增 test_duplicate_key_raises（先失败后通过），本地全量测试通过。
影响范围：仅配置加载路径；不改变现有合法配置的行为。
```

## 评审往返

- CI 失败先自己修，不要等维护者指出；
- 每条意见都回应：改了什么，或说明为什么保持原状；
- 被要求「把无关改动拆出去」时照做——大 diff 是合并的主要阻碍；
- 评审拖几天是常态，一周后可以礼貌 ping 一次。

## 被关闭怎么办

先看理由：方向不对、已有计划、超出范围、缺少测试。然后问一句：**「如果我要做这件事，应该怎么改？」** 把答案用在下一个贡献上。

一次被关闭不等于能力不行，通常说明流程没走对（多数是没先读 CONTRIBUTING 或在 issue 下确认方向）。

## 合并之后

- 记录到自己的贡献清单（项目名、PR 号、解决了什么）；
- 同一个项目继续做第二个改动，价值高于到处撒网；
- 把这次学到的规范（提交信息、测试要求、格式）用在下一个项目。

## 自检

- 我的 PR 只做了一件事吗？
- 描述里有没有「怎么验证」？
- 我读过 CONTRIBUTING 并在 issue 下确认过方向吗？
