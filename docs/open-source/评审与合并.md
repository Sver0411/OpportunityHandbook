# Code Review 怎么做（给与被给）

评审不是找茬，是**在合并前降低风险**。给评审与接评审是同一套能力的两个方向。

## 评审时看什么（按优先级）

1. **正确性**：逻辑是否覆盖了边界与失败路径；
2. **可维护性**：命名、结构、是否有隐藏耦合；
3. **测试**：改动是否有对应测试，测试是否真的会失败；
4. **范围**：有没有夹带无关改动；
5. **风格**：最后看（有自动格式化就不必人工挑）。

## 意见怎么表达

- 对事不对人：写「这里在并发下可能重复扣款」而不是「写得不严谨」；
- 给出**理由与替代方案**，并标明严重程度（建议 / 需要修改 / 阻塞合并）；
- 分清楚「必须改」和「可以更好」，否则对方无法判断优先级；
- 提问式表达：「如果输入为空会怎样？」比「这里有问题」更容易被接受。

## 收到意见怎么回应

- 逐条回应：改了什么、为什么这么改；
- 不认同就说明理由（用场景与数据，不用情绪）；
- 拿不准就问：「你的意思是改成 X 吗？」；
- 改完在原 PR 上更新，不要另开新 PR。

## 什么时候可以不改

如果意见属于风格偏好、且项目没有明确规范，可以说明理由后保持现状。但**要明确回应**，沉默会让 PR 挂着。

## 维护者的时间成本

维护者处理一个 PR 的成本远高于提交者：要读 diff、理解上下文、跑测试、判断影响。降低这个成本的三件事：改动小、描述清楚、测试齐全。见 [第一次 PR：从发现到合并](第一个PR.md)。

## 自检

- 我的评审意见里，有没有一条只说了「不好」而没说怎么做？
- 我提交的 PR 描述里，有没有写清「怎么验证」？
- 收到意见后，我是不是每条都回应了？
