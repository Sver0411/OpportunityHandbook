# 第一个 Issue 怎么写

Issue 的目的不是「报告问题」，而是**让别人能用最小成本复现并判断它是否值得修**。

## 提之前：先搜

搜三处：已关闭的 issue（可能已修）、开放 issue（可能有人在做）、文档与 FAQ（可能是用法问题）。重复提问是最招人烦的一类。

## 一个合格 issue 的五个部分

```
1. 标题：一句话说清现象（不要写「有个 bug」）
   例：配置文件含重复键时静默使用最后一个值，不报错
2. 环境：版本号、操作系统、运行时版本、安装方式
3. 复现步骤：最小可复现的输入与命令（能贴代码就贴代码）
4. 期望结果 vs 实际结果：分别写清楚
5. 影响与频率：偶发还是必现、影响谁
```

## 对照示例

**差**：

> 标题：`程序有问题`
> 内容：`我运行的时候报错了，麻烦看一下。`

**好**：

> 标题：`v2.3.1 在 Windows 下读取含中文路径的配置时抛 UnicodeDecodeError`
> 环境：v2.3.1 / Windows 11 / Python 3.12 / pip 安装
> 复现：新建目录 `测试/`，写入 `config.yaml`（附内容），执行 `tool run --config 测试/config.yaml`
> 期望：正常读取并输出统计
> 实际：抛 `UnicodeDecodeError: 'gbk' codec can't decode...`
> 附加信息：Linux 下同样操作正常；改目录名为英文可绕过

差异在于：第二份**维护者可以照着重现**。

## 最小复现的做法

把触发问题所需的输入缩到最小：删掉无关配置、换更小的数据、去掉中间步骤。很多问题在缩的过程中自己就消失了（说明是用法问题），这比提一个含糊的 issue 更有价值。

## 提问的语气

- 陈述事实，不加评价（避免「这么简单的 bug 都测不出来」）；
- 说明你已经试过什么（排除掉的可能）；
- 如果是用法问题，也说明你读过的文档位置，方便维护者改文档。

## 提完之后

- 关注回复，能补信息就补；
- 被判定为「不是 bug」也是有效结果：记下原因，避免再犯；
- 如果决定自己修，在 issue 下说一声，避免与别人撞车（见 [第一次 PR：从发现到合并](../open-source/第一个PR.md)）。

## 自检

- 别人照我的步骤，第一次就能复现吗？
- 有没有写清期望与实际？
- 我把版本与环境写全了吗？
