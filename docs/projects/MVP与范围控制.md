# MVP 与范围控制

项目烂尾很少是因为技术太难，多数是因为**范围一直在长大**。这一页讲怎么把范围钉住。

## 最小闭环长什么样

最小闭环 = **输入 → 处理 → 输出 → 有人看到**，四段齐全，中间不断。

它和「做一小块」的区别在这里：你可以把界面做得很丑、把后端写成手工脚本、把反馈放在聊天里，但流程必须能从头走到尾。**闭环一旦断了，收到的信号就作废**——没上线的功能等于没有功能。

对照 [MVP](../manuals/创业与自由职业.md) 的常见误解：MVP 不是「做个烂版本」，而是「用最小代价回答一个具体问题」。

## MVP 不等于做得烂

| 可以粗糙 | 不能粗糙 |
| --- | --- |
| 界面样式、文档排版、部署方式 | 核心流程的正确性 |
| 手动处理的部分（先人工代替） | 数据是否被真实保存与可追溯 |
| 只支持一种输入格式 | 出错了有没有提示 |
| 只有一台机器能跑 | 你能不能说明它现在是什么状态 |

分界线是：**粗糙不影响判断，错误会污染判断**。如果粗糙的部分让人看不出结果对不对，那它就不是可以省的地方。

## 哪些功能必须，哪些必须延后

必做（砍掉就无法闭环）：核心流程、最小的数据存储、一次可演示的输出。

常见该延后的：多用户与权限、移动端适配、复杂的设置项、导出格式支持五种、管理后台、通知系统、国际化。

一条实用规则：**新功能必须回答「不加它，这一版的问题还能不能被回答」**。能回答，就延后。

## feature creep 的识别

典型的 creep 迹象：

- 连续几周没有「能给别人看的东西」新增，但代码改动很多；
- 每次讨论都新增需求，没有一次删除需求；
- 你在为「以后可能需要」做设计；
- 里程碑一再后推，且每次推迟的理由都是新加的功能。

## scope freeze 与里程碑

做法很朴素：

1. 把「这一版要做的」写成条目清单，每条能判断做完没做完；
2. 冻结：冻结之后新增的条目一律进入**下一个版本**的清单，不插队；
3. 设两到四个里程碑，每个里程碑要求「能运行 / 能演示 / 能评审」；
4. 每个里程碑后写一页进展：做完了什么、没做完什么、下一段砍什么。

节奏安排参见 [项目管理](../../book/02-在学校里先把基础打好.md#skill-project-management) 里的三类节奏表。

## 继续加功能还是停止

问三个问题：

- 当前这一版能不能回答你最初要回答的问题？能，就先停下来测量；
- 新功能是在补齐闭环，还是在润色细节？润色可以延后；
- 加完这个功能，你能拿到什么新证据？拿不到，就不加。

## 项目烂尾的典型路径（对照自查）

1. 起步顺利，功能越加越多，没有一次发布；
2. 中途遇到一个技术上不熟的环节，转向去学新东西，项目停摆；
3. 因为「还没准备好」一直不给人看，于是没有反馈；
4. 临近期末/面试，赶工做出一个只在自己机器上能跑的版本；
5. 最后交出去的东西，连自己都说不清做了什么。

任何一步都能被前面几节的检查点拦住。

## 自检

- 现在的状态，能不能跑一次完整闭环给别人看？
- 有没有一份写下来的「不做什么」？
- 最近两次改动，是在补齐闭环还是润色？
- 里程碑有没有被推迟超过两次？
