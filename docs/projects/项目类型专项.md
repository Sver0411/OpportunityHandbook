# 项目类型专项：什么证据才算做得好

「有人用」是产品型项目的证据，不是所有项目的证据。这一页按类型说明**什么才算做得好**，以及每种类型最常见的自欺。

## Web / App

证据：可访问的地址、核心流程可完成、真实使用记录（哪怕几个人）、可量化的体验指标（首屏时间、错误率）。

自欺：只展示首页截图；把「部署成功」当成「有人用」；功能多但流程走不通。

## AI / Data

证据：**基线对比**、清晰的训练/验证划分、多指标（不只一个数字）、重复试验的波动、消融、失效样例、可复现脚本。

自欺：只报最好一次的结果；和弱基线比较；换了数据集却不说明；把 notebook 里的一个单元格当成「系统」。

## 嵌入式 / IoT

证据：长时间运行记录、异常恢复行为、链路质量（丢包、RSSI、延迟）、功耗、重启原因、现场部署照片或数据。

自欺：演示成功一次就宣称稳定；只测理想距离与无遮挡；不记录重启次数。

## 硬件 / 机器人

证据：设计文件与迭代版本、测试台架数据、误差/精度、良率或成功率、故障模式清单、可复现的搭建步骤。

自欺：只给成品照片；不给失败率；把「能跑一次」当成「能用」。

## 开发者工具 / 库

证据：使用者数量与使用深度（被谁依赖）、文档质量、测试覆盖关键路径、性能或体验改进数字、Issue 响应记录。

自欺：star 数当成质量；把「自己每天用」当成「产品验证」。

## 开源项目

证据：贡献被合并的记录、Issue 处理、release 与变更日志、下游使用、维护者身份。

自欺：提交了很多 PR 但合并率极低；把格式调整当成主要贡献；项目无法在别人机器上跑起来。

## 科研项目

证据：明确的研究问题、可复现的实验、基线与消融、数据与代码、论文或报告、同行反馈（哪怕是一次组会质疑）。

自欺：把「读了很多文献」当产出；只有一次实验没有重复；结果不显著却按显著写。

## 一张对照表

| 类型 | 最有力的证据 | 最弱但常被当真的证据 |
| --- | --- | --- |
| Web/App | 真实使用 + 指标 | 截图 |
| AI/Data | 基线对比 + 复现 | 单次最好结果 |
| IoT | 长时运行 + 链路数据 | 一次演示成功 |
| 硬件 | 测试数据 + 失败模式 | 成品照片 |
| 开发者工具 | 被依赖 + 文档 | star 数 |
| 开源 | 合并记录 + 维护 | PR 数量 |
| 科研 | 复现 + 同行反馈 | 文献阅读量 |

## 怎么用它自检

先确定你的项目属于哪一类，再看「最有力的证据」那一列——**能不能在两周内补出一条**。能，就去补；不能，说明项目还停留在一个只有你自己知道的阶段。

跨类型的共同标准只有一条：**你能不能说清「我怎么知道它有效」**。相关方法见 [工程项目的测试、指标与证据](测试与指标体系.md)。
