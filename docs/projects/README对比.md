# README 的技术写作（三档对比）

README 的唯一职责：**让一个不认识你的人，在没有你在场的情况下把你的项目跑起来，并判断它值不值得看下去。**

## 差 / 普通 / 优秀三档

### Overview

- 差：`这是一个用 Python 写的系统` —— 说了等于没说；
- 普通：`一个基于 Flask 的待办事项管理工具` —— 有技术栈，没有问题；
- 优秀：`把课程作业的截止日期集中管理，避免在多个平台之间来回核对。目前支持导入导出与提醒，只处理个人使用场景。` —— 问题、范围、边界都在。

### Problem（为什么做）

- 差：无；
- 普通：`方便管理任务`；
- 优秀：`我每周要在三个平台核对作业截止时间，漏过一次实验报告。这个项目只做一件事：把三处时间合并成一份清单，并在截止前一天提醒。`

### Architecture（结构）

- 差：把目录树贴上来；
- 普通：一张组件图；
- 优秀：一张数据流图加三句说明——数据从哪来、在哪处理、存到哪，并注明「为什么不用队列」（因为它引入了比问题本身更复杂的东西）。

### Quick Start（怎么跑）

- 差：`pip install -r requirements.txt` 后面没了；
- 普通：给命令但缺前置条件（版本、环境变量、数据库）；
- 优秀：写清前置条件、三步命令、成功时应该看到什么输出，以及常见失败的两种表现。

### Hardware / Wiring（硬件项目）

- 差：只写型号；
- 普通：列出元件清单；
- 优秀：接线图（引脚到引脚）、供电方式与电压、注意事项（哪一步容易烧板子）。

### Benchmark（数据）

- 差：无，或写「性能很好」；
- 普通：给一个数字，不给条件；
- 优秀：给指标定义、环境、样本量与原始数据位置，并写清在什么条件下不成立。写法见 [工程项目的测试、指标与证据](测试与指标体系.md)。

### Testing（测试）

- 差：无；
- 普通：`运行 pytest`；
- 优秀：说明覆盖了哪些核心流程、哪些没有覆盖、如何手动复现失败路径。

### Known Limitations（已知限制）

- 差：无（这是最伤可信度的一栏）；
- 普通：一句「仍在开发中」；
- 优秀：明确写出不支持的场景、已知缺陷与原因。**主动写限制的项目，比声称完美的项目可信得多。**

### Roadmap（后续）

写「下一步做什么、不做什么」，而不是愿望清单。

### License

写清许可证类型；如果自己也不确定，就用最宽松的常用许可证并说明。正文与代码的许可可以不同，参见仓库的 [LICENSE-CONTENT](../../LICENSE-CONTENT) 与 [LICENSE](../../LICENSE)。

## 哪些项目不需要全写

- 一次性课程作业：Overview + Quick Start 基本够；但**不许写假数据**；
- 私有脚本：Overview + 已知问题即可，不必写 Roadmap 与 License（但要确认公司内部规定）；
- 硬件项目：Hardware / Wiring 必写，Benchmark 可选；
- 开源项目：除了上面全部，还要有贡献指南与 Issue 模板。

## 自检

- 别人按 Quick Start 跑，第一次就成功了吗？失败时看到的信息能自己排查吗？
- 你的数字有没有条件说明？
- 写没写「不支持什么」？
- README 里的截图或命令，是不是上个版本的？
