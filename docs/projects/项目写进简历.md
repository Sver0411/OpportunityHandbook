# 项目如何写进简历与面试（5 组 Before / After）

一条好的项目描述要经得起追问。判断标准很简单：**读完这段，对方能不能问出一个具体问题**。问不出，说明写得太抽象。

## 完整链路

```
项目本体 → 提取你的贡献 → 找到证据 → 写成 bullet → 预判技术追问
        → 准备 trade-off → 准备 failure → 准备 improvement
```

多数人只做了第二步和第四步，于是面试一到第五步就崩。

## 五组对照

### 1. 无结果型（学生最常见）

- 原文：`使用 Python 和 Flask 开发了一个博客系统，实现了文章发布、评论和标签功能。`
- 问题：读完不知道它和另外十个博客系统有什么区别，也问不出问题。
- 改写 v1：`独立开发课程项目博客系统（Flask + SQLite），支持文章发布与标签检索。`
- 改写 v2：`为解决课程小组资料散落在聊天记录里的问题，独立开发文档站（Flask + SQLite）：支持 Markdown 发布与标签检索，被同组 6 人用于整个学期，累计 42 篇文档。`
- 理由：v2 给出了问题来源、范围与使用证据；「6 人用一个学期」是可核对的规模。

### 2. 有数据型

- 原文：`优化了系统的性能，效果显著。`
- 改写：`把列表接口的 P95 从 480 ms 降到 90 ms：定位到 N+1 查询后改为批量查询，并给热点加缓存；压测条件为 50 并发、持续 10 分钟。`
- 理由：给出前后数字、手段与测量条件——面试官可以顺着问「缓存失效策略是什么」。

### 3. 硬件 / 嵌入式型

- 原文：`基于 ESP32 做了物联网系统。`
- 改写：`用 ESP32 + LoRa 做远程采集节点：隔两道墙场景下丢包率 18%，加入重传与自适应发送间隔后降到 4%；连续 72 小时运行无重启。`
- 理由：硬件经历的通用语言是**条件 + 数字**（距离、遮挡、丢包、功耗、稳定性），不是技术名词。

### 4. 开源贡献型

- 原文：`参与开源项目开发。`
- 改写：`为 xx 项目提交 4 个 PR（3 个已合并）：修复 YAML 解析在嵌套引用下的缺陷（附最小复现与回归测试），补齐 Windows 安装文档。`
- 理由：写清项目名、PR 数与合并状态、每个改动解决了什么问题——这些都能公开核对。

### 5. 转行型

- 原文：`自学了前端，做了几个小项目。`
- 改写：`从医疗器械销售转向前端（自学 8 个月）：为原公司内部做了一版客户随访看板（React + 后端接口），替代原先每天手工汇总 Excel 的流程，团队 4 人日常使用；同项目作为求职作品集主项。`
- 理由：用「原有行业里的真实问题」证明能力迁移，比孤立的练习项目更有说服力。

## before/after 的公共规则

- 每条只说一件事，句式：**为 X 问题，做了 Y（技术/手段），结果是 Z（数字/范围）**；
- 数字必须有条件（样本、时间、并发、环境），否则等于自设陷阱；
- 不写「精通」「熟练掌握」这类无法验证的词；
- 项目多而浅时，删到只剩能讲透的两个。

## 与面试的衔接

简历上每一条 bullet 都对应一段面试时的展开：为什么这么做、还考虑过什么、最难的点、失败过什么、重做会怎么改。准备方式见 [项目面试：从第一句开始的追问链](../job-search/项目面试.md)。

## 自检

- 每条 bullet 能不能被追问三层而不崩？
- 数字后面有没有条件？
- 有没有一条能说明「你的判断」，而不只是「你的实现」？
