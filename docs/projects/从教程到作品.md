# 从教程 Demo 到真正作品

跟教程做出来的东西不是错的，它只是停在「我能跑通」。这一页给一条从跑通走到作品的路径——每一步都增加一个别人能验证的东西。

## 完整路径（十三个台阶）

| 台阶 | 做什么 | 留下的证据 |
| --- | --- | --- |
| 1 跑通 | 按教程把示例跑起来 | 能运行的代码 |
| 2 重写 | 不看教程重写一遍，卡住再回看 | 自己的实现 |
| 3 换输入 | 换成自己的数据/场景 | 新数据与结果 |
| 4 加异常 | 空输入、超长、乱序、断网 | 错误处理的代码与截图 |
| 5 真实数据 | 用真实规模的数据跑一次 | 性能/精度记录 |
| 6 测试 | 核心流程的自动检查 | 测试文件 |
| 7 指标 | 定义一个能量化的指标 | 前后对比数字 |
| 8 长时间运行 | 连续跑几小时或几天 | 稳定性记录 |
| 9 文档 | README + 结构与限制 | 可复现说明 |
| 10 Demo | 一段能看懂的演示 | 链接或录屏 |
| 11 发布 | 打版本、写变更 | 版本记录 |
| 12 真实环境 | 给别人用或部署到真实环境 | 反馈与故障记录 |
| 13 作品集 | 按岗位重写「问题—动作—结果」 | 一页案例 |

不是所有项目都要走完十三步。**能走到第 7 步就已经超过多数课程作业**；第 12 步是分水岭——从这一刻起，你的项目开始产生别人给的证据。

## 软件（Web / 工具）案例路径

跑通一个 Todo 教程 → 换成自己真正在用的清单（例如课程作业追踪）→ 加入导入导出与并发修改 → 用自己三个月的数据跑一遍 → 加核心流程测试 → 记录首屏加载与列表渲染耗时 → 部署到公网 → 让两位同学用一周 → 按反馈砍功能 → 写 README 与限制。

关键证据：可访问的地址、真实使用记录、性能数字、你主动删掉的「不做的功能」清单。

## AI / 数据项目案例路径

跑通一个分类示例 → 换成自己领域的数据集 → 加入脏数据与不平衡样本 → 做数据清洗与划分（避免泄漏）→ 固定随机种子 → 设置基线（简单启发式 + 已有方法）→ 记录多组指标与置信区间 → 做一次消融 → 把限制写进 README → 给出可复现脚本。

关键证据：基线对比、数据划分说明、可复现脚本、明确写出的失效场景。相关方法见 [Baseline 怎么设计](../research-deep/Baseline设计.md) 与 [数据管理与可复现性](../research-deep/数据与可复现.md)。

## IoT / 嵌入式案例路径

点亮传感器 → 打通采集与上报 → 加入断网重连与看门狗 → 连续运行 24 小时以上 → 记录丢包率、重启次数、功耗 → 换一个更差的环境（隔墙、远距离）再跑 → 整理成实验表 → 写接线图与复现步骤。

关键证据：长时间运行记录、异常恢复日志、功耗与丢包数据、接线与复现说明。指标定义与记录方式见 [工程项目的测试、指标与证据](测试与指标体系.md)。

## 三个最容易停住的地方

- **第 3 步**（换输入）：教程数据太干净，换真实数据立刻出问题。这一步是分水岭，跨过去才算自己的项目；
- **第 7 步**（指标）：没有指标就没有改进方向，项目会变成无止境地加功能；
- **第 12 步**（真实环境）：多数人在这里停下，因为真实环境会暴露自己不想面对的问题。

## 自检

- 关掉教程，你能从零把核心流程写出来吗？
- 换成自己的数据/场景后，哪些地方坏了？坏在哪里？
- 有没有一个数字，能说明这个版本比上个版本好？
- 别人能不能在十分钟内把你的项目跑起来？
