# 日志、可观测性与故障分析

项目一旦跑在别人手里，你就不在现场了。日志是你在现场之外的唯一眼睛。

## 日志该记什么

一条有用的日志包含四样：**时间、级别、上下文、发生了什么**。

```
2026-09-29T10:12:03Z  WARN   device=A7F2 retry=3 rssi=-91  上报失败，第 3 次重试
2026-09-29T10:12:08Z  ERROR  device=A7F2 reason=uart_timeout  串口读取超时，丢弃本包
```

反例（等于没记）：

```
错误
error occurred
fail
```

判据很简单：**半年后的你，看到这行日志能不能判断当时发生了什么**。

## 级别的用法

- `DEBUG`：开发时看的细节，默认关闭；
- `INFO`：正常但重要的事件（启动、配置加载、关键状态变化）；
- `WARN`：可以继续，但已经偏离预期（重试、降级、丢弃数据）；
- `ERROR`：这次操作失败了，但程序还活着；
- `FATAL`：程序要退出了。

最常见的滥用是把所有东西都写成 `ERROR`，于是真正的错误被淹没。

## 上下文比信息更重要

嵌入式与分布式场景里，单条日志没有意义，必须能串起来：设备号/请求号、关键参数、重试次数、当时的状态。做法是**每条日志都带一个可追踪的标识**（trace id / device id），这样你才能把一次故障的完整过程捞出来。

## metrics 与 trace

日志之外，还需要两类信号：

- **metrics（指标）**：随时间变化的数字——请求数、错误率、队列长度、内存占用、丢包数。它们回答「现在是否异常」；
- **trace（链路）**：一次请求经过哪些环节、每段耗时多少。它们回答「慢在哪一环」。

学生项目的轻量版本：定时把关键计数打成一行 `INFO` 或写进 CSV，事后画图。见 [Benchmark 记录表](../tools/Benchmark记录表.md)。

## 崩溃与重启

- **崩溃信息**：异常类型、调用栈、当时的输入，能记就记；
- **看门狗（watchdog）**：嵌入式与长时间运行的服务需要一个「如果 N 秒没有心跳就重启」的机制，重启时**必须记录重启原因**；
- **重启原因**：上电重启、看门狗重启、主动重启、异常重启——分不清这四种，就永远查不清「为什么它自己断了」。

## 故障复现与根因

顺序不要跳：

1. **稳定复现**：先让故障按需出现（同输入、同环境、同操作）；
2. **缩小范围**：注释掉一半、换更小输入、二分定位；
3. **建立假设**：写下「我认为是因为 X」，并预测验证结果；
4. **验证假设**：改一个变量看结果是否如预期；
5. **区分相关与因果**：两个现象同时出现不代表前者引起后者；
6. **找到根因**：不是「让它不报错」，而是「为什么会有这个输入/状态」。

## 一次完整的小故障分析（示例）

现象：IoT 节点每小时丢一次数据。日志显示每次丢包前 2 秒出现 `uart_timeout`，重启后恢复。假设是缓冲溢出。验证：把采集周期从 1 秒改为 2 秒，丢包消失但延迟翻倍——说明是吞吐不足而不是数据损坏。根因：串口读取与上报在同一循环里串行执行，上报阻塞导致缓冲溢出。修复：上报改为独立任务 + 环形缓冲，加一个「缓冲超阈值」告警。验证：连续 72 小时无丢包，缓冲水位曲线平稳。

## postmortem（事后复盘）

一页纸就够：时间线、影响范围、根因、修复动作、**为什么之前没发现**、下次如何更早发现。最后一条最关键——它决定你会不会在同一种故障上再栽一次。用 [Failure Log](../tools/Failure日志.md) 持续记录。

## 自检

- 现在出故障，我能从日志里还原出当时的输入与状态吗？
- 我知道设备/服务上一次重启是因为什么吗？
- 有没有一个指标能在用户发现之前告诉我出问题了？
- 我的复盘写的是「怎么修好的」，还是「为什么会坏」？
