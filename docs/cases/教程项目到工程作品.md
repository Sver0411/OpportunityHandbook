# Case：从教程项目到工程作品（三种项目）
背景：同一位学生的三个教程项目，分别代表三类技术栈。他给自己定了一条规则——**每个项目只改四处，不多做**。

## 案例 A：Web（待办清单）

- 原状：跟着教程做的 CRUD 应用，用内存存数据；
- 四处改动：
  1. 换输入：改成自己真实的课程作业清单（60 条，含截止时间与状态）；
  2. 加异常：空标题、超长文本、重复提交、网络中断；
  3. 加持久化：SQLite + 一次导出/导入；
  4. 加测试：核心流程 6 条自动检查（增删改查 + 两个边界）；
- 结果：不再丢数据；导出功能被两位同学使用；
- 证据：可访问地址、6 条测试、两位使用者的反馈截图。

## 案例 B：AI / 数据（文本分类）

- 原状：教程里用现成数据集训一个分类器，报了一个准确率；
- 四处改动：
  1. 换输入：换成自己领域的 800 条真实文本（手工标注）；
  2. 加划分与种子：固定训练/验证划分，记录随机种子；
  3. 加基线：多数类基线 + 一个简单规则法 + 一个现成模型；
  4. 加指标与限制：准确率 + 两类召回 + 失效样例；写清「长尾类别不如规则法」；
- 结果：结论从「准确率 92%」改成「在长文本上优于基线，短文本上不如规则法」；
- 证据：可复现脚本、基线对比表、失效样例清单。

## 案例 C：IoT / 嵌入式（温湿度上报）

- 原状：教程里点灯 + 串口打印；
- 四处改动：
  1. 加通信：LoRa 上报，加断网重连；
  2. 加长时运行：连续 72 小时，记录丢包与重启；
  3. 加条件测试：近距离 / 隔一道墙 / 隔两道墙，各测 30 分钟；
  4. 加文档：接线图、供电说明、已知限制（远距离丢包率上升）；
- 结果：丢包率从「未测」变成有分条件的数字；
- 证据：实验记录表、接线图、72 小时运行日志。

## 三条共同规律

1. **换输入**是最有分水岭意义的一步——教程数据太干净，真实数据立刻暴露问题；
2. **加基线或对照**让「效果不错」变成可判断的结论；
3. **写限制**反而提升可信度：三个项目都因为写了「在什么条件下不成立」而在面试里被追问得更深。

## 改造优先级（时间有限时）

换输入 → 加测试 → 定指标 → 写文档 → 发布。前两项做完，项目性质就变了。
