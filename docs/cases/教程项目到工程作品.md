# Case：从教程项目到工程作品（三种项目）

教程项目的问题不是“它太简单”，而是**关键决定已经被教程替你做完了**。真正把它升级成作品，不是继续堆功能，而是把原来被隐藏的判断重新拿回来：输入从哪里来、失败怎么办、怎么证明有效、别人能不能复现。

下面用三类项目走同一条“证据升级链”。

## Case A：Web 待办应用

### 教程状态

已有 CRUD、页面和内存数据。继续加主题切换、头像和动画不会明显增加工程深度。

### 第一次改造：换成真实输入

把它拿来管理真实课程任务。很快出现教程没有的问题：
- 截止时间跨时区；
- 重复提交；
- 页面刷新后数据丢失；
- 文本过长；
- 网络中断；
- 两个标签页同时修改。

这一步的价值是把“功能列表”变成“真实状态”。

### 第二次改造：让失败可处理

加入持久化、输入校验、错误状态和导出/导入。然后主动制造异常：断网提交、重复点击、数据库文件损坏、非法输入。

项目开始能回答：

> 出错时用户看到什么？数据会不会丢？恢复以后会不会重复写？

### 第三次改造：留下工程证据

补核心流程测试、一次数据迁移、README 和部署说明。让另一个人按文档从零运行。

最终作品不再是“我做了一个 Todo App”，而是：

> 我把一个教程 CRUD 改造成真实使用的任务工具，处理持久化、重复提交和断网场景，并用自动测试与复现文档验证核心路径。

## Case B：AI / 数据文本分类

### 教程状态

用公开数据集跑一个现成模型，最后只剩“accuracy 92%”。

这里最大的问题是：你不知道模型为什么有效，也不知道换数据以后是否还成立。

### 第一次改造：重新定义任务

换成和自己领域相关的数据。先定义标签，再抽样检查歧义。数据不够时宁可缩小任务，也不要假装标签可靠。

### 第二次改造：建立 baseline

不要直接上复杂模型。先做：
- 多数类；
- 简单规则；
- 传统模型或轻量模型。

只有复杂方法稳定超过合理 baseline，才有必要讨论它的价值。

### 第三次改造：做错误分析

把错样本分类：短文本、长文本、讽刺、类间歧义、标注错误。你可能发现模型平均分不错，但在真正重要的少数类上很差。

这时结论应该缩小：

> 在某类文本上优于基线，但在长尾类别上仍不稳定。

这个结论比“92%”更可信。

### 第四次改造：让别人能重跑

固定数据版本、划分、配置和随机种子；保存评估脚本和失败样例。README 里写清楚限制。

最终证据是：**baseline + 评测协议 + 失效样例 + 可复现脚本**。

## Case C：IoT / 嵌入式温湿度上报

### 教程状态

传感器能读数，LoRa 能发包，串口能打印。

这只能证明“在当前桌面环境里成功过一次”。

### 第一次改造：定义什么叫稳定

先明确要测什么，而不是先定“跑多久”：
- 发送与接收包数；
- 序号连续性；
- 丢包；
- UART/E220 错误；
- 重启；
- 断电恢复；
- 不同距离与遮挡；
- 功耗。

持续时间应由你想覆盖的故障模式决定。想测短时连通性和想验证长期稳定性，本来就不该用同一个测试窗口。

### 第二次改造：主动制造真实故障

例如：
- 接收端暂时断电；
- 串口数据异常；
- 传感器拔掉再接；
- 链路遮挡；
- 供电波动；
- 连续运行后观察是否重启。

重点不是“故障越多越好”，而是每个故障都能回答：系统怎么发现、怎么恢复、恢复后数据是否可信。

### 第三次改造：写成测试协议

测试前写：
- 目的；
- 条件；
- 设备和固件版本；
- 输入；
- 指标口径；
- 原始日志保存位置；
- 什么结果会推翻当前结论。

然后再运行，而不是看到好结果以后才决定如何描述。

### 第四次改造：把负结果也留下

如果远距离丢包上升、某种异常会导致重启，不要删。写进 limitation，并说明下一版准备验证什么。

最终作品不再是“ESP32 + LoRa 智慧农业”，而是一组**可核验的工程结论**。

## 三类项目真正共通的升级顺序

不是固定的功能清单，而是五个问题：

1. **输入真实吗？** —— 换掉教程最干净的输入；
2. **失败看得到吗？** —— 主动覆盖异常和边界；
3. **结论有对照吗？** —— baseline、旧方案、测试前后；
4. **结果可复现吗？** —— 配置、数据、版本、文档；
5. **限制写清了吗？** —— 知道哪里还不能成立。

只要这五个问题逐步有答案，哪怕项目功能不多，也会从练习走向作品。

## 时间有限时怎么取舍

不要按固定顺序机械推进。先找**最大的不确定性**：

- 如果根本没人需要：先验证问题；
- 如果功能经常坏：先处理失败路径；
- 如果效果说不清：先做 baseline/指标；
- 如果只有你能跑：先补复现与文档。

先解决最可能推翻项目价值的那个问题。
