# Case：第一次开源贡献

背景：大三学生，会 Python，想用开源贡献补项目经历。目标：一个他在用的命令行工具（约 2 万行代码）。

## 第一次尝试：被关闭

他翻了项目的 issue 列表，看到一个标着 `good first issue` 的条目：给某个命令加一个 `--json` 输出选项。花了两天写完，直接提了 PR。

结果：被维护者关闭，理由是「该选项的设计已在 #812 讨论，方案是先重构输出层」。

**复盘**：他跳过了两步——没有读 CONTRIBUTING，也没有在 issue 下确认方向。规则就写在仓库里，只是他没看。

## 第二次尝试：按流程走

1. **选问题**：在自己使用中遇到一个真实缺陷——当配置文件里有重复键时，工具静默使用最后一个值，不报错；
2. **搜 issue**：搜索 `duplicate key`，发现有人提过但未解决，且维护者说「欢迎 PR」；
3. **复现并写最小复现**：附上最小配置文件与命令，说明期望与实际；
4. **在 issue 下留言**：说明打算修，问是否有偏好方案；维护者回复「与现有校验逻辑一致即可」；
5. **写测试**：先加一个会失败的测试（重复键应报错），确认它确实失败；
6. **改代码**：在配置加载阶段加入重复键检测，保持与现有报错格式一致；
7. **提 PR**：标题写清问题，描述里写「改了什么、为什么、怎么验证」，关联 issue 编号；
8. **评审往返**：第一轮被要求「错误信息里带上键名」；改完后 CI 通过；
9. **合并**：三天后合并，进入下一个 release 的 Changelog。

## 这次踩到的三个细节

- **不要夹带无关改动**：他顺手改了一处格式，被要求回滚；
- **错误信息要一致**：项目的报错风格是固定的，新代码必须跟随；
- **CI 失败先自己修**：不要等维护者指出。

## 之后半年

- 又提交了 5 个 PR（4 个合并）：文档补全、两个边界修复、一个测试补充；
- 在 issue 里帮别人复现问题 3 次；
- 从「提 PR 的人」变成「这个模块的熟人」——维护者在讨论新功能时会 @ 他。

## 简历上怎么写

`为 xx 项目提交 6 个 PR（5 个已合并）：修复配置重复键静默覆盖的缺陷（附回归测试）、补全 Windows 安装文档；参与 issue 复现 3 次。`

## 可复用要点

1. 先读 CONTRIBUTING，再在 issue 下确认方向；
2. 从「自己在用的问题」入手，动机与上下文都更充分；
3. 先写测试再修，是最快被合并的路径；
4. 保持改动小而聚焦，一次只做一件事；
5. 被关闭的第一次不是失败，是没读规则。
