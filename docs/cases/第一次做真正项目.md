# Case：第一次做真正的项目

背景：大二学生，会 Python 基础，做过两个教程项目，想做一个「能写进简历」的项目。可支配时间：每周 8 小时，持续六周。

## 第 1 周：从「想做什么」改成「谁有麻烦」

最初的 idea 是「做一个学习打卡 App」。追问一句「谁有麻烦」之后发现：真正麻烦的是**课程作业的截止时间散落在三个平台**，他每周要手工核对，还漏交过一次。

问题收窄为：把三处截止时间合并成一份清单，并在截止前一天提醒。范围明确到「只处理自己的课程」。

## 第 2 周：范围与 MVP

写死「不做什么」：不做多用户、不做移动端、不接入通知推送（先用邮件）。

第一版标准：手工把截止时间录入一份 CSV → 脚本读取 → 生成合并清单 → 输出到一份 Markdown 文件 → 邮件发给自己。**流程完整，但每一段都很土。**

## 第 3 周：实现与第一次失败

写到一半发现三个平台的导出格式完全不同（一个给 iCal，一个只有网页表格，一个是截图）。这时有两个选择：写三个解析器，或者先只做能导出 iCal 的那个。

选择后者（先闭环）。前两周只支持一个平台，另外两个手工补录。**这条决定让项目没死在数据格式上。**

## 第 4 周：测试与真实使用

加了三类检查：空文件、日期格式错误、重复条目。自己用了一周，发现两个问题：跨时区的时间偏移、同一门课的多个截止时间被合并。

修完之后加了「原样保留来源」的字段，问题可追溯。

## 第 5 周：测量

没有用户数可统计，于是记录了三个能测的数：手工处理时间（从约 15 分钟/周降到 2 分钟）、漏交次数（1 次 → 0）、脚本执行时间（1.3 秒）。同时记录了限制：只支持一个平台、遇到格式变化会失败。

## 第 6 周：README 与 Demo

README 写了问题、范围、安装、限制；Demo 用 30 秒录屏，内容是「运行一次，生成清单」。

## 失败分支：上线没人用

他把项目发到班级群，只有 3 个人点了链接，0 个真实使用者。

处理方式不是继续推广，而是**换一个证据**：把他的工具给两位同样有多平台作业的同学，手工帮他们配置，观察他们的使用与卡点。两人用了两周，其中一人提出「能不能加一个已完成的勾选」。

这件事真正带来的收获是：**他后来把这个项目改写成「解决自己的真实流程问题 + 两位同学使用」**，并且在面试里能讲清「为什么只支持一个平台」。

## 最终产出

- 一个可运行的工具（含 README 与限制说明）；
- 三个可量化的数字（时间、漏交、执行耗时）；
- 一份失败记录（推广无效）与一次有效的替代验证；
- 简历上一条有边界、有数字、能追问三层 bullet。

## 可复用的判断点

1. 把 idea 收成「谁有什么麻烦」；
2. 用「不做什么」把范围切小；
3. 数据格式是学生项目最常见的死因——先做能闭环的那一条路；
4. 没有用户数时，用时间和错误率也能构成证据；
5. 推广失败时，改用「手工陪着用」来获得真实反馈。
