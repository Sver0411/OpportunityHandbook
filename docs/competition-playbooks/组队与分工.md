# 竞赛组队与分工

多数竞赛的胜负在组队那一刻就决定了一半。判断队友的标准不是「关系好」，而是**能不能按时交出东西**。

## 找队友的三个标准

1. **能交出东西**：过去有没有完整交付的经历（课程项目、比赛、作品都算）；
2. **时间能对齐**：赛期内的可用时间是否匹配（问具体时段，不要问「有没有空」）；
3. **技能互补**：确认角色缺口，而不是找三个同类。

优先找合作过一次的人。第一次合作、又赶上高强度赛期，是最容易翻车的组合。

## 角色划分

常见三类角色（不同赛事权重不同）：

| 角色 | 负责 | 需要的能力 |
| --- | --- | --- |
| 设计与决策 | 方案、取舍、进度把控 | 判断力、能把问题拆开 |
| 实现 | 主要产出（代码/模型/原型） | 动手能力、能快速试错 |
| 表达与交付 | 材料、演示、答辩 | 写作、讲清逻辑 |

三人小队里，**不要三个人都做实现**：到最后没人写材料，也没人盯进度。

## 开工前的约定（写下来）

- 目标与验收标准（要做出什么、到什么程度）；
- 分工与边界（谁负责哪一块、产出交给谁）；
- 同步节奏（每天固定一次简短同步）；
- 冲突处理：谁拍板，拍板后如何执行；
- 退出机制：如果某人无法投入，怎么调整（谁来补位、是否重排范围）。

这五条写在共享文档里，赛期里能省掉大量争论。

## 时间表对齐

用一张表对齐每个人的可用时段与不可用时段（课程、考试、实习）。**赛期的最后一天必须全员可用**，否则前面的努力会停在提交前。

## 冲突处理

- 分歧围绕方案时，用「哪个方案更快能被验证」来决策，而不是靠嗓门；
- 分歧围绕人时，先私下沟通一次，说明具体行为与影响，不要群里点名；
- 进度落后时，先砍范围，不要靠熬夜顶。

## 不同赛事的团队结构差异

- **工程 / Hackathon**：偏实现，2–4 人，需要一个人管交付节奏；
- **数据 / AI**：数据与建模占大头，需要一个人专门做验证与结果整理；
- **商业案例 / 创业赛**：分析与表达优先，需要有人专门做财务与逻辑收口；
- **学科竞赛（建模类）**：建模、编程、写作三角色，缺一不可。

## 自检

- 我的队友过去有没有完整交付过东西？
- 我们的角色有没有明确缺口与补位方案？
- 赛期最后一天全员可用吗？
