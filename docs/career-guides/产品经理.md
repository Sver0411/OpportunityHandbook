# 产品经理

用一句话概括：判断**该做什么、不该做什么**，并推动它被做出来、被用起来。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 需求文档、跟进排期、数据核对、用户反馈整理 |
| 中级 | 独立负责一个模块的需求与迭代、做取舍 |
| 资深 | 定义方向、跨团队协调、对业务指标负责 |

真实工作里，写文档与开会占很大比例；「想创意」只是很小一部分。

## 团队与相邻岗位

与研发、设计、测试、运营、数据协作。边界：产品定义「做什么、为谁解决什么问题」，研发定义「怎么做」，设计负责体验方案。

## 常见岗位名称

产品经理、产品助理、增长产品、B 端/C 端产品、策略产品、数据产品。

## 招聘与门槛

- 硬技能：需求分析、数据分析基础、原型与文档；
- 软技能：结构化表达、推动他人、接受被否；
- 校招：学历与实习经历影响大；社招：看负责过的模块与结果。

## 项目与面试怎么准备

- 证据：一份完整的产品文档 + 上线结果（数据或用户反馈）；
- 面试考法：案例分析（「某指标下降怎么查」）、产品设计（「为某人群设计一个功能」）、项目追问；
- 案例面试的答法：先澄清目标与约束 → 拆解 → 优先级 → 验证方式。

## 第一份工作怎么看

看是否有真实用户与数据反馈（做内部系统虽稳，但产品判断力的训练慢）。

## 3–5 年出口

产品负责人、增长/策略方向、创业、转运营或数据方向。

## 常见误区

- 以为产品就是「提想法」（真正难的是取舍与推动）；
- 不做数据与用户验证；
- 只做需求搬运，不定义问题。

## 低成本试法

为一个小场景写一页产品方案（问题、用户、方案、指标、风险），再找三位目标用户验证需求是否真实。

## 一天通常是这样的

| 时间 | 做什么 | 备注 |
| --- | --- | --- |
| 10:00 | 看数据与用户反馈：某功能使用率 12%，反馈集中在「找不到入口」 | 先判断是曝光还是体验问题 |
| 10:30 | 与设计过一遍三个方案的取舍 | 带上约束与目标 |
| 11:30 | 写需求文档：目标、范围、不做什么、验收标准 | 「不做什么」必写 |
| 14:00 | 需求评审：与研发确认工作量与风险，砍掉两个非核心点 | 砍范围而不是砍质量 |
| 16:00 | 跟进上一个版本上线后的指标 | 上线不是结束 |
| 17:00 | 整理用户访谈记录，找重复出现的痛点 | 重复出现的才值得做 |

## 一次面试追问的典型走向

下面这段按面试与复盘里常见的追问整理，用来说明答法的结构，不是某位候选人的原话。

> **面试官**：这个功能你怎么判断该不该做？
> **候选人**：先看有多少用户在什么场景下遇到这个问题，再看现有替代方案的成本。我们访谈了 12 位用户，其中 9 位提到同一处卡点，且都在手工绕过。
>
> **面试官**：上线后指标如何？
> **候选人**：入口曝光到点击的转化从 12% 提到 24%，但整体使用率只涨了 3 个点，说明还有第二道门槛在流程里，这是我下一轮的假设。
>
> **面试官**：如果研发说做不了，你怎么办？
> **候选人**：先问清是哪一部分做不了，把方案拆成能做的 80%，剩下的排进下一版；不硬压时间。

**要点**：产品面试考的是**判断依据与取舍过程**，不是创意。

## 产品经理真正交付的是“更少的错误决定”

写 PRD 只是载体。核心工作是把用户、业务和工程约束放到同一个问题里：谁有问题、问题多痛、为什么现在做、什么证据说明做对了。好产品经理会主动删需求，因为资源有限时，**不做什么**和做什么一样重要。

## 从需求到上线的真实链路

需求来源 → 访谈/数据核实 → 定义目标与非目标 → 与设计和研发拆方案 → 确定成功指标 → 开发期间处理变化 → 上线观察 → 复盘。每一步都可能推翻前一步的假设。准备项目时不要只展示原型图，要展示至少一次“因为证据改变了原方案”。

## 面试案例怎么讲

面对“设计一个校园二手平台”这类题，先问用户与场景，再定义最关键问题，不要直接列功能。最后给出最小方案、指标和风险。面试官更看你的取舍过程，而不是功能数量。
