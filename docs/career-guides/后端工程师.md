# 后端工程师

用一句话概括：让系统在真实流量与故障下**稳定地给出正确结果**。

## 后端真正处理的是状态、失败和并发

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 写接口、修缺陷、写测试、查日志 |
| 中级 | 模块设计、数据结构与索引、性能优化、参与容量评估 |
| 资深 | 系统设计、一致性与可用性取舍、跨团队方案、事故处理 |

真实工作里，「设计新功能」大概只占一半，其余是排查、优化、兼容与协作。

## 服务背后有哪些协作边界

与前端、产品、测试、运维、数据协作。与运维/SRE 的边界：后端负责业务系统的正确与性能，SRE 负责基础设施、发布体系与整体稳定性。与数据工程的边界：在线事务系统属后端，离线管道与仓库属数据工程。

## 后端岗位为什么名字很多

后端开发、服务端工程师、Java/Go 后端、业务后端、交易/支付/风控后端。

## 从 CRUD 到工程能力，面试看什么

- 硬技能：语言 + 数据库（索引、事务）+ 缓存 + 网络基础 + 并发基础；
- 加分：消息队列、分布式基础、可观测性工具；
- 学历：校招初筛用，社招弱化。

## 让一个服务经得起追问

- 证据：接口性能数据（P95、并发）、一次故障处理记录、测试覆盖关键路径；
- 面试考法：编程题 + 数据库与并发知识 + 项目追问 + 系统设计（初中级可能不问）；
- 系统设计的答法：澄清需求 → 规模估算 → 数据模型 → 核心流程 → 瓶颈与取舍（见 [技术面试全流程](../job-search/技术面试.md)）。

## 第一份后端工作要不要接触线上

优先选有真实流量、有线上值班（哪怕只跟不独立）、有评审文化的团队。

## 后端的几条长期分支

架构方向、SRE/平台方向、数据工程、技术管理、转产品（懂系统的产品有优势）。

## “会中间件”不等于会后端

- 只写业务逻辑，不关心数据与容量；
- 认为「框架会用」等于「系统会设计」；
- 忽略日志与监控——排障能力是后端的分水岭。

## 把一个接口压到它开始坏

用两周做一个带真实输入的小服务：加索引、压一次、记录 P95，再故意注入一次依赖超时看系统表现。


## 后端工作的主线是“状态怎么可靠地变化”

后端不只是写接口。真正困难的地方通常是：数据什么时候写入、重复请求怎么办、失败后能不能重试、多个服务看到的数据是否一致、流量突然放大时哪里先坏。

例如一个“创建订单”接口，至少要考虑：请求重复、库存并发、支付超时、消息重复、数据库失败、状态回滚、审计日志。只会 CRUD 时这些问题都看不见；开始处理这些问题，才真正进入后端工程。

## 一条请求应该怎么追

训练后端最有效的方法之一，是选一条真实请求，从入口一路追到：

网关 → 鉴权 → 服务逻辑 → 缓存 → 数据库 → 消息 → 下游服务 → 日志与指标。

对每一层问：
- 失败会怎样？
- 超时在哪里？
- 能不能重复执行？
- 数据会不会丢或重复？
- 怎么知道它出问题了？

这比孤立背“Redis 八股”“消息队列八股”更容易形成系统理解。

## 容量、稳定性和成本是另一半工作

一个接口平均 20ms 不代表稳定。要继续看 P95/P99、并发下的变化、数据库连接、缓存命中、限流、降级和依赖故障。规模上去后，成本也会反过来限制架构。

学生项目可以做一个小型实验：逐级提高并发，记录延迟、错误率、CPU/内存和数据库变化，再注入下游超时。最后写的不是“支持高并发”，而是“在哪个条件下开始退化，瓶颈是什么”。

## 第一份后端工作要问什么

问清楚你会不会接触线上、是否参与设计评审、数据库和中间件是否只是平台团队全包、值班/故障复盘怎么做。只长期写薄业务接口，和能看到完整服务生命周期，成长路径差别很大。
