# Forward Deployed Engineer（FDE）

Forward Deployed Engineer 不是“会写代码的售前”，也不是“经常出差的软件工程师”。更准确的理解是：**直接贴近客户的真实工作流，用工程方式把模糊业务问题变成可运行系统，再把现场发现反馈回产品与平台。**

当前不同公司的 FDE 职责并不完全相同，但公开岗位中反复出现几类工作：需求发现、技术范围界定、原型、系统设计、生产部署、客户协作、效果评估，以及把一次性交付沉淀成可复用工具或产品反馈。

## 一次项目通常怎么发生

一个 FDE 项目往往不是从“这是需求文档”开始，而是从一句模糊的话开始：

> 我们想让 AI 帮客服处理工单，但数据在三个系统里，安全要求又很高。

接下来不是直接写代码，而是连续收敛问题：

1. **发现问题**：谁在做这件事、当前流程是什么、真正痛点在哪里；
2. **定义成功**：速度、准确性、采用率、成本、风险，哪一个最重要；
3. **梳理约束**：数据在哪里、权限如何、能否出网、谁负责上线；
4. **做最小原型**：先验证最危险的假设，而不是把完整产品做完；
5. **评测**：模型/系统到底在哪些输入上可靠、在哪些条件下失败；
6. **接入生产环境**：身份、日志、监控、权限、数据管道、故障恢复；
7. **让客户真正使用**：上线不等于采用，要看工作流是否真的变化；
8. **沉淀**：哪些部分应该变成平台能力、工具、模板或产品需求。

这条链路的难点是：技术问题和业务问题会交替出现，你必须同时推进。

## FDE 与几个相邻岗位到底差在哪

### 与 Software Engineer

软件工程师通常围绕相对稳定的产品和代码库持续建设；FDE 更经常面对**客户特定环境、模糊需求和更短反馈周期**。

FDE 仍然必须能写 production-grade code。区别不是“工程要求更低”，而是工程决策常常要在现场约束中快速完成。

### 与 Solutions Engineer / 售前

售前的核心通常是帮助客户理解产品、设计方案、完成技术验证并支持成交。FDE 更进一步：**自己承担较重的构建和生产交付责任**，可能直接写前后端、数据管道、Agent、集成层和评测系统。

具体公司边界会重叠，所以看 JD 时不要只看职位名，要看：
- 是否真正写生产代码；
- 是否拥有从 prototype 到 production 的交付责任；
- 是否长期嵌入客户团队；
- 是否要把现场模式反馈进产品路线。

### 与 Technical Consultant

咨询更强调分析、方案与变革管理；FDE 通常要求更强的亲手工程实现能力。但在一些公司，两者的工作形态会部分重合。

## 真正需要的能力不是“全栈都会”

### 工程底座

你至少要能独立把一个系统从本地原型推进到可部署状态：
- Python / TypeScript / Java 等一到两门主力语言；
- API、数据库、身份认证、云环境、日志与监控；
- 能读陌生代码、接第三方系统、处理脏数据；
- 知道测试、权限、失败恢复和可观测性为什么重要。

AI FDE 还经常需要：
- LLM / Agent 应用构建；
- eval 设计；
- prompt 与 tool calling；
- RAG / retrieval；
- latency / cost / reliability trade-off；
- 模型输出失败模式。

### 问题定义

客户说“做一个智能助手”，你要继续问到可以工程化：

> 谁使用？在什么节点使用？它能读取什么？能做什么动作？错一次的代价是什么？人工怎么接管？成功怎么衡量？

不会拆问题的人，会很快陷入“客户不断改需求”。

### 交付判断

FDE 最容易遇到的不是“不会写”，而是：
- 这个需求到底该不该做；
- 原型做到什么程度该停；
- 是定制代码还是平台能力；
- 为速度牺牲多少通用性；
- 哪个风险必须现在解决，哪个可以以后补。

### 客户沟通

这里的沟通不是“表达能力好”这么简单。你需要做到：
- 把业务语言翻译成技术约束；
- 把技术限制讲给非技术利益相关者；
- 当需求不合理时提出替代方案；
- 在现场出现问题时保持信息透明；
- 不为了让客户满意而过度承诺。

## 一个学生怎么证明自己有 FDE 潜力

不要只做“一个 Agent Demo”。更有说服力的是一个**带约束的端到端交付项目**。

例如做一个“企业文档问答 Agent”，把项目推进到：

- 数据源来自真实结构：PDF、表格、知识库混合；
- 有权限边界；
- 有离线评测集；
- 有失败样例；
- 有日志与反馈；
- 可以部署；
- 写清成本、延迟和已知限制；
- 找真实使用者验证工作流，而不是只问“好不好用”。

然后准备一份 delivery note：

> 原问题是什么 → 我怎么缩小范围 → 最危险假设是什么 → 原型怎么验证 → 为什么改架构 → 生产化时补了什么 → 最后哪些问题仍然没解决。

这比“用了某个框架或某个模型”更像 FDE 能力。

## 面试通常会追什么

不同公司流程不同，但 FDE 面试很可能同时检查三类能力。

### Coding / Engineering

不是只会调用 API。你要能写、读、调试真正的应用代码，并解释可靠性和设计取舍。

### System / Product Thinking

可能给一个模糊场景：

> 一家大型企业要把内部知识接入 AI 助手，你会怎么做？

优秀回答不会立刻画架构，而是先问：
- 用户是谁；
- 数据权限；
- 更新频率；
- 允许的错误；
- 如何评测；
- 生产环境；
- 上线后的采用指标。

### Customer / Ambiguity

会看你怎么处理：
- 客户需求不断变化；
- 关键数据拿不到；
- deadline 不变但 scope 失控；
- 模型效果不稳定；
- 多个利益相关者目标冲突。

这里没有“标准话术”，重点是判断过程。

## 第一份相关工作不一定叫 FDE

FDE 很多岗位并不是纯应届入口。更现实的积累路线可能来自：

- Software Engineer + 客户交付；
- Solutions Engineer，但持续亲手构建；
- Implementation Engineer；
- Developer Experience 中偏工程的一侧；
- Technical Consultant；
- Applied AI / ML Engineer；
- 创业公司全栈工程师，直接面对客户。

关键不是职位名，而是你有没有同时积累：

> **工程交付 + 模糊问题定义 + 客户现场 + 生产系统。**

## 怎么判断自己适不适合

FDE 的吸引力通常来自“变化快、离客户近、能看到结果”；代价也来自同一个地方。

你可能更适合，如果你：
- 不排斥陌生代码与陌生业务；
- 喜欢把模糊问题拆清楚；
- 愿意和客户一起调系统，而不是只等 PRD；
- 能接受计划经常变化；
- 既在意工程质量，也愿意为了验证先做小而快的版本。

如果你更喜欢长期深挖单一系统、很少切换上下文，传统产品工程或基础设施团队可能更适合。

## 3–5 年之后能去哪

常见出口取决于你积累的重心：
- 产品/平台工程；
- Staff 级工程与架构；
- Solutions / GTM Engineering 负责人；
- Applied AI / AI 产品工程；
- 产品管理；
- 创业或技术合伙人。

真正有价值的积累不是“做过很多客户项目”，而是你能否把重复模式沉淀成平台、工具和判断。
