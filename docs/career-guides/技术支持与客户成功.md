# 技术支持 / 客户成功

用一句话概括：**在客户现场解决问题**，并把反复出现的问题反馈回产品。

## 从工单到客户价值，工作怎么升级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 处理工单、复现问题、解答使用疑问 |
| 中级 | 处理复杂问题、参与上线支持、做客户培训 |
| 资深 | 关键客户负责人、质量改进推动、团队管理 |

日常节奏由客户驱动：突发问题优先，计划性工作常被打断。

## 支持、CS、研发和售前怎样分工

与研发、产品、销售、运维协作。与研发的边界：你负责定位与沟通，研发负责修复；**能把问题定位到可复现的步骤**是你的核心价值。

## Support、TAM、CSM 的职责边界

技术支持工程师、售后工程师、客户成功（CSM）、实交付程师、Technical Support Engineer。

## 排障、沟通和产品理解哪个更重要

- 硬技能：产品与系统理解、日志与数据库基础、脚本能力加分；
- 软技能：耐心、书面表达（要写清问题与复现步骤）、情绪管理；
- 学历：门槛相对宽松，通信与逻辑能力更重要（部分岗位需要外语）。

## 把一次客户问题整理成诊断闭环

- 证据：一次复杂问题的定位记录（现象 → 复现 → 定位 → 修复 → 预防）、一份客户培训材料；
- 面试考法：场景题（客户情绪化投诉怎么办）、排障题（给日志找线索）；
- 高频考点：先止损再定位，以及怎么把个案变成产品改进。

## 别只看工单量，要看能否形成方法

看是否有「问题反馈到产品」的通道（只处理工单不改进的岗位成长有限）。

## 从支持走向 TAM、Solutions、产品或研发

技术支持负责人、产品经理、售前/解决方案、运维、转研发（需补工程能力）。

## “服务客户”不等于低技术含量

- 把技术支持当「接电话」（真正的价值在定位与推动修复）；
- 不记录问题模式（同类问题反复出现）；
- 忽视书面表达，导致问题反复来回。

## 把一个模糊报错收敛成最小复现

在你常用的某个软件里，主动定位一个真实问题，写出可复现步骤并提交给官方；看对方的回应与你自己的感受。


## 技术支持不是“接工单”，客户成功也不是“维护关系”

技术支持的核心是**把客户现象快速收敛成可复现问题**；客户成功更关注客户能否持续获得价值、采用范围是否扩大。很多公司会把两者混在一起，所以看岗位时要确认自己主要负责故障、实施、采用还是续约。

## 一张高质量工单应该是什么样

当客户说“系统很慢”，不要直接转研发。先补齐：
- 发生时间；
- 影响范围；
- 是否稳定复现；
- 客户环境与版本；
- 最近变更；
- 日志/请求 ID；
- 期望与实际；
- 已尝试过什么。

好的支持工程师能把“模糊抱怨”变成研发可以立即行动的最小问题。

## 什么时候该自己解决，什么时候升级

关键不在职位边界，而在信息完整度和风险。升级前最好已经做到：
- 已复现或明确无法复现；
- 排除了常见配置问题；
- 收集了必要日志；
- 说明客户影响和紧急程度；
- 给出当前假设。

这样研发收到的不是“客户说坏了”，而是一份可调查的问题包。

## 这条路线怎么避免被困在低价值重复工单

要主动积累可复用产出：知识库、诊断脚本、自动化检查、常见故障决策树、产品缺陷模式。能把重复问题消掉的人，才更容易往 Technical Account、Solutions、产品或研发方向走。
