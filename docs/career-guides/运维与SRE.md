# 运维与 SRE

用一句话概括：用工程手段**让系统尽量不出事，出了事能快速恢复**。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 部署与配置、处理工单、跟班处理告警 |
| 中级 | 监控与告警体系、自动化脚本、容量与成本优化 |
| 资深 | 稳定性架构、SLO 制定、事故复盘机制、工具平台 |

日常有相当比例是**处理告警与排查**；改进工作（自动化、容量规划）需要主动争取。

## 团队与相邻岗位

与后端、DBA、安全、网络协作。与后端的边界：后端负责业务正确性，SRE 负责基础设施、发布体系与整体可靠性。

## 常见岗位名称

运维工程师、SRE、DevOps 工程师、平台工程师、基础架构工程师。

## 招聘与门槛

- 硬技能：Linux、网络基础、脚本（Shell/Python）、容器与编排、CI/CD；
- 加分：监控体系、可观测性、云平台认证；
- 学历：门槛中等，实操与事故处理经历更重要。

## 项目与面试怎么准备

- 证据：一套完整的监控与告警方案、一次事故的处理与复盘记录、自动化成果（省了多少人工）；
- 面试考法：Linux 与网络排障题（现场给现象让你查）、容量估算、故障处理思路；
- 高频考点：先止损再定位（不是先找根因）、以及「你怎么避免它再发生」。

## 第一份工作怎么看

看是否有值班能力培养与复盘文化（只做人工操作的岗位会停滞）。

## 3–5 年出口

平台工程、稳定性架构、安全方向、转后端或数据平台。

## 常见误判

- 把运维当「装环境」（现代运维是工程能力）；
- 只救火不改进（永远在处理同类告警）；
- 不做复盘，事故重复发生。

## 低成本试法

用一台云主机部署一个服务，配齐监控与告警，然后故意让服务挂一次，走完「发现 → 止损 → 复盘」流程。


## SRE 不是“服务器出问题我来修”

SRE 的核心问题是：**系统要多可靠，团队愿意为可靠性付出多少成本。** 因此它同时包含工程、运维、监控、容量、事故响应和自动化。

## 从 SLI/SLO 开始理解可靠性

不要一上来背工具。先选一个用户真正感知的指标，例如请求成功率或延迟，再定义目标和统计窗口。之后才能讨论：
- 告警应该因为什么触发；
- 哪些故障值得叫醒人；
- 发布速度和可靠性怎么平衡；
- 什么时候该做容量扩展；
- 错误预算耗尽后要不要停功能发布。

工具只是实现这些目标的手段。

## 一次事故处理真正看什么

事故发生时：
1. 先控制影响，而不是立刻证明根因；
2. 建立统一事实时间线；
3. 缩小故障域；
4. 恢复服务；
5. 再做根因和长期修复；
6. 复盘系统为什么允许这个错误扩大。

好的 postmortem 不找“谁犯错”，而是找缺失的保护机制、观测和流程。

## 学生如何做 SRE 型项目

给一个小服务加：
- 指标与 dashboard；
- SLO；
- 自动部署；
- 健康检查；
- 依赖超时和重试；
- 故障注入；
- 一次恢复演练；
- postmortem。

这样能证明你理解的是可靠性，而不是会用某个监控软件。
