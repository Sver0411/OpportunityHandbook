# 运维与 SRE

用一句话概括：用工程手段**让系统尽量不出事，出了事能快速恢复**。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 部署与配置、处理工单、跟班处理告警 |
| 中级 | 监控与告警体系、自动化脚本、容量与成本优化 |
| 资深 | 稳定性架构、SLO 制定、事故复盘机制、工具平台 |

日常有相当比例是**处理告警与排查**；改进工作（自动化、容量规划）需要主动争取。

## 团队与相邻岗位

与后端、DBA、安全、网络协作。与后端的边界：后端负责业务正确性，SRE 负责基础设施、发布体系与整体可靠性。

## 常见岗位名称

运维工程师、SRE、DevOps 工程师、平台工程师、基础架构工程师。

## 招聘与门槛

- 硬技能：Linux、网络基础、脚本（Shell/Python）、容器与编排、CI/CD；
- 加分：监控体系、可观测性、云平台认证；
- 学历：门槛中等，实操与事故处理经历更重要。

## 项目与面试怎么准备

- 证据：一套完整的监控与告警方案、一次事故的处理与复盘记录、自动化成果（省了多少人工）；
- 面试考法：Linux 与网络排障题（现场给现象让你查）、容量估算、故障处理思路；
- 高频考点：先止损再定位（不是先找根因）、以及「你怎么避免它再发生」。

## 第一份工作怎么看

看是否有值班能力培养与复盘文化（只做人工操作的岗位会停滞）。

## 3–5 年出口

平台工程、稳定性架构、安全方向、转后端或数据平台。

## 常见误区

- 把运维当「装环境」（现代运维是工程能力）；
- 只救火不改进（永远在处理同类告警）；
- 不做复盘，事故重复发生。

## 低成本试法

用一台云主机部署一个服务，配齐监控与告警，然后故意让服务挂一次，走完「发现 → 止损 → 复盘」流程。

## 一天通常是这样的

| 时间 | 做什么 | 备注 |
| --- | --- | --- |
| 9:00 | 交接班：看昨晚的告警与处理记录 | 交接要写文档 |
| 9:30 | 一条磁盘告警：先扩容止损，再查日志膨胀原因 | 先止损，后根因 |
| 11:00 | 把这次处理写成复盘：影响面、时间线、根因、防线 | 复盘是核心产出 |
| 14:00 | 优化部署流水线：把发布从 25 分钟压到 8 分钟 | 记录前后对比 |
| 16:00 | 容量评估：按当前增长，落后端存储还能用多久 | 用数据预测 |
| 17:00 | 更新值班手册与告警阈值 | 减少无效告警 |

## 一次真实的面试问答（原话）

> **面试官**：线上服务突然变慢，你先做什么？
> **候选人**：先确认影响面（多少用户、哪个功能），再做止损——扩容、回滚或限流；根因分析放在恢复之后。
>
> **面试官**：怎么判断该回滚？
> **候选人**：看最近一次变更时间与故障时间的相关性；如果变更后开始且范围与变更一致，优先回滚再排查。
>
> **面试官**：怎么避免同类事故？
> **候选人**：把这次的两条防线补上——磁盘水位提前告警、日志按天滚动；并把检查项写进发布清单。

**要点**：运维面试的纪律是**先止损、后根因、再防线**，顺序错了就丢分。

## SRE 不是“服务器管理员”

SRE 把可靠性当作工程问题：哪些服务必须多可靠、失败预算是多少、怎么监控、怎么发布、故障时怎样恢复。工作内容可能覆盖自动化、容量、可观测性、变更管理和事故响应，而不仅是执行命令。

## 从告警到根因，不要直接 SSH

先判断用户影响和范围，再看指标、日志、最近变更和依赖，形成假设后再验证。事故结束后要问“系统为什么允许这个错误扩大”，而不是只问“谁操作错了”。好的复盘会留下行动项和负责人。

## 入门项目怎么贴近真实工作

用一个小服务做部署、健康检查、指标、日志、备份与恢复演练；人为让依赖失败，再记录发现、缓解和恢复过程。能证明“我让系统更可恢复”，比搭十个中间件更像 SRE。
