# 数据分析师

用一句话概括：用数据回答业务问题——**定义指标、找到原因、给出可执行的结论**。

## 从取数到影响决策，中间有哪些层次

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 取数、做报表、维护看板 |
| 中级 | 指标体系设计、专项分析、给业务做决策支持 |
| 资深 | 指标体系治理、跨部门分析框架、带人 |

日常中约一半时间在**对齐口径与清洗数据**，而不是做「高大上」的建模。

## 分析、数据科学和数据工程怎么分

与业务、产品、数据工程、算法协作。边界：数据工程负责数据可用性（管道与仓库），算法负责预测与优化，分析负责解释与决策支持。

## BI、经营分析、产品分析到底差在哪

数据分析师、商业分析（BA）、业务分析师、数据运营、指标产品经理。

## SQL 只是门票，判断能力怎么被考

- 硬技能：SQL（必须）、Excel/BI 工具、基础统计、至少一门脚本语言；
- 软技能：把结论讲给非技术同事听、追问业务目标；
- 学历：门槛相对宽松，作品与实习更重要。

## 别只做 dashboard，要留下分析链

- 证据：一份完整分析报告（问题 → 数据 → 口径 → 结论 → 限制）；看板或仪表盘；
- 面试考法：SQL 题、指标设计题（「如何衡量 X」）、案例分析（给一个下降的指标，你怎么查）；
- 高频陷阱：把相关性当因果、不做口径说明。

## 第一份分析岗最怕变成报表搬运

看是否有机会接触业务决策（只做取数与报表的岗位成长有限）。

## 分析师之后的几条路

数据科学、数据产品、业务分析负责人、转产品/运营（懂数据的人在这些岗位有优势）。

## 相关性、口径和漂亮图表的陷阱

- 以为会用工具就是分析（工具是下限，判断是上限）；
- 只交数字不给结论与建议；
- 不写口径与限制。

## 用一个公开问题做一页可行动结论

找一份公开数据，回答一个真问题并写成一页报告：结论、依据、口径、限制、建议。


## 数据分析真正难的是“口径”和“因果解释”

SQL 和可视化只是工具。真实工作里最麻烦的是：同一个“活跃用户”不同团队定义不同、指标突然下降但原因不明、业务方已经有结论只想让你证明它。

因此数据分析的核心链路更接近：

业务问题 → 指标定义 → 数据可用性 → 查询与清洗 → 描述性分析 → 假设 → 验证 → 结论边界 → 建议 → 后续观察。

## 一次好分析应该怎样留下证据

不要只交一个 dashboard。至少留下：
- 指标口径和排除条件；
- 数据时间窗与来源；
- 异常值怎么处理；
- 哪些结论只是相关，不是因果；
- 关键分群；
- 哪个发现会改变决策；
- 分析之后应该继续监控什么。

如果一个分析最后不能告诉业务“接下来做什么、什么情况下结论会失效”，它很容易变成漂亮报表。

## 分析师和数据科学/数据工程的边界

分析师重点是**解释业务与支持决策**；数据工程师重点是数据稳定产生、治理和可用；数据科学更可能承担预测、实验和模型。

实际公司会混岗，所以判断岗位不要看 title，要看 JD 里是“取数/报表/经营分析”，还是“模型/实验”，还是“管道/仓库”。

## 项目怎么做得不像课程作业

选一个公开或自己采集的数据问题，不要先决定要画什么图。先写出一个业务问题和可行动结论，再做：
- 指标字典；
- 一份 SQL/数据处理过程；
- 一个异常或反直觉发现；
- 至少一次分群或对照；
- 一页“我不会下什么结论”。

这种作品更接近真实分析工作。
