# 解决方案工程师 / 售前

用一句话概括：**用技术把客户的问题讲清楚**，并把它翻译成公司能交付的方案。

## 从第一次客户会到方案落地，工作链是什么

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 支持演示与测试、整理方案材料、回答技术问题 |
| 中级 | 独立对接客户、设计方案、参与投标 |
| 资深 | 大客户方案负责人、行业方法论沉淀、带团队 |

时间大致分布：客户沟通 40%、方案与材料 35%、内部协作 25%。写代码的比例通常很低。

## 销售、产品、研发和交付之间怎么站位

与销售、产品、研发、交付协作。与销售的边界：销售负责商务，你负责技术可行性、方案与客户信任。

## 售前、Solutions、FAE、技术顾问怎么区分

售前工程师、解决方案工程师、技术顾问、Field Application Engineer（FAE）、Technical Account Manager。

## 技术深度和客户判断要同时过线

- 硬技能：至少一门技术栈的深度理解、能独立做演示与环境搭建；
- 软技能：**表达与倾听**是核心（能把技术讲给非技术人）、能承受被客户质疑；
- 学历：本科为主，技术背景 + 沟通能力比学历重要。

## 用一份真实方案证明你会收敛需求

- 证据：一次完整的技术方案（背景、约束、方案、取舍、成本）、一次面向非技术听众的讲解答辩；
- 面试考法：模拟客户场景（客户提出不合理需求怎么处理）、方案设计、技术深度追问；
- 高频考点：如何在「客户想要」与「产品能做到」之间找到第三条路。

## 能不能独立见客户决定成长速度

看是否有机会独立面对客户（只做内部材料的岗成长有限）与是否有技术支持体系。

## 从售前走向行业专家、产品或管理

行业解决方案专家、产品经理（懂客户的产品）、销售管理、转研发（需补工程能力）。

## 会讲 PPT 和真正的方案能力差在哪

- 以为「会讲 PPT」就够了（技术不到位会被客户一眼看穿）；
- 过度承诺（交付团队会替你承担后果）；
- 忽视内部协作，导致方案落不了地。

## 拿一个真实产品做一次客户场景方案

给一个真实产品写一份 3 页解决方案，找一个不了解该领域的人讲一遍，看能否让他复述要点。


## 一次售前项目真正怎么推进

真实售前不是“客户要什么就做什么 PPT”。更常见的链路是：

客户目标 → 现状与约束 → 决策链 → 技术方案 → POC → 风险与边界 → 商务交接 → 实施/交付。

其中最难的是前两步：客户常常能说出想买什么，却说不清为什么要买。好的售前会继续问业务目标、现有系统、数据来源、集成方式、安全要求和真正的决策标准。

## POC 为什么经常做着做着失控

POC 本来只该验证关键假设，但很容易变成“免费定制开发”。进入 POC 前最好写清：
- 这次只验证什么；
- 什么不在范围内；
- 成功标准是什么；
- 谁提供数据与环境；
- 什么时候停止；
- 成功后下一步是什么。

否则客户会不断把新需求塞进“顺便验证一下”。

## 技术深度和商业判断必须同时存在

只懂技术的人容易做出“很正确但卖不出去”的方案；只懂销售的人容易过度承诺。这个岗位真正的难点是把三件事对齐：

> 客户愿意买什么 × 产品真实能做什么 × 交付团队能长期维护什么。

面试里的场景题往往就在看你如何处理三者冲突。

## 怎么准备一份像真的售前作品

找一个真实产品，做一次完整方案：
- 客户背景与目标；
- 现有架构；
- 约束；
- 方案图；
- POC 目标；
- 风险；
- 成本；
- 哪些需求拒绝或延期；
- 交付后怎么判断成功。

重点不是 PPT 漂亮，而是每个结论都有依据。
