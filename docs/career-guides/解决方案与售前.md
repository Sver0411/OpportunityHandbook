# 解决方案工程师 / 售前

用一句话概括：**用技术把客户的问题讲清楚**，并把它翻译成公司能交付的方案。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 支持演示与测试、整理方案材料、回答技术问题 |
| 中级 | 独立对接客户、设计方案、参与投标 |
| 资深 | 大客户方案负责人、行业方法论沉淀、带团队 |

时间大致分布：客户沟通 40%、方案与材料 35%、内部协作 25%。写代码的比例通常很低。

## 团队与相邻岗位

与销售、产品、研发、交付协作。与销售的边界：销售负责商务，你负责技术可行性、方案与客户信任。

## 常见岗位名称

售前工程师、解决方案工程师、技术顾问、Field Application Engineer（FAE）、Technical Account Manager。

## 招聘与门槛

- 硬技能：至少一门技术栈的深度理解、能独立做演示与环境搭建；
- 软技能：**表达与倾听**是核心（能把技术讲给非技术人）、能承受被客户质疑；
- 学历：本科为主，技术背景 + 沟通能力比学历重要。

## 项目与面试怎么准备

- 证据：一次完整的技术方案（背景、约束、方案、取舍、成本）、一次面向非技术听众的讲解答辩；
- 面试考法：模拟客户场景（客户提出不合理需求怎么处理）、方案设计、技术深度追问；
- 高频考点：如何在「客户想要」与「产品能做到」之间找到第三条路。

## 第一份工作怎么看

看是否有机会独立面对客户（只做内部材料的岗成长有限）与是否有技术支持体系。

## 3–5 年出口

行业解决方案专家、产品经理（懂客户的产品）、销售管理、转研发（需补工程能力）。

## 常见误区

- 以为「会讲 PPT」就够了（技术不到位会被客户一眼看穿）；
- 过度承诺（交付团队会替你承担后果）；
- 忽视内部协作，导致方案落不了地。

## 低成本试法

给一个真实产品写一份 3 页解决方案，找一个不了解该领域的人讲一遍，看能否让他复述要点。

## 一天通常是这样的

| 时间 | 做什么 | 备注 |
| --- | --- | --- |
| 9:30 | 准备下午的客户演示环境（含离线备份） | 环境一定要自己先跑一遍 |
| 11:00 | 与销售对齐客户关注点：预算、时间、合规 | 先知道对方在意什么 |
| 14:00–15:30 | 客户演示：讲 20 分钟，答问 60 分钟 | 答问比演示重要 |
| 15:30 | 记录客户提出的三个硬需求，标出产品做不到的一条 | 当场不承诺 |
| 16:30 | 写方案初稿：约束 → 方案 → 取舍 → 成本 | 一天内出雏形 |
| 17:30 | 与研发确认「做不到的那条」有无替代方案 | 回来再答复客户 |

## 一次对话的典型走向

下面这段按面试与复盘里常见的追问整理，用来说明答法的结构，不是某位候选人的原话。

> **客户**：这个功能下个月能不能上线？
> **售前**：（不直接答应）「我先确认两件事：这个功能是走标准配置还是要定制？以及上线后由谁来运维？这决定工作量差别很大。我明天给你一个带时间点的方案，而不是现在拍一个日期。」
>
> **客户**：我们预算就这么多。
> **售前**：「那我把范围按优先级排一下：第一期的三项是必须的，第四项可以放到第二期。这样总价能落在预算内，同时不影响你们先跑起来。」

**要点**：售前的核心能力是**不承诺做不到的事，同时给出可行的替代路径**。

## 方案不是把产品功能重新念一遍

面对客户时，要先把业务目标、现有系统、约束、预算与决策人弄清。真正的方案通常不是“功能最多”，而是风险、成本和落地路径最清楚。客户要求做不到时，售前的价值是提出可接受的替代方案，而不是替研发承诺。

## 一次 PoC 怎么跑

先定义 PoC 要证明什么、数据从哪来、成功标准和不验证什么；再准备环境、接口和演示脚本；过程中记录客户真正关心的问题；结束后形成结论与未解决风险。没有提前定义成功标准的 PoC 很容易变成无限试用。

## 与 FDE 的区别

传统售前更偏需求澄清、方案与成交前技术支持；FDE 往往会更深入到客户现场的代码、数据、集成和生产落地。两者会重叠，但不能简单视为同一岗位。见 [Forward Deployed Engineer](FDE.md)。
