# 测试与质量（QA）

用一句话概括：**在设计阶段就把「怎么算对」问清楚**，并在交付前用最少的成本发现最多的问题。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 执行用例、提交缺陷、维护回归清单 |
| 中级 | 用例设计、自动化脚本、参与需求评审提质量风险 |
| 资深 | 质量体系与发布门槛、测试策略、工具平台 |

日常重点是**设计用例**（边界、异常、组合）与推动问题闭环，而不是「点点点」。

## 团队与相邻岗位

与开发、产品、运维协作。与开发的边界：开发负责实现与单元测试，测试负责系统级验证、边界与发布质量。

## 常见岗位名称

测试工程师、QA、自动化测试、测试开发（SDET）、质量工程师。

## 招聘与门槛

- 硬技能：用例设计方法、SQL、至少一门脚本语言、接口测试工具；
- 加分：自动化框架、性能测试、CI 集成；
- 学历：门槛相对宽松，作品与细致度更重要。

## 项目与面试怎么准备

- 证据：一份完整的测试计划（用例表 + 通过标准 + 已知缺陷），见 [项目测试计划模板](../tools/项目测试计划.md)；
- 面试考法：给一个功能现场设计用例、缺陷描述题、自动化思路；
- 高频考点：边界值、等价类、失败路径、以及「你怎么判断一个 bug 的优先级」。

## 第一份工作怎么看

看团队是否重视质量（有没有评审、灰度、回滚机制），这决定你能否建立真正的质量观。

## 3–5 年出口

测试开发（工具与平台）、质量负责人、转开发或运维（对质量体系理解深的人有优势）。

## 常见误区

- 认为测试比开发「低一等」（实际是质量责任的另一半）；
- 只会执行不会设计用例；
- 不参与需求评审，只在最后发现「需求本身就有问题」。

## 低成本试法

给一个你熟悉的产品写 20 条用例（含 5 条边界与 3 条异常），实际执行并提交一份缺陷报告。

## 一天通常是这样的

| 时间 | 做什么 | 备注 |
| --- | --- | --- |
| 9:30 | 参加需求评审，提三个质量风险点（权限、并发、超时） | 在源头拦问题 |
| 10:30 | 为新功能设计用例：正常、边界、异常共 28 条 | 边界值优先 |
| 13:30–15:00 | 执行用例，提交 5 个缺陷（含 1 个阻断级） | 缺陷描述要能复现 |
| 15:00 | 与开发确认缺陷优先级与修复计划 | 影响面决定优先级 |
| 16:00 | 把这批用例里可自动化的部分脚本化 | 一次投入长期收益 |
| 17:00 | 更新回归清单与发布检查项 | 发布把关不能靠记忆 |

## 一次真实的面试问答（原话）

> **面试官**：给你一个「登录」功能，你怎么设计用例？
> **候选人**：分四组——正常（正确账号密码）、边界（密码长度上下限、超长输入）、异常（错误密码、账号不存在、网络中断、重复提交）、以及安全相关（连续错误锁定、SQL 注入式输入）。大约 20 条，其中异常组占一半。
>
> **面试官**：一个 bug 开发说不是 bug，你怎么办？
> **候选人**：先拿用例与需求文档对齐「应该是什么行为」；如果需求没写清，就升级到产品确认。争论的地方通常是需求模糊，而不是谁对谁错。
>
> **面试官**：自动化到什么程度？
> **候选人**：核心流程与回归用例自动化，探索性测试留人工。不是为了覆盖率数字，而是为了发布前能快速重跑。

**要点**：测试面试考**用例设计能力**与**推动问题闭环的能力**。

## QA 的价值不是“找到更多 bug”

质量工程的目标是让风险在更早、更便宜的阶段暴露。测试对象包括功能、接口、数据、性能、兼容、安全和发布流程。成熟 QA 会参与需求评审，因为很多 bug 本质上是需求定义不清，而不是代码写错。

## 怎么从手工测试走向质量工程

先学会把需求变成测试模型：正常路径、边界、状态转换和失败路径；再把稳定、重复的检查自动化；最后建立缺陷分类、回归范围与上线门禁。自动化不是越多越好——频繁变化、判断主观的场景可能更适合人工探索。

## 一个高价值项目

给一个已有系统设计测试策略，而不是从零写测试框架。明确风险优先级、覆盖哪些层、哪些不测、如何构造故障、发现问题后如何防止复发。
