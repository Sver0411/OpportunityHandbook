# 测试与质量（QA）

用一句话概括：**在设计阶段就把「怎么算对」问清楚**，并在交付前用最少的成本发现最多的问题。

## 从执行用例到设计质量策略

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 执行用例、提交缺陷、维护回归清单 |
| 中级 | 用例设计、自动化脚本、参与需求评审提质量风险 |
| 资深 | 质量体系与发布门槛、测试策略、工具平台 |

日常重点是**设计用例**（边界、异常、组合）与推动问题闭环，而不是「点点点」。

## 质量不是测试团队一个人的事

与开发、产品、运维协作。与开发的边界：开发负责实现与单元测试，测试负责系统级验证、边界与发布质量。

## 功能、自动化、性能、质量平台怎么分

测试工程师、QA、自动化测试、测试开发（SDET）、质量工程师。

## 会工具之外，风险判断怎么被考

- 硬技能：用例设计方法、SQL、至少一门脚本语言、接口测试工具；
- 加分：自动化框架、性能测试、CI 集成；
- 学历：门槛相对宽松，作品与细致度更重要。

## 做一套围绕风险而不是数量的测试

- 证据：一份完整的测试计划（用例表 + 通过标准 + 已知缺陷），见 [项目测试计划模板](../tools/项目测试计划.md)；
- 面试考法：给一个功能现场设计用例、缺陷描述题、自动化思路；
- 高频考点：边界值、等价类、失败路径、以及「你怎么判断一个 bug 的优先级」。

## 能否参与需求和发布决定成长速度

看团队是否重视质量（有没有评审、灰度、回滚机制），这决定你能否建立真正的质量观。

## QA 的技术和管理分叉

测试开发（工具与平台）、质量负责人、转开发或运维（对质量体系理解深的人有优势）。

## 测试用例越多为什么不一定越好

- 认为测试比开发「低一等」（实际是质量责任的另一半）；
- 只会执行不会设计用例；
- 不参与需求评审，只在最后发现「需求本身就有问题」。

## 给一个项目做一次风险地图和故障注入

给一个你熟悉的产品写 20 条用例（含 5 条边界与 3 条异常），实际执行并提交一份缺陷报告。


## QA 的目标不是“找 bug”，而是降低发布风险

手工测试、自动化、性能、可靠性、质量平台都属于质量工作的一部分。成熟 QA 会从需求阶段就问：什么最可能出错、哪个错误代价最高、哪些路径值得自动化、上线后怎么发现逃逸问题。

## 怎样从需求变成测试策略

不要把 PRD 每句话机械变成 case。先做风险拆解：

核心路径 → 高风险边界 → 外部依赖 → 数据状态 → 权限 → 并发/性能 → 恢复。

再决定：
- 哪些必须每次回归；
- 哪些适合自动化；
- 哪些只能真实环境验证；
- 哪些可以通过监控而不是发布前测试发现。

这就是测试工程和“点点点”的差别。

## 自动化测试真正难在哪里

写脚本并不难，难的是让测试长期可信。常见问题包括：
- 测试本身不稳定；
- 环境和数据不可控；
- 大量 UI 自动化导致维护成本爆炸；
- case 很多但没有覆盖真正风险；
- CI 失败大家习惯性重跑。

好的自动化策略更强调测试金字塔、稳定数据、明确失败原因和快速反馈。

## 项目怎么证明 QA 能力

可以拿一个开源或自建系统：
1. 画风险地图；
2. 写关键路径自动测试；
3. 做一次故障/边界注入；
4. 记录 bug 从发现到修复；
5. 建一个最小 CI；
6. 写一份 release checklist。

这比“写了 200 条测试用例”更能说明质量判断。
