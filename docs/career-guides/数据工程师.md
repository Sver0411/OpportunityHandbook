# 数据工程师

用一句话概括：让数据**准时、完整、可追溯**地从源头流到使用者的手上。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 写 ETL/ELT 任务、修数据缺陷、监控任务失败 |
| 中级 | 数据模型设计、调度与依赖管理、质量校验 |
| 资深 | 平台与架构、成本与性能治理、数据治理规范 |

日常里大部分时间在处理「数据为什么会晚/会错/会对不上」。

## 团队与相邻岗位

与分析、算法、后端、运维协作。与后端的边界：后端负责在线业务系统，数据工程负责离线/准实时的数据流动与建模。

## 常见岗位名称

数据工程师、ETL 工程师、数仓开发、大数据开发、数据平台工程师。

## 招聘与门槛

- 硬技能：SQL（深度）、一门脚本语言、调度工具、数据仓库概念、至少一种大数据组件；
- 加分：数据质量体系、成本优化经验、流处理；
- 学历：门槛中等，工程能力与项目经历更重要。

## 项目与面试怎么准备

- 证据：一条真实跑通的管道（含调度、重试、质量校验），附数据量与运行时长；
- 面试考法：SQL 深度题、数据建模题（维度建模/拉链表）、管道设计题（幂等、重跑、迟到数据）；
- 高频追问：「任务重跑会重复计数吗？」——幂等性是核心概念。

## 第一份工作怎么看

看数据规模与规范程度：没有质量校验与调度的团队，成长会慢。

## 3–5 年出口

数据平台/架构、数据治理、分析方向（懂管道做分析更稳）、转后端。

## 常见误判

- 只会写 SQL 不会设计管道（漏数据、重跑出错）；
- 忽视成本（大规模任务的开销常被忽略）；
- 不做数据质量校验，把问题留给下游。

## 低成本试法

用一台云主机搭一个完整管道：采集 → 清洗 → 建模 → 调度 → 校验，记录失败处理方式。


## 数据工程师交付的不是“表”，而是可信的数据供应链

从埋点/业务库到最终报表或模型，中间会经过采集、传输、清洗、建模、调度、质量检查、权限和血缘。真实难点不是 Spark/SQL 会不会，而是**数据出了错谁能发现、多久恢复、下游会不会被悄悄污染**。

## 一条数据管道应该问哪些问题

- 上游 schema 变了会怎样；
- 重跑会不会重复写入；
- 迟到数据怎么处理；
- 任务失败后从哪里续；
- 分区和索引是否支持实际查询；
- 数据质量规则是什么；
- 哪些字段是敏感信息；
- 下游怎么知道口径发生变化；
- 成本在哪一层增长最快。

这些问题把“会 ETL”变成“能维护数据平台”。

## 项目证据比技术栈列表重要

学生项目可以做一个小型但完整的 pipeline：

采集 → 原始层 → 清洗层 → 业务层 → 调度 → 数据质量检查 → dashboard/下游消费。

然后故意制造：
- 重复输入；
- schema 变化；
- 任务中断；
- 迟到数据。

记录系统如何恢复。这样的项目即使用的工具不复杂，也比“Kafka + Flink + Spark 全家桶”更像真正数据工程。

## 职业分支怎么选

靠近业务的数据工程更重仓库建模与分析支持；平台型更重基础设施、调度、流处理和可靠性；ML Data/Feature Platform 会更靠近机器学习。

第一份工作最好确认你会不会只做 SQL 取数，还是能接触数据模型、调度和质量治理。
