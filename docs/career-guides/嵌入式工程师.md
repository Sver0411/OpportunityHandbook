# 嵌入式工程师

用一句话概括：让代码在**资源受限、会掉电、会干扰**的真实硬件上可靠运行。

## 从寄存器到产品，嵌入式到底分几层

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 驱动适配、外设调试、按规格实现功能 |
| 中级 | 系统架构（任务划分、通信协议）、功耗与稳定性优化 |
| 资深 | 平台选型、跨软硬件方案、量产问题处理、带人 |

日常工作里相当一部分时间是**用示波器、逻辑分析仪、串口日志找问题**，而不是写代码。

## 软硬件交界处怎么协作

与硬件工程师、测试、结构、产线协作。与硬件工程师的边界：硬件负责电路与器件选型，嵌入式负责固件与软硬件接口。

## MCU、BSP、驱动、Linux、汽车不是一回事

嵌入式软件工程师、固件工程师、驱动开发、MCU 开发、BSP 工程师、汽车电子软件工程师。

## 行业分布

消费电子、汽车电子、工业控制、医疗设备、通信设备、智能家居。行业周期差异大，选行业比选公司更影响长期体验。

## C、RTOS、协议到底要会到什么程度

- 硬技能：C 语言、一款 MCU/RTOS、通信协议（UART/I2C/SPI/CAN）、基本电路阅读能力；
- 加分：功耗优化、Linux 驱动、量产经验；
- 学历：本科为主，部分岗位接受专科 + 强动手能力。

## 真机、故障和测试才是核心证据

- 证据：真机、长时间运行记录、功耗数据、现场部署或量产经历的细节；
- 面试考法：C 语言与内存问题、中断与并发、协议细节、调试经历（「遇到过最难的 bug」几乎必问）；
- 一个高价值准备：把一次「偶发故障」的排查过程写清楚。

## 第一份工作其实在选行业约束

优先选能接触到完整产品周期的团队（从打样到量产），而不是只做维护。

## 嵌入式之后的技术分叉

系统架构、汽车电子/工业控制专家方向、Linux 与边缘计算、技术管理、转硬件或产品。

## 点亮外设以后，真正难的才开始

- 以为只会点亮外设就行（稳定性与功耗才是真门槛）；
- 忽视工具与文档（量产问题往往出在测试与规范）；
- 不看行业周期，只比薪资。

## 拿一块板做一次完整故障闭环

用一块开发板做一次 72 小时连续采集，记录丢包、重启与功耗——能坚持调完的人通常适合这个方向。


## 嵌入式不是一个岗位，而是一组完全不同的工作

MCU 应用、BSP、驱动、Embedded Linux、汽车电子、工业控制、无线协议栈虽然都可能叫“嵌入式”，但日常完全不同。

MCU 应用更靠近外设、RTOS 与产品逻辑；BSP/驱动更贴近启动、寄存器和硬件接口；Embedded Linux 会深入内核、设备树、驱动与系统服务；汽车岗位还会受到功能安全、AUTOSAR、CAN 等体系影响。

找工作前最好先确定自己想靠近哪一层，而不是把所有“嵌入式技能树”全部学一遍。

## 一个真实功能怎样从原理图走到稳定运行

假设你要接一个新的 I²C 传感器，生产级流程比“读出数值”长得多：

1. 看 datasheet、电气条件和时序；
2. 对照原理图确认电源、上拉与引脚；
3. 先做最小通信验证；
4. 设计驱动接口与错误码；
5. 处理 NACK、总线占用、设备掉线；
6. 接入任务调度或状态机；
7. 做异常注入和长时间运行；
8. 用逻辑分析仪/示波器验证难以解释的问题；
9. 记录版本、接线、测试条件和已知限制。

面试里真正有价值的故事通常发生在第 5～8 步，而不是“我会 I²C”。

## 怎样把 ESP32/STM32 项目做成求职证据

至少留下四类东西：**接线与架构、故障处理、量化测试、调试过程**。

例如 LoRa 项目不要只写“完成无线通信”，可以记录不同距离/遮挡下的包统计、设备掉电恢复、UART/AUX 异常、长期运行、功耗，以及一次偶发问题如何定位。真实失败记录往往比功能列表更能证明你会工程。

## 行业选择会改变技术路径

消费电子强调成本、功耗与快速量产；汽车更重流程、可靠性与规范；工业控制重长期稳定和现场环境；医疗设备还会增加法规和验证要求。

所以第一份工作不仅是在选公司，也是在选以后最熟悉的约束类型。
