# 前端工程师

用一句话概括：把设计变成用户能用、快、稳的界面，并处理浏览器、网络与状态带来的各种不确定。

## 前端复杂度从哪里长出来

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 按设计稿实现页面、修样式与兼容问题、接接口 |
| 中级 | 组件抽象、状态管理设计、性能优化、参与技术选型 |
| 资深 | 前端架构、工程化（构建/发布/监控）、跨端方案、带人 |

容易被忽略的部分：**性能、错误监控、可访问性、加载失败与降级**——这些占了相当比例的工作量。

## 设计、后端和产品之间的边界

通常与产品、设计、后端、测试协作。与设计的边界：设计负责视觉与交互方案，前端负责实现与可行性反馈；与后端的边界：接口契约由双方共同定义。

## 业务前端之外还有哪些前端

前端开发、Web 前端、React/Vue 工程师、客户端（Web 方向）、跨端工程师、Node 全栈。

## 招聘为什么不只看会不会 React

- 学历：校招有筛，社招看作品；
- 硬技能：HTML/CSS/JS 基础、一个主流框架、构建工具、浏览器调试；
- 软技能：与设计沟通、能把「做不到」说成「这样做要多少代价」。

## 作品怎么从“好看”变成工程证据

- 证据：**可访问的线上地址**比截图有力得多；加上性能数字（首屏、包体）、兼容清单、错误监控；
- 面试考法：JS 基础题、手写题（防抖、深拷贝）、框架原理、性能优化思路、项目追问；
- 如果只能准备一件事：把自己的项目部署上线，并说清一次性能优化的过程。

## 新人最值得接触哪类前端问题

看团队是否有设计规范与代码评审、是否重视性能与质量（还是只堆需求）。

## 前端之后可以往哪里走

前端架构、跨端/客户端、Node 服务端、技术管理、独立开发（前端技能最容易做独立产品）。

## 只看页面截图会错过什么

- 把「会切图」当成前端（真正的难点在状态、性能、工程化）；
- 只学框架不学基础（浏览器与语言基础决定上限）；
- 忽视质量：线上报错没人管，技术债越积越多。

## 做一个有状态、有失败路径的真实页面

两周做一个小工具并上线，记录首屏时间与包体大小，再让三个人用一次。


## 前端真正困难的部分不是“把页面写出来”

页面能显示只是起点。真实前端要同时处理：状态、网络、权限、性能、浏览器差异、可访问性、埋点、异常和多人协作。

举一个支付结果页：设计稿只有几张图，但工程问题可能包括重复提交、弱网、支付状态延迟、返回历史页、登录过期、多语言、移动端键盘、埋点一致性。前端的深度往往藏在这些“截图看不出来”的地方。

## 从视觉稿到生产页面的工作链

更接近真实工作的流程是：

设计稿与需求 → 澄清交互状态 → 组件与数据边界 → API 契约 → 错误/加载/空状态 → 实现 → 性能与可访问性 → 埋点 → 联调 → 灰度 → 线上反馈。

因此一个好的前端作品，不应该只有最终截图。最好能展示：
- 状态设计与关键交互；
- 为什么这样拆组件；
- 数据缓存和请求策略；
- 首屏/交互性能怎么测；
- 一个真实兼容或线上问题怎么定位；
- 如何让设计与实现长期一致。

## 前端岗位内部差异很大

业务前端重交付和产品协作；基础设施/工程化更看构建、编译、性能和开发者体验；可视化前端会更强调图形、Canvas/WebGL 与数据；跨端则要处理原生能力和多平台边界。

所以“我想做前端”还不够。看 JD 时要继续问：**这个团队的主要复杂度到底在业务、体验、性能还是工具链。**

## 面试项目怎么避免只讲 UI

如果面试官问“最难的问题”，不要回答“还原设计稿”。更值得准备的是：一次状态错乱、一次性能瓶颈、一次跨端/兼容问题、一次 API 变化导致的重构，以及你如何验证修复没有引入新问题。
