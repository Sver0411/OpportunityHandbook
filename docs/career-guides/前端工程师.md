# 前端工程师

用一句话概括：把设计变成用户能用、快、稳的界面，并处理浏览器、网络与状态带来的各种不确定。

## 日常与层级

| 层级 | 主要工作 |
| --- | --- |
| 初级 | 按设计稿实现页面、修样式与兼容问题、接接口 |
| 中级 | 组件抽象、状态管理设计、性能优化、参与技术选型 |
| 资深 | 前端架构、工程化（构建/发布/监控）、跨端方案、带人 |

容易被忽略的部分：**性能、错误监控、可访问性、加载失败与降级**——这些占了相当比例的工作量。

## 团队与相邻岗位

通常与产品、设计、后端、测试协作。与设计的边界：设计负责视觉与交互方案，前端负责实现与可行性反馈；与后端的边界：接口契约由双方共同定义。

## 常见岗位名称

前端开发、Web 前端、React/Vue 工程师、客户端（Web 方向）、跨端工程师、Node 全栈。

## 招聘与门槛

- 学历：校招有筛，社招看作品；
- 硬技能：HTML/CSS/JS 基础、一个主流框架、构建工具、浏览器调试；
- 软技能：与设计沟通、能把「做不到」说成「这样做要多少代价」。

## 项目与面试怎么准备

- 证据：**可访问的线上地址**比截图有力得多；加上性能数字（首屏、包体）、兼容清单、错误监控；
- 面试考法：JS 基础题、手写题（防抖、深拷贝）、框架原理、性能优化思路、项目追问；
- 如果只能准备一件事：把自己的项目部署上线，并说清一次性能优化的过程。

## 第一份工作怎么看

看团队是否有设计规范与代码评审、是否重视性能与质量（还是只堆需求）。

## 3–5 年出口

前端架构、跨端/客户端、Node 服务端、技术管理、独立开发（前端技能最容易做独立产品）。

## 常见误区

- 把「会切图」当成前端（真正的难点在状态、性能、工程化）；
- 只学框架不学基础（浏览器与语言基础决定上限）；
- 忽视质量：线上报错没人管，技术债越积越多。

## 低成本试法

两周做一个小工具并上线，记录首屏时间与包体大小，再让三个人用一次。

## 一天通常是这样的

| 时间 | 做什么 | 备注 |
| --- | --- | --- |
| 10:00 | 与设计对齐新页面的交互细节（含空态与加载态） | 空态常被漏掉 |
| 10:30–12:00 | 实现列表页：先搭结构，再接接口，最后接状态 | 用自己的测试数据先跑通 |
| 14:00–15:00 | 处理兼容与响应式问题（一个弹窗在小屏溢出） | 用真机或设备模拟器 |
| 15:00–16:30 | 性能自查：首屏 2.4 秒 → 图片压缩 + 路由懒加载 → 1.6 秒 | 记录改动前后 |
| 16:30–17:30 | 修线上报错：错误监控里有个空指针，定位到一处可选字段 | 加防御 + 补测试 |
| 17:30 | 把这次改动写进变更说明 | 方便回滚与追踪 |

## 一次真实的面试问答（原话）

> **面试官**：首屏 2.4 秒是怎么测的？
> **候选人**：用 Lighthouse 在本地生产构建上测的，也看了真实用户的监控数据，两者差 0.3 秒左右。
>
> **面试官**：为什么不直接上 SSR？
> **候选人**：第一版内容是登录后才可见，SSR 收益有限，反而增加部署复杂度；我先做了资源层优化。如果首屏还要压到 1 秒以内，我会再评估 SSR 或预渲染。
>
> **面试官**：兼容性怎么保证？
> **候选人**：目标用户里有两成还在用较老的浏览器，我列了一份兼容清单，改动后都过一遍。

**要点**：说清「测的方式」「被否掉方案的代价」「你自己的判断」。

## 前端工作的难点不在把页面写出来

真实前端工作同时处理设计还原、交互状态、数据一致性和运行环境。一个“按钮点一下弹窗”的需求，还要考虑加载中、失败、重复点击、权限、键盘操作、移动端、国际化与埋点。真正拉开差距的是**状态建模与边界处理**，不是组件数量。

可以拿一个现成页面做练习：把正常路径之外的所有状态列出来——空数据、慢网、接口失败、登录过期、表单重复提交——然后让 UI 在每种状态下都有明确行为。这比再仿一个首页更接近工作。

## 性能和可访问性怎么进入工作流

不要先背阈值。先学会通过浏览器工具回答：时间花在网络、脚本、渲染还是图片？哪些资源阻塞首屏？一次交互为什么卡？可访问性也不是最后补一个属性，而是从语义结构、焦点顺序和键盘操作开始。能定位问题来源，比记住某个数字更重要。

## 项目面试会追到哪里

准备一个项目时，按**状态、性能、工程化、失败恢复**四条线各准备一个真实例子：为什么选这个状态管理方案、接口慢时怎么表现、列表规模放大后怎么处理、线上白屏如何定位。
