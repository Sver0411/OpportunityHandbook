# 数据管理与可复现性

可复现不是道德要求，而是**让结论站得住的技术条件**。这一页按数据、代码、环境三层给出做法。

## 数据层

- **版本**：数据集要有版本号与获取时间；自己采集的数据要写明采集条件与清洗步骤；
- **划分**：训练/验证/测试的划分方式必须写明（随机？按时间？按人？），并固定下来；
- **泄漏（leakage）**：最隐蔽也最致命的一类错误。常见形态：
  - 预处理在划分之前做（用全体数据算均值/归一化，把测试集信息带进训练）；
  - 同一人的多条记录被分到不同集合；
  - 时间序列用了未来信息；
  - 特征里含有标签的代理变量。
  检查方法：问「这个特征在预测时点真的可得吗？」
- **元数据**：来源、许可、采集时间、缺失处理方式，一并留档。

## 代码层

- 一个命令能从原始数据跑到最终表格；
- 随机种子写死并记录，多处随机要分别固定；
- 中间产物可重建，不依赖手工修改的文件；
- 关键脚本写注释说明「为什么」而不是「做了什么」。

## 环境层

- 依赖版本锁定（requirements / lock 文件 / 容器镜像）；
- 硬件与系统信息记录（GPU 型号、CUDA 版本、操作系统）；
- 运行命令与环境变量写进 README，让别人的第一次尝试能成功。

## artifact 与 FAIR

可交付的研究产物（数据、代码、模型、配置）应尽量做到：可被发现（有稳定链接）、可访问（不用申请）、可互操作（通用格式）、可复用（有许可与说明）。这就是 FAIR 的四条原则。做不到全部，至少做到「公开代码 + 说明数据获取方式」。

## reproducibility 与 replicability 的区别

- **reproducibility（可复现）**：用同一份数据与代码，能得到同样结果；
- **replicability（可重复）**：换一批数据或换一种实现，结论仍然成立。

两者都要：只做到前者，说明代码没问题；只做到后者，说明现象稳定。**写作时要说清你验证的是哪一种。**

## 自查清单

- 我的划分方式写清楚了吗？预处理在划分之前还是之后？
- 随机种子固定了吗？跑三次结果差异多大？
- 别人按 README 能在自己机器上跑起来吗？
- 原始数据、中间结果、最终结果分别在哪个目录？
- 我声称的是可复现还是可重复？
