# Baseline 怎么设计

没有基线的结果不是结果，只是一个数字。基线的作用是回答「**这个提升相对于什么**」。

## 基线要回答的三个问题

1. 这个问题有多难？（随机猜、多数类、简单规则的得分就是难度下限）
2. 现有最好方法做到了什么程度？（决定你的方法是改进还是重做）
3. 你的提升来自方法本身，还是来自更多算力、更多数据、更多调参？

第三个问题最容易被忽略，也最容易被审稿人抓住。

## 常见的四类基线

| 类型 | 例子 | 用途 |
| --- | --- | --- |
| 平凡基线 | 随机、多数类、上一次的值 | 证明任务不是「随便做做就行」 |
| 简单启发式 | 规则法、线性模型、最近邻 | 证明复杂方法有必要 |
| 强基线 | 当前主流方法 + 官方实现 + 同等调参预算 | 证明你的方法真的有竞争力 |
| Oracle | 知道答案上界 | 说明还有多少空间 |

## 公平比较的前提

- **相同数据划分**：同一个训练/验证/测试集，或至少同分布同规模；
- **相同预算**：算力、调参次数、训练轮数可比；不同预算要在文中说明；
- **相同评估协议**：指标定义、阈值选择方式、是否用测试集调参；
- **可复现**：基线的代码与配置要能跑起来，而不是引用别人论文里的数字了事；
- **报告不确定性**：多次运行给均值与波动，不给「最好一次」。

## 把基线做弱是严重问题

有些论文会无意（或有意）地把基线做弱：用未调参的官方实现、在不利条件下跑对手方法、只跑一次、换更少的数据。这样得到的提升没有意义，原因有三：

- 与真实水平不符，其他人复现不出来；
- 会把后续研究引向错误方向；
- 一旦被识别，整个工作的可信度都会受影响。

**自检方法**：把自己当作最挑剔的审稿人，问「如果我用对手的方法，会不会得到更好结果？」答不出，就去把基线做强一次。

## oracle 与对照组

- **oracle** 给的是上界（如果知道正确答案，最高能做到多少），用来判断改进空间；
- **对照组（control）** 在实验科学里是必须的：只改变一个变量，其余保持不变；
- **消融**（去掉组件）与基线是两件事：前者回答「哪一部分起作用」，后者回答「比现有方法好不好」。见 [Ablation 怎么设计](消融实验.md)。

## 一份可用的基线清单

写论文前把这张表填满，缺格就说明准备不足：

- 任务与数据集是什么；
- 已有方法有哪些，各自在什么条件下最好；
- 我选谁做基线，为什么；
- 预算如何对齐；
- 我的方法预期在哪一维度超过它，超过多少才算有意义。
