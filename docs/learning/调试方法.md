# 如何 Debug：从现象到根因

调试不是「碰运气改代码」，而是一套可以重复的流程。核心原则：**每次只改一个变量，并且事先预测结果。**

## 九步流程

1. **重现**：让错误稳定出现（同输入、同顺序、同环境）。不能重现的问题，先解决「为什么不能重现」；
2. **写下现象**：报错原文、期望结果、实际结果、发生频率；
3. **缩小范围**：注释掉一半代码、换更小输入、换一组参数；
4. **建立假设**：写下「我认为是因为 X」，并写下「如果是，那么改 Y 会让错误消失」；
5. **检查输入**：打印/查看实际传进来的数据，而不是你以为传进来的数据（这一条能解决相当比例的问题）；
6. **加日志**：在关键路径打点，看流程实际走到哪一步；
7. **最小复现**：把问题缩到十行以内——很多 bug 在缩的过程中自己就暴露了；
8. **二分定位**：改动多时用二分查找：注释后半段、切一半数据、回退一半提交；
9. **验证修复**：改完之后，用原来能复现的输入跑一遍；再跑一遍相关回归测试。

## 一个真实错误案例

现象：定时任务偶尔失败，报「文件不存在」，但文件明明在。

- 重现：手动跑不失败，只有定时触发时失败 → 说明与运行环境有关；
- 假设：定时任务的工作目录与手动执行不同；
- 验证：把当前工作目录打印出来 → 定时任务下是 `/`，不是项目目录；
- 根因：代码用了相对路径；
- 修复：改为基于脚本位置的绝对路径；同时补一条「输出当前目录」的启动日志，避免同类问题再排查一次。

**注意最后的动作**：修 bug 的时候顺手加一条能更早发现它的日志或测试，这是把一次故障变成长期收益的方式。

## 常见反模式

- 同时改三处，然后「好了」——但不知道是哪一处起作用；
- 不重现就开始瞎改；
- 只看代码不看实际数据；
- 用 try/except 把错误吞掉；
- 修完不写测试，下次同样的问题再来一遍。

## 独立性与怀疑顺序

排查时按「最可能且最容易验证」排序，而不是按你的直觉最喜欢的假设。优先怀疑：最近改动过的地方、输入数据、环境与版本、并发与时序、最后才是「框架有 bug」。

## 自检

- 我能不能用一句话描述现象与复现步骤？
- 我的假设是什么，验证结果支持它吗？
- 修复之后，我加了什么防止它再发生？
